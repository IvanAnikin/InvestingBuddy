# V3.17 — Research Escalation Loop

**Status:** Phase 0 design. **V3.17.1 implemented** (migration 040 + `research_decisions`); V3.17.2 onward not started.
**Baseline when designed:** `main` = `60fc8d0`, Alembic **039**.
**Current:** `main` = `9871044` (V3.16.1b accepted), Alembic **040** after V3.17.1.
**Author's note:** every claim below is a traced fact with a file and line. Where I could

## 0. The finding, in one paragraph

The escalation loop is **almost entirely built already, three times over, and none of the
three pieces is connected to the next.** The discovery council already decides
`research_next` / `monitor_for_evidence` / `reject_for_now` / `insufficient_data` per
candidate. A durable job queue with leases, idempotency, retries and a worker already
exists. Research gaps already carry forward into the next run's plan. What does not exist
is a **controller**: nothing reads a decision and creates work, and nothing starts the next
run that the carried-forward gaps were prepared for.

V3.17 should therefore be **one small deterministic controller plus one decision table** —
not a new queue, not a new agent, and not a second gap system.

### 1.1 Where the decisions live — the answer to the brief's question

**JSON on the run. Not database state. Not per-candidate. Not queryable.**

| Property | Reality |
|---|---|
| Storage | `discovery_runs.config_json` → `["discovery_council"]["review"]` (JSONB) |
| Granularity | the **run**, not the candidate |
| Candidate column | **none.** `DiscoveryCandidate` has no `decision`, `research_required`, `bucket` or `verdict` field |
| Queryable | no — no column, no index, no status |
| Origin | **LLM.** `internal_action` is emitted by the chair (`discovery_prompts.py:70`) |
| Trusted? | no — coerced to an allowlist by `discovery_citation_checker.py:134` |

**Backend consumers of `candidates_to_research_next`: zero.** The only references are the
API schema (`schemas/market_discovery.py:652`), the storage dict
(`llm/discovery_schemas.py:336,397`) and the bucket map (`llm/discovery_council.py:86`).
Nothing executes it. This is the repository's signature failure mode — *metadata existed
but was never connected to execution* — in its purest form yet.

### 1.5 Other gap surfaces (distinct, do not merge)

| Surface | Where | Scope |
|---|---|---|
| `research_gaps` | V3 ledger | per research run — **the actionable one** |

## 2. Proposed architecture

```
  Discovery ──► DiscoveryCandidate
       │
       ▼
  Discovery Council ──► internal_action  (LLM, coerced to allowlist)
       │
       ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  RESEARCH DECISION CONTROLLER   (NEW — deterministic)       │
  │  reads: coerced action, blocking_gap_count, confidence,     │
  │         prior decisions, cost ledger, escalation round      │
  │  writes: research_decisions row                             │
  └─────────────────────────────────────────────────────────────┘
       │
       ▼
  research_decisions  (NEW table — the DECISION's own lifecycle)
       │
       ▼  enqueue (idempotency_key = decision id)
  research_jobs  (EXISTING — migration 019, leases, retries)
       │
       ▼
  worker.run_worker  (EXISTING)
       │
       ▼
  company research → V3 pipeline → filing bridge (V3.16) → corpus
       │
       ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  EVIDENCE DELTA MEASUREMENT  (NEW — deterministic, cheap)   │
  │  indexed chunks before/after; gaps closed; facts added      │
  └─────────────────────────────────────────────────────────────┘
       │
       ├── improved? ──► re-plan with carry-forward ──► Council
       └── not improved? ──► terminal, with the reason recorded
```

The only genuinely new parts are the **controller**, the **decision table**, and the
**evidence-delta measurement**. Everything else is existing infrastructure being *called*.

## 3. State machine

```
              ┌──────────────┐
              │  DISCOVERED  │  DiscoveryCandidate row exists
              └──────┬───────┘
                     ▼
            ┌──────────────────┐
            │ COUNCIL_REVIEWED │  internal_action assigned + coerced
            └──────┬───────────┘
                   ▼
       controller evaluates deterministic predicates
        ├── no  ──► MONITORED / REJECTED / INSUFFICIENT_EVIDENCE  (terminal)
        └── yes ─►┌───────────────────┐
                  │ RESEARCH_REQUIRED │  research_decisions row created
                  └─────────┬─────────┘
                            ▼
                     ┌────────────┐
                     │   QUEUED   │  research_jobs row (idempotency_key = decision id)
                     └─────┬──────┘
                           ▼
                     ┌────────────┐
                     │  RUNNING   │  worker holds the lease
                     └─────┬──────┘
                           ▼
                ┌────────────────────┐
                │  EVIDENCE_UPDATED  │  delta measured
                └─────────┬──────────┘
                          ▼
            improved AND round < max AND budget left?
             ├── yes ──► REANALYSIS ──► (back to QUEUED, round+1)
             └── no  ──► ┌───────────┐
                         │ COMPLETED │  or EXHAUSTED / ABANDONED, reason recorded
                         └───────────┘
```

Terminal states are terminal. `EXHAUSTED` (no improvement) and `ABANDONED` (budget//round
cap) are distinct from `COMPLETED`, because "we stopped learning" and "we stopped
spending" need different follow-ups and a reader must be able to tell them apart.

## 4. Architecture decisions

### 4.1 Research queue — **Option B/C: reuse `research_jobs`, plus a small decision table**

| Option | Verdict |
|---|---|
| **A** — new `research_queue` entity | **Rejected.** It would duplicate `research_jobs`, which already has idempotency (DB-enforced), leases, heartbeats, attempts, `available_at`, cancellation and dead-lettering, plus `claim_next` with `FOR UPDATE SKIP LOCKED` and a worker. Building a second queue beside a working one is how two sources of truth start. |
| **B** — extend company research jobs | **Chosen for the QUEUE.** `research_jobs.payload_json` carries the escalation context; `idempotency_key` gives duplicate prevention for free. |
| **C** — use existing task/gap infrastructure | **Chosen for the INPUT.** `research_gaps` + `carry_forward_questions` already turn gaps into the next run's questions. V3.17 adds the trigger, not a parallel task system. |

**Why a decision table is still needed.** A job is one execution; a decision has a longer
life and may span several. `research_jobs` rows are consumed and retried; a decision must
survive them to answer "why is this company being researched, how many rounds has it had,
what did each round improve, and when do we stop?" Putting that in `payload_json` would
make it unqueryable — the precise mistake §1.1 documents.

### 4.2 Task creation — **deterministic controller, LLM as signal only**

**Rejected: LLM-controlled (`research_required=true` starts work).**

This repository already answered this question in the opposite direction and wrote the
reason down. `playbooks/schema.py` refuses to let a model set `blocking=True` because "a
model able to set one could stop every run." The inverse is worse: a model able to create
work could start unbounded *paid* work. `internal_action` is already treated as untrusted
— `discovery_citation_checker.py:134` coerces an out-of-vocabulary action.

**Chosen: the council's coerced action is one input to a deterministic predicate.**

```
create_decision(candidate) IF ALL:
  1. coerced internal_action == "research_next"            (model SIGNAL)
  2. candidate.blocking_gap_count > 0 OR confidence < threshold
  3. no OPEN decision already exists for this company       (duplicate prevention)
  4. last completed research for this company older than cooldown
  5. escalation_round < V3_ESCALATION_MAX_ROUNDS
  6. cumulative cost for this decision < budget cap
```

Every clause is checkable, loggable and testable without a model. The model influences
*which* company is considered; it never decides *what the platform does* — the same
boundary V3.15 drew with `matching_sector`.

### 4.3 Loop prevention

| Risk | Control | Built on |
|---|---|---|
| Infinite escalation | `escalation_round` + `V3_ESCALATION_MAX_ROUNDS` (default **2**) | new column |
| No-progress churn | **evidence-improvement threshold**: a rerun requires the prior round to have increased indexed chunks or closed ≥1 gap | V3.16 `indexed_at`; `research_gaps` |
| Unclosable gaps | a `closable=False` gap can never justify escalation | `planner.py:669` — exists |
| Duplicate work | `idempotency_key` UNIQUE + partial unique index "one open decision per company" | migration 019 + new |
| Cost explosion | per-decision cumulative cost cap **derived** from `research_run_consumption`, attributed by `research_job_id` — see §5.4 | migration 020 + V3.17.9 |
| Runaway fan-out | max decisions created per discovery run | new config |

**The improvement threshold is the load-bearing one**, and V3.16 is what makes it
measurable: indexed chunk count is now a real, moving number (MRNA went 0 → 383). Without
that, "did this round help?" would be unanswerable and the loop would be unsafe.

## 5. Database changes

### 5.1 New table — `research_decisions`

```
id                    UUID PK
company_id            UUID FK → companies.id            ON DELETE SET NULL (lineage)
discovery_run_id      UUID FK → discovery_runs.id       ON DELETE SET NULL
discovery_candidate_id UUID FK → discovery_candidates.id ON DELETE SET NULL
source                VARCHAR(40)  NOT NULL   -- 'discovery_council' | 'gap_carry_forward'
decision              VARCHAR(40)  NOT NULL   -- research_next | monitor | reject | insufficient_data
status                VARCHAR(40)  NOT NULL   -- the state machine, §3
reason                TEXT         NOT NULL   -- which predicate fired, in words
priority              INTEGER      NOT NULL DEFAULT 100
escalation_round      INTEGER      NOT NULL DEFAULT 0
max_rounds            INTEGER      NOT NULL DEFAULT 2
evidence_before_json  JSONB        -- indexed chunks / open gaps / facts at round start
evidence_after_json   JSONB        -- the same, after
improvement_json      JSONB        -- the computed delta and the verdict
cost_usd_total        NUMERIC(12,4) NULL     -- NULL = unpriced, NEVER 0 (rule 6)
last_job_id           UUID FK → research_jobs.id ON DELETE SET NULL
terminal_reason       VARCHAR(80)  NULL      -- exhausted_no_improvement | budget | rounds | …
created_at / updated_at  TIMESTAMPTZ
```

**Indexes**

* `ix_research_decisions_status_priority (status, priority, created_at)` — the claim query.
* `ix_research_decisions_company (company_id)`.
* **`ux_research_decisions_one_open` UNIQUE PARTIAL on `(company_id) WHERE status IN
  ('research_required','queued','running','evidence_updated','reanalysis')`** — "one open
  decision per company" is a database constraint, not a convention a writer is trusted to
  keep. This repo has the precedent: `ix_research_document_versions_one_current`.

### 5.2 Migration **040** — additive only

One new table, four FKs all `SET NULL` (lineage, never cascade — CLAUDE.md rule 15), no
change to any existing table, no backfill. Reversible; verify upgrade → downgrade →
upgrade on real PostgreSQL 16 before it goes near production.

**No change to `discovery_candidates`.** A `decision_id` column there would be a second
place the decision lives.


### 5.4 Cost attribution — V3.17.9

`cost_usd_total` is **derived, never accumulated**. `controller.complete_round` recomputes
the whole total from the rows on every closure, which is what makes a replayed round
closure — the terminal observer *and* the startup sweep can both fire for one job —
produce the same number rather than twice it.

**The lineage.** `research_run_consumption.research_job_id` → `research_jobs.id`. The jobs
belonging to a decision are found through the `idempotency_key` the decision itself minted
(`escalation:<decision>:round:<n>#<generation>`) plus its stored `last_job_id`. There is
deliberately **no** fallback to "jobs for this company" or "the latest job": two concurrent
jobs for one company — an operator's manual research and an escalation round — share a
`company_id` and nothing else, and company-based attribution bills each for both.

**One money table.** `research_run_consumption` carries the derived USD.
`research_tool_calls` is the audit trace; its units are folded into the run row by
`company_research_service._record_consumption`, so summing both would count the
investigator's tokens twice. Tool calls prove lineage; the run row carries the money.

**What NULL means.** `spend.basis` says which:

| `basis` | `cost_usd_total` | Meaning |
|---|---|---|
| `no_jobs` | `NULL` | the decision has ordered no job yet |
| `no_consumption_recorded` | `NULL` | jobs exist; `V3_RUN_CONSUMPTION_ENABLED` is off or no run reached recording |
| `unpriced_consumption` | `NULL` | measured, and no configured price covers it — **the production state today** |
| `attributed_from_priced_consumption` | a number | every attributable row is priced |

A sum over only the priced rows is reported as `priced_subtotal_usd` and is **never** the
total: a cap compared against a subtotal passes on spend it never saw.

## 6. API changes

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/v1/research-decisions` | list; filter `status`, `company_id` |
| `GET` | `/api/v1/research-decisions/{id}` | one decision with its rounds and evidence delta |
| `POST` | `/api/v1/research-decisions/{id}/cancel` | operator stop — sets terminal `abandoned` |
| `POST` | `/api/v1/discovery/runs/{id}/escalate` | **explicit** controller invocation for a reviewed run |

`POST …/escalate` is deliberately explicit rather than automatic-on-council-completion, for
the first release. An escalation that starts itself the moment a council finishes is how a
feature becomes an outage — the same argument migration 019's docstring makes about
backfills that start themselves.

Response schemas carry `evidence_before` / `evidence_after` / `improvement` so the reader
sees **what changed**, not merely that something ran.

## 7. Agent changes

**None. No new agent.**

The discovery chair already emits `internal_action`. The Director already re-plans from
carry-forward gaps. The specialists already exist. V3.17 is orchestration: a controller
that reads existing outputs and calls existing machinery.

The one prompt-adjacent question — whether the chair should also emit *which evidence is
missing* — is deliberately deferred. `blocking_gap_count` and `missing_fields_json` already
carry that, deterministically, and asking a model for it again would create a second answer
to a question the platform can already answer without one.

## 9. Failure modes

| Mode | Behaviour | Mechanism |
|---|---|---|
| Provider unavailable | job retries with backoff, then dead-letters; decision → `abandoned`, reason recorded | `attempt`/`max_attempts`/`available_at`/`dead_letter_reason` (019) |
| No evidence found | round completes, delta = 0, decision → `exhausted_no_improvement` — **not** retried | improvement threshold |
| Duplicate research | second decision refused by the partial unique index; second job refused by `idempotency_key` | DB constraints |
| Infinite loop | `escalation_round >= max_rounds` → `abandoned` | counter + cap |
| Cost explosion | cumulative `cost_usd_total` over cap → `abandoned`; **`NULL` cost is treated as unknown and blocks escalation, never as zero** | rule 6 |
| Spend that cannot be attributed | until V3.17.9 every `research_job_id` was NULL, so `cost_usd_total` had no producer and `cost_unknown` meant *unlinked* as well as *unpriced*. The two are now separable — §5.4 | V3.17.9 |
| Worker dies mid-run | lease expires; another worker claims it; `attempt` increments | lease (019) |
| Council never ran | no decision created; recorded as such | predicate 1 |
| Unclosable gap | can never justify escalation | `closable=False` |
| **Findings still not produced** | see §11 — the honest one | — |

## 11. Testing requirements

Every slice needs all three. The repository's own history is the argument: a fixture once
written *from the parser* agreed with the parser's mistake and 6,000 tests passed green.

1. **Producer** — does the component write the right row? (controller creates a decision
   with the right reason)
2. **Consumer** — *does the next component actually read it?* This is the one that would
   have caught today's defect. A test asserting `candidates_to_research_next` is populated
   passes today, while nothing consumes it. The consumer test must assert that a decision
   **causes a `research_jobs` row to exist**.
3. **End-to-end** — does the user-visible workflow improve? Not "a decision was created"
   but "indexed chunk count rose and the report cites new evidence".

**Explicitly forbidden:** a test that asserts the decision JSON has a key. That is the
shape of test that let this gap survive.

### Acceptance scenario — "Find European luxury companies"

| Step | Expectation | Measurable by |
|---|---|---|
| Discovery finds candidates | `DiscoveryCandidate` rows | count |
| Council evaluates | `internal_action` per candidate | buckets |
| **Decisions persisted** | `research_decisions` rows — **database state, not JSON** | query |
| **Jobs auto-created** | `research_jobs` rows with `idempotency_key` = decision id | query |
| Evidence acquired | V3.16 bridge acquires filings | indexed chunk delta |
| Corpus grows | before < after | count |
| Council reruns | second run with carry-forward questions | ledger |
| Report improves | new evidence cited | report diff |
| Evidence still insufficient | `exhausted_no_improvement` + reason, **no further round** | terminal state |

⚠️ **European issuers have no SEC CIK**, so the V3.16 filing bridge — the main evidence
acquisition path — **cannot fire for them**. For a European luxury name the loop will
correctly reach `exhausted_no_improvement` on round 1. That is honest behaviour, not
success. Demonstrating *evidence actually growing* needs a US issuer (MRNA) or the European
document path, which is out of scope here. **The acceptance scenario as written will prove
the loop terminates safely; it will not prove the corpus grows.** Both should be run.

| **findings recorded** | **0** | **18** |
| blocking questions | `cash_runway`, `pipeline_state` | **`cash_runway` only** |

See [`v3.16.1b-production-acceptance-report.md`](v3.16.1b-production-acceptance-report.md).

**So investigator→Finding is closed, and V3.17 is no longer downstream of an unproven
step.** Two things follow, and only one of them is good news:

1. Escalation can now, in principle, demonstrate new findings — the headline product
   claim is reachable.
2. **The improvement threshold must still be defined on indexed chunks and closed gaps,
   never on finding count.** The reasoning has changed but the conclusion has not: finding
   count is now non-zero but it is *model output*, and a threshold that rewards a model
   for emitting more findings is a threshold that pays for prose. Chunks indexed and gaps
   closed are measurements of what the platform retrieved and resolved. Those are the
   honest numbers, and V3.16 is what made the first of them move (MRNA 0 → 383).

That remains a design constraint, not a caveat.

**The one genuinely open risk.** `cash_runway` is still blocking the Council and still
retrieves *no citable evidence at all*. An escalation loop that reruns research on MRNA
will rerun into that same emptiness. So V3.17's termination path — `exhausted_no_improvement`
— is not a rare edge case to be designed around; on the first real company it is **the
expected outcome of round 1**, and it must be correct before anything else is.

## 12A. V3.17.8 — the round-0 evidence baseline (added 2026-09-20)

### The defect the design did not state

§6 describes `evidence_before_json` as *"indexed chunks / open gaps / facts at round
start"* and §5 describes the improvement threshold as a delta. Both are correct as
intent. Neither says **who writes the baseline, or when** — and the implementation wrote
it at exactly one place, `controller.complete_round`, for the *next* round.
`store.create_decision` built the row without it.

So every **round 0** compared against `EvidenceSnapshot.from_dict(None)`: all zeros. The
tell reached production on all four live decisions:

```
closable_gaps_closed: -14, -16, -28, -32        improved: true
```

Minus fourteen gaps were not closed. That number is `0 − 14`: the company's *pre-existing*
open gaps, subtracted from a baseline that did not exist. Likewise `facts_added: 35`
counted facts the platform had held for weeks. Every round 0 therefore reported
`improved: true` whatever it acquired, and the improvement threshold — the mechanism §5
introduces specifically so that a round that acquires nothing cannot buy another — was
inverted.

It cost nothing only because `cost_unknown` stops every decision at round 0 (§11, open
question 4). **It becomes live spend the moment a price book is configured.**

### The contract, stated where it was missing

> **A round is measured against a snapshot taken before anything that could execute it
> exists — or it is not measured at all.**

Four rules implement it:

| Rule | Where |
|---|---|
| `create_decision` takes `evidence_before` as a **required** argument and refuses a company decision without it | `escalation/store.py` |
| `escalate_discovery_run` snapshots **before** it creates the decision, which is before any job exists | `escalation/controller.py` |
| `_enqueue` refuses to queue any round of any decision that carries no baseline — the single choke point every producer passes through | `escalation/controller.py` |
| `complete_round` reads the baseline with `EvidenceSnapshot.persisted`, which answers `None` for an absent measurement instead of zeros | `escalation/controller.py` |

`complete_round` still writes this round's `after` snapshot as the next round's `before`
— unchanged — but now **flushes it before** enqueueing the next round's job, so round
*n+1* obeys the same rule as round 0.

### A missing baseline fails closed, and does not fabricate one

A decision created before this slice has no baseline and its round may already have run.
Snapshotting "now" would produce an *after* measurement labelled "before", so the platform
refuses:

* `decide_next_state` gains a new terminal reason, **`evidence_baseline_missing`**, asked
  **after** "did research happen?" and **before** "did it acquire anything?". It claims
  nothing about the world and nothing about the platform's ability to look — only that the
  delta cannot be computed, so no further paid round may be authorised.
* `improvement_json` then carries `measurable: false` and **no numeric dimensions at
  all**. Zeros would be indistinguishable from a round that genuinely acquired nothing.
* `recover_stranded_decisions` may snapshot a baseline **only** where it can prove the
  round never began: status `research_required`, round 0, and **no `research_jobs` row
  under the decision's round-0 idempotency key**. `JobStore` commits in its own session,
  so a claimable job can outlive a rolled-back decision; without that third check the
  repair path would reintroduce the defect it exists to survive.
* Everywhere else the decision is closed `abandoned` / `evidence_baseline_missing`, which
  releases `ux_research_decisions_one_open` so the company can receive a correct decision
  rather than trading one permanent lockout for another.

`recover_stranded_decisions` now also takes its rows `FOR UPDATE … SKIP LOCKED`, as
`reconcile_terminal_decisions` already did: it writes a baseline, and two sweeps meeting
the same row must not each take their own snapshot of it.

### Gaps opened and gaps closed are two numbers

A single signed `closable_gaps_closed` cannot be rendered honestly. The delta now carries
`closable_gaps_closed` **and** `closable_gaps_opened`, both non-negative. Discovering a
gap remains a legitimate result of reading something new and still does not count against
improvement — it is now *reported* as what it is.

**The four historical production decisions are left exactly as they are.** Their bad
deltas are the evidence of the defect, and rewriting them would destroy the record.
