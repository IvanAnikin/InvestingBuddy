## 2. OBSERVED — durable worker topology, decided from code and Azure

The brief required this to be determined, not guessed.

| Evidence | Value |
|---|---|
| App Service startup command | `gunicorn app.main:app --workers 1 --worker-class uvicorn.workers.UvicornWorker --bind 0.0.0.0:8000 --timeout 300` |
| App Service plan | `ib-stg-plan`, **B1**, `numberOfWorkers: 1` |
| `DEPLOYED_GUNICORN_WORKERS` (code) | `1` — matches the live command |
| `v3_job_worker_in_process` default | `True` |
| Worker start | `app/main.py::_start_durable_worker`, only when `v3_durable_jobs_enabled` **and** `v3_job_worker_in_process` |
| Worker stop | bounded grace, then the lease lapses and the next process reclaims — a shutdown never marks a job failed |
| Env injection in the startup command | none |

### Decision: **Option A — the in-process worker.**

Reasons, in order:

1. **It is the topology the code was written for.** `config.py` states it plainly: *"True
   is the honest default for the current single-App-Service deployment."*
2. **One gunicorn worker on one B1 instance** means exactly one in-process worker, so
   there is no multi-worker lease contention to reason about on the first release.
3. It supplies everything the brief asked for — durable DB-backed queue, lease,
   heartbeat, retry, restart recovery — **with no additional infrastructure**.
4. Option B (standalone `python -m app.services.jobs.worker`) requires a second App
   Service. That is new infrastructure, it fails the "no additional infrastructure
   dependency" requirement, and the code records it as OPEN DECISION #2 — unapproved
   cost.
5. `research_job` reads `DEPLOYED_GUNICORN_WORKERS` to decide whether a job that started
   before this process booted can be called abandoned. With exactly one worker that is
   knowable immediately; the shortcut disables itself automatically if the count is ever
   raised.

**Honest limitation, recorded rather than glossed:** the in-process worker leaves
CPU-heavy extraction in the API process. It makes execution survive a recycle, which is
the point, but it does not move load off the API. Setting
`V3_JOB_WORKER_IN_PROCESS=false` and running the standalone worker elsewhere moves it
with no code change.

## 6. OBSERVED — evidence delta and round control

`escalation/evidence.py` and `escalation/rounds.py`, 43 tests.

**Improvement is measured on acquisition, never on model output.** The decisive
dimensions are indexed chunks, searchable documents, closable gaps closed, and active
scoped facts. Verified findings are carried as **secondary telemetry only** — a threshold
that rewards a model for emitting more findings pays for prose, and an investigator
defect would make genuinely acquired evidence look like nothing and terminate a working
loop.

**Counting is scoped three ways**, each of which has burned this repository before: to the
company (via `ResearchDocument.company_id` *and* the chunk's denormalised `company_id`),
to current/active rows (`is_current` version **and** `is_active` derivation), and to
`research_gaps` rather than `DiscoveryCandidate.missing_fields_json`.

**Two defects were found by writing the tests, not by reading:**

1. The first chunk query joined only to the version and checked `is_current`, so chunks
   from a **superseded derivation of a current version** were still counted — a
   re-extraction of a document already held would have read as fresh acquisition and
   authorised a paid round.
2. Mutation testing showed the denormalised `chunk.company_id` filter was unreachable by
   any test. It is redundant while the data agrees and load-bearing when it does not, so
   a denormalisation-drift test now makes it matter.

**`exhausted_no_improvement` and `research_did_not_complete` are different claims**, and
`decide_next_state` asks *"did research actually happen?"* before *"did it find
anything?"*. A job that did not complete can never reach `exhausted`. This is the one
distinction the brief called mandatory.

## 7. OBSERVED — the crash that could have caused a permanent outage

A decision row and a job row are written in **different transactions** — `JobStore` owns
its own session by design. A process dying between them leaves one without the other, and
an open decision with no executable job is not a stalled item: `ux_research_decisions_one_open`
then forbids **any** further decision for that company, permanently.

Fixed before merge, two ways:

* **Order.** `complete_round` enqueues the next round's job *before* moving the decision
  to `reanalysis`. A crash between leaves `evidence_updated` + a live job — recoverable.
* **Key.** `round_idempotency_key(decision_id, round)` is deterministic and recomputable
  from the row alone, so re-enqueueing after a crash joins rather than duplicates. That is
  what makes `recover_stranded_decisions` safe to run repeatedly and concurrently.

## 14. ⛔ THE DECISIVE DEFECT — the autonomous loop does not close

### 14.1 OBSERVED

At **16:28:00Z**, both European jobs had reached a terminal state:

```
PNDORA/CO  dec=queued round=0 job=completed_with_warnings term=None after=None
           updated_at=2026-09-19T16:06:34.870548Z
CFR/SW     dec=queued round=0 job=completed_with_warnings term=None after=None
           updated_at=2026-09-19T16:06:34.412222Z
```

`updated_at` is still each decision's **creation** timestamp. Nothing has touched either
decision since it was created, twenty-two minutes and two completed research runs earlier.

### 14.2 Root cause

An exhaustive grep over `apps/api`:

| Symbol | Where it appears |
|---|---|
| `complete_round` | `controller.py` — its own `__all__`, its own `def`, one docstring. **Plus `tests/test_v3_17_3_escalation_controller.py`.** |
| `recover_stranded_decisions` | the same three places, plus the same test file |

**Neither function has a production caller.** Both are fully implemented and correct, and
both are reachable only from tests that call them directly — which is why three merges of
CI stayed green over an open loop.

`worker.py` is deliberately domain-free (*"nothing here knows what research is"*) and
exposed **no terminal-outcome extension point**, so there was no seam the escalation
domain could have hooked. The wiring is absent rather than wrong.

### 14.3 Consequences

1. `evidence_before_json`, `evidence_after_json`, `improvement_json` are **never written**.
2. `terminal_reason` is **never set**; no decision can reach `exhausted_no_improvement`.
3. **No next round is ever created**; `max_rounds` is never exercised.
4. The decision stays in an OPEN status for ever, and `ux_research_decisions_one_open`
   then forbids **any** further decision for that company. **CFR/SW and PNDORA/CO are now
   permanently locked out of future escalation by rounds that finished successfully.**
   This is the stranding hazard the design documented — now live.

This is the same defect class the campaign has been removing: V3.16, metadata correct and
connected to nothing; V3.17, a council bucket nothing ever read; V3.17.6, the
round-completion function nothing ever calls.

### 14.4 The fix — V3.17.7, implemented on `feature/v3-17-7-close-the-escalation-loop`

* `worker.py` gains a domain-free seam: `register_terminal_observer` /
  `notify_terminal`, called at **both** terminal writes — after `store.complete`, and
  after `store.fail` **only when `will_retry` is false**, so a round about to be retried
  is never announced as ended.
* `escalation/job_hook.py` registers `advance_research_decision`, which finds the OPEN
  decision whose `last_job_id` is that job (`SELECT … FOR UPDATE`) and calls
  `complete_round` with the real `job_completed` / `job_dead_lettered`.
* `jobs/handlers.py` imports it, for the same reason it imports the handlers.
* An observer that raises is logged by type and skipped: the terminal write has already
  happened and must not be undone.

**Mutation-verified, both directions:**

| Mutation | Caught by |
|---|---|
| remove the success-path `notify_terminal` call | `test_a_completed_job_notifies_observers` (drives the **real** `run_once`) |
| remove the registration import from `handlers.py` | `test_importing_handlers_registers_the_escalation_observer` |

The wiring test was itself **wrong on first writing** — it reloaded `job_hook` directly, so
it passed with the import deleted. It now clears the registry, drops both modules from
`sys.modules` *and* deletes the stale attribute from the parent package before importing
`handlers` alone. A test that passes whether or not the thing is wired is the exact defect
class this slice exists to close, so it is recorded rather than quietly corrected.

### 14.5 The hole the observer alone still left — and the durable repair

Pre-merge review caught that §14.4 was **not sufficient**. `notify_terminal` deliberately
swallows whatever the observer raises, the observer runs in its own session after its own
commit, and the job never runs again to notify twice. So:

```
terminal job commits -> observer hits a transient DB error -> exception swallowed
-> decision stays OPEN for ever -> the company is locked out again
```

The same outage, reachable by one dropped socket. The notification is therefore the FAST
path only, and the database — not a callback — is the authority on what still needs
finishing:

* **`controller.reconcile_terminal_decisions`** — open decisions whose `last_job_id`
  names a job in `job_contract.TERMINAL`. It reuses `complete_round` verbatim, and reads
  `HAS_RESULT` / `STATUS_DEAD_LETTER` from the contract instead of restating status
  strings that could drift from the state machine.
* **Rows taken `FOR UPDATE ... SKIP LOCKED`**, with the OPEN re-check performed *after*
  the lock is held.
* **`worker.register_sweep_hook` / `run_sweeps`** — once at startup **before the first
  claim** (a new process may be replacing one that died between a terminal write and its
  notification), then on a 300s cadence. Not the 2s poll: a repair path on a work-queue
  cadence is a hot loop.
* **`recover_stranded_decisions` was also given its first production caller** in the same
  sweep. It repairs the *other* stranding — `last_job_id IS NULL`, where the process died
  after the decision was written and before its job was. Recovery runs first.
* Bounded to 50 rows per pass.

Because it asks the database rather than trusting a callback, it heals decisions stranded
**before this code existed** — which is how CFR/SW and PNDORA/CO are meant to be fixed.
They are deliberately **not** being cancelled; their automatic healing is the acceptance
proof for this failure mode.

**Mutation-verified four ways. Two of these initially did NOT fail**, and the tests were
rewritten until they did:

| Mutation | Caught by | Why the first attempt was invalid |
|---|---|---|
| delete the success-path notification | `test_a_completed_job_notifies_observers` | — (drives the real `run_once`) |
| delete the startup sweep | `test_the_worker_sweeps_BEFORE_it_claims_any_job` | "a sweep ran" passed either way — the in-loop call fires on iteration 1 too. The event **order** is the assertion. |
| delete the in-loop sweep | `test_the_sweep_repeats_on_its_cadence` | "a sweep ran" passed either way — the startup call satisfies it. **Repetition** is the assertion. |
| delete the recover call | `test_the_sweep_also_repairs_decisions_with_no_job` | — |

`SKIP LOCKED` is a no-op on SQLite, so every SQLite test proves the *filtering* and
nothing about the *concurrency*. Two tests in the PostgreSQL lifecycle file prove it where
it is implemented, and **both passed in CI against PostgreSQL 16**: concurrent sweeps
close a decision exactly once, and repeated sweeps never rewrite a closed one.

Those two tests failed on their first CI run with a `ForeignKeyViolation` — they invented
a `discovery_run_id`, which SQLite accepts with foreign keys off and PostgreSQL rejects.
Recorded because it is the trap this repository has hit before, and because the tests
caught a defect in themselves on their first honest run.
