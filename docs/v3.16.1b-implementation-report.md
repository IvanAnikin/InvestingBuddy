# V3.16.1b — Investigator Response Shaping: Implementation Report

**Slice:** V3.16.1b — bound the investigator's output so its write-ups survive
**Branch:** `feature/v3-16-1b-investigator-response-shaping`
**Baseline:** `b8e5ab3` (Merge V3.16.1a — investigator response diagnostics)
**Migration:** none
**Status:** implemented, locally accepted; **production acceptance not yet run**

---

## 1. What this slice had to fix

V3.16.1a made the failure legible and the first production run it observed
([`v3.16.1a-production-acceptance-report.md`](v3.16.1a-production-acceptance-report.md))
said this:

```json
{"responses_total": 8, "responses_truncated": 8, "responses_unparseable": 8,
 "finish_reasons": {"length": 8}}
```

Eight write-ups, eight replies cut off at the output ceiling, **zero findings**, and
eight `tool_unavailable` gaps manufactured by the truncation itself.

The brief forbade blindly multiplying `max_tokens` and required four inspections first.
Those are in [`v3.16.1b-root-cause-measurement.md`](v3.16.1b-root-cause-measurement.md),
measured against the live `deepseek-v4-flash` endpoint with the investigator's real
prompt. The headline: the model was **over-producing**, not under-budgeted.
`_write_up` keeps `[:MAX_FINDINGS_PER_QUESTION]` findings and the same number of gaps,
and **the prompt never said so** — so the model wrote a fifth gap the code was always
going to discard unread, and the room that fifth gap took is what pushed the four items
the code *does* keep past the ceiling.

**The campaign's signature defect in a new place: a limit the consumer enforces that the
producer was never told.** Seventh confirmed instance.

## 2. What changed

| # | Change | Evidence it rests on |
|---|---|---|
| 1 | The prompt now states the item caps, **derived from `MAX_FINDINGS_PER_QUESTION`**, plus per-field character bounds and a token target | §2.4: median reply 1,435 → ~845 tokens |
| 2 | `json_mode` forwarded on the investigator's write-up call | §3: removes length variance; measured *not* to fix truncation |
| 3 | `max_tokens` 1,200 → **1,800** | §2.4 distribution: min 668 / median 845 / max 1,763. Read off, not multiplied |
| 4 | One tighter **retry** when a reply truncates | §4: 12/12 complete at median 263 tokens |
| 5 | `finish_reasons` recorded **per model call**, not per question | §7.1 — the retry had blinded V3.16.1a's authoritative field |
| 6 | A provider error on the retry no longer erases the diagnosis | §7.2 — a retry must never leave the run worse off than no retry |
| 7 | `json_mode` declared on the `DeepSeekTransport` Protocol and its shared fake | §7.3 — the seam was narrower than its own implementation |

Changes 5–7 were found by reading the patch against the measurement document, not by the
measurement itself. Two were introduced by the fix; one it exposed.

**The fix costs fewer tokens, not more.** Production burns 1,200 completion tokens per
call and returns zero findings, because all 1,200 are discarded. The shaped configuration
uses a median of 845 and returns four findings. Raising the *ceiling* does not raise
spend — completion tokens are billed on what the model writes.

### What was NOT touched

The citation guard, the period/scope conflict check, the validator, playbook blocking
semantics, and the rule that a fabricated citation discards its finding. One probe run
saw the model invent the citation id `ev:c:0000` under length pressure; that is an
argument for keeping the guard, not relaxing it.

## 3. Test evidence

**New:** `apps/api/tests/test_v3_investigator_response_shaping.py` — 30 tests.

The cap is never spelled out as a literal in the assertions. It is **read out of the
prompt and checked against what the code keeps**, because a test asserting
`"At most 4 findings" in prompt` passes on a prompt that has drifted from the constant —
which is the exact defect being fixed.

### Mutation check — every test was made to fail on the broken code

| Mutation applied to the fixed code | Tests that failed |
|---|---|
| Cap typed into the prompt instead of derived from the constant | 1 — `test_the_cap_is_derived_from_the_constant_not_typed_into_the_prompt` |
| `finish_reasons` noted per question again (pre-7.1) | 2, incl. `assert {'stop': 1} == {'length': 1, 'stop': 1}` |
| Retry's provider error allowed to propagate (pre-7.2) | 1 — `test_a_provider_error_on_the_retry_leaves_the_diagnosis_intact` |
| Retry removed entirely (the V3.16.1a state) | 9 |
| `max_tokens` back to 1,200 | 2 |
| `json_mode` forwarded by nobody (the V3.16.1a state) | 2 |

A third model call is made to escape `_write_up`'s handler via a `BaseException`
subclass, so an unbounded retry loop fails the test rather than being logged as a tidy
gap.

## 4. Residual risk, stated plainly

The right tail is long and 15–27 samples do not bound it. A reply can still exceed 1,800
tokens. When it does, the retry converts it into a short complete answer; if the retry
also truncates, `responses_truncated`, `responses_retried_after_truncation` and the
per-question gap text record it in readable English.

**The failure mode after V3.16.1b is visible and degraded, never silent and total.**
That is the whole difference between this slice and the state it replaces.

Not yet known, and only a production run can say: whether shaping alone is enough to
unblock `cash_runway` and `pipeline_state`, and therefore whether
`council_may_convene` turns true. V3.16 established that `cash_runway` is *legitimately*
unsupported (facts inactive, `scope_type=None`), so it may remain a gap for reasons this
slice does not touch.
