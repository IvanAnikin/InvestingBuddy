**Date:** 2026-09-20
**Branch:** `feature/v3-17-9-durable-job-cost-attribution`
**Schema change:** none. Migration head stays **040**.
**Tracked verdicts:** `COST ATTRIBUTION` — see §9; `RUN CONSUMPTION TELEMETRY` — see §12.

---

## 1. The defect

`run_company_research_job` holds the real durable id in `ctx.job.id` and passed
`content_run_id` — an **AgentRun** id — into the only id parameter company research had.

Five tables carry a `research_job_id` foreign key to `research_jobs.id`. Every one of
them was NULL in production, for two causes stacked on top of each other:

1. **The id never left the handler.** The id that *was* passed named no `research_jobs`
   row, so the V3.13.1 guard dropped it. That guard is correct — writing it violates the
   constraint, PostgreSQL aborts the transaction, and the V2 report goes with it (measured
   at head 038: 0 tool calls, 0 findings, **no report**). Correct behaviour, on a wrong
   input, which is why the failure was silent.
2. **Three of the five writers never took the argument.** `ledger.open_run` has accepted
   `research_job_id` since V3.5 and no caller passed it. `persist_lead` has accepted it
   since V3.13 and no caller passed it. `calculation_records.research_job_id` has existed
   since migration 030 and nothing wrote it.

So even a correct id would have reached two tables out of five.

**The consequence.** `ResearchDecision.cost_usd_total` had **no producer at all**. Every
decision reported unknown spend, and the round transition stopped at `cost_unknown`. That
reads as "no price book is configured" — which is true — and concealed that the spend was
also **unattributable**. Those are different problems, and configuring prices would have
fixed only one of them.

## 2. The contract

> **A durable job id is threaded explicitly or it is NULL. It is never derived from an
> AgentRun id, a company id, a timestamp, or the most recent job.**

| Rule | File |
|---|---|
| The handler passes `ctx.job.id` on its **own** parameter, beside the content id | `app/services/jobs/company_research_job.py` |
| `process_company_research_by_id(..., durable_job_id=...)` — two ids, two parameters | `app/services/company_research_service.py` |
| Validated once, **fail-closed**, before it can reach any foreign key | `app/services/jobs/lineage.py` |
| The V3 pipeline re-validates on its own entry and records a degraded line when it drops one | `app/services/pipeline/v3_pipeline.py` |
| No durable job → NULL, honestly. The V2 background path passes nothing | `app/services/company_research_service.py` |

Overloading one parameter with "whichever id the caller happened to have" is what produced
the defect; a single parameter of that shape cannot be checked.

### The five columns, and who writes them now

| Table | Writer | Was |
|---|---|---|
| `research_runs` | `v3_pipeline` → `ledger.open_run` | argument existed since V3.5, never passed |
| `research_tool_calls` | `agent_tools/session.py` `_record` | wired since V3.13, id was wrong |
| `research_leads` | `agent_tools/external.py` → `persist_lead` | argument existed since V3.13, never passed |
| `calculation_records` | `agent_tools/calculations.py` `_persist` | column existed since 030, nothing wrote it |
| `research_run_consumption` | `company_research_service._record_consumption` | **the money record** |

### The third path, checked and deliberately not changed

`market_discovery_service.run_candidate_analysis` calls `execute_company_research`
directly. It never enters `process_company_research_by_id`, so it runs **no V3 pipeline
and writes no consumption row** — there is nothing for it to attribute, and adding a
durable id to it would be inventing a job that does not exist. Stated here so a later
reader can see it was examined rather than missed.

`ToolContext` gained `research_job_id` so a lead or a calculation a tool persists is
attributable to the same job as the call that produced it. It arrives **already
validated**: a tool must never be able to write a broken foreign key, because a tool's own
`except Exception` cannot un-abort the transaction the V2 report is waiting to commit in.

## 3. The money record is one table

Two tables persist consumption. Exactly one is summed.

`research_run_consumption` — one row per research run, with `estimated_cost_usd` derived
from the configured price book. **This is the money record.**

`research_tool_calls` — one row per attempted call, with `consumption_json` units. The
audit and debugging trace. Its `estimated_cost_usd` column has never been written by
anything, and its units are now *folded into* the run row, so summing both would count the
investigator's tokens twice.

> **Tool calls prove lineage; the run row carries the money.**

### The V3 half of the spend reaches the money record

`result["consumption"]` was the **V2** half only — the council's tokens plus wall time. The
V3 pipeline runs after `execute_company_research` returns, so the investigator and tool
spend, which on a real run is the larger half, reached this table not at all. It is now
added to the same row rather than written as a second one, because
`research_run_consumption` claims to be one row per run and a second row would have to be
told apart from a retry by every reader that ever sums the table.

`elapsed_seconds` is deliberately **not** taken from the V3 outcome: the V2 record already
spans the whole run, V3 included, and adding it again would report a run as having lasted
longer than it did.

## 4. Attribution is by lineage, never by company

`escalation/cost.py` finds a decision's jobs through **two explicit links and no third**:

* the `idempotency_key` the decision itself minted —
  `escalation:<decision>:round:<n>#<generation>` — which reaches **every** round, not just
  the one `last_job_id` currently points at;
* `decision.last_job_id`, the decision's own stored FK, which is the only link a decision
  written before this slice has.

There is deliberately no fallback to "jobs for this company" or "the latest job". Two
concurrent jobs for one company — an operator's manual research and an escalation round —
share a `company_id` and nothing else, and attributing by company bills each of them for
both. That case is tested.

**Derived, never accumulated.** `complete_round` recomputes the whole total from the rows
on every closure. The terminal observer *and* the startup sweep can both close one round —
that is a normal outcome, not a fault — so recomputation is what makes a replayed closure
yield the same number instead of twice it. A retry is different and is counted: two
attempts called the providers twice and both budgets were really spent.

## 5. What a NULL cost means, and which NULL it is

A single null column cannot distinguish a defect from an honest gap. `spend.basis` names
which:

| `basis` | `cost_usd_total` | Meaning | Fix |
|---|---|---|---|
| `no_jobs` | `NULL` | the decision has ordered no job yet | none needed |
| `no_consumption_recorded` | `NULL` | jobs and tool calls exist; no run-consumption row does | set `V3_RUN_CONSUMPTION_ENABLED` |
| `unpriced_consumption` | `NULL` | measured, and no configured price covers it | configure a price book |
| `attributed_from_priced_consumption` | a number | every attributable row is priced | — |

A sum over only the priced rows is reported as `priced_subtotal_usd` and is **never** the
total. A cost cap compared against a subtotal passes on spend it never saw.

`tool_call_model_tokens` is summed from `research_tool_calls.consumption_json`, which is
written whatever `V3_RUN_CONSUMPTION_ENABLED` says. With the recorder off it is the only
place consumption is visible, and it is what makes "lineage known, consumption measured,
price unknown" a checkable statement rather than a claim.

## 6. Where a reader sees it

### `GET /api/v1/company-research/jobs/{job_id}/lineage` — new

Row counts for every V3 table that carries a `research_job_id` foreign key to this job.
It exists because this platform's PostgreSQL is not reachable from outside its virtual
network — two acceptance sessions had a ledger read denied — so *"was this job's work
attributed to it?"* has to be answerable over HTTP or it cannot be answered at all.

A row is counted only when its `research_job_id` **equals** this id. Never by company,
never by AgentRun, never by time; a zero means nothing was attributed. `agent_run_id` is
returned beside it and is always a different id — a response where the two agree is one
where a substitution happened.

`404` for an id that is no durable job, because *"this job exists and nothing was
attributed to it"* is the defect and *"no such durable job"* is a V2 job id. Collapsing
them would hide the first.

`v3_pipeline_completed` now carries `research_job_id` too, so the same fact is checkable
from the log stream without any endpoint at all.

### `GET /api/v1/research-decisions/{id}`

Recomputes `spend` live — a decision still `queued`
or `running` has no recorded spend yet and is exactly the one an operator is looking at.
The **list** read returns what the round recorded instead: three extra queries per row
would make a 200-row page 600 queries to restate numbers already written.

The queue UI renders `costLabel` unchanged — an unknown cost still reads exactly
`unknown`, never `$0.0000` — with the reason on a second line: *no research job yet*,
*consumption not recorded*, *measured, not priced*.

### No migration, and why that was a choice

A `research_jobs.research_decision_id` column was designed, built and **reverted**.
`research_decisions.last_job_id` already points at `research_jobs`, so the reverse FK
creates a two-table cycle; SQLAlchemy then defers `research_decisions`' foreign keys to
separate `ALTER TABLE` statements, which SQLite cannot execute — breaking every test that
builds the schema with `Base.metadata.create_all`.

The `idempotency_key` is the better link anyway. `controller._enqueue` mints it from the
decision id and the controller's own docstring already calls it "a fact rather than a
convention", it reaches every round rather than only the current one, and — decisively —
it works for the jobs **production has already created**. A new column would have been
NULL for all of them.

**Migration head stays 040. Nothing to run at deploy time.**
