# V3.17.1 — `research_decisions` + migration 040

**Slice:** V3.17.1, the decision record (schema only — nothing writes to it yet)
**Branch:** `feature/v3-17-1-research-decisions`
**Baseline:** `9871044` (V3.16.1b accepted), Alembic **039**
**Migration:** **040**, additive
**Status:** implemented, locally accepted; not merged

---

## 1. What this closes

The discovery council has been emitting `research_next` per candidate for several phases,
into `discovery_runs.config_json["discovery_council"]["review"]["candidates_to_research_next"]`.

**Backend consumers of that field: zero.** It is rendered to a human and goes no further —
no column, no status, no index, nothing a query can reach
(`docs/v3.17-research-escalation-design.md` §1.1).

That is this repository's signature failure mode — *metadata existed but was never
connected to execution* — and it is the same shape as the defect V3.16.1b closed a layer
down, where a cap the consumer enforced was never told to the producer.

## 2. What was built

One table, `research_decisions`, plus the state-machine vocabulary it is written in. **No
controller, no predicates, no enqueue.** V3.17.1 deliberately lands a table nothing writes
to yet, so the migration is proved reversible before any behaviour depends on it.

**Why a decision is not a job.** `research_jobs` (migration 019) already has idempotency,
leases, heartbeats, attempts, backoff, cancellation and dead-lettering, and V3.17 reuses
it rather than building a second queue beside a working one. But a job is *one execution*
and a decision outlives its executions: it has to answer "why is this company being
researched, how many rounds has it had, what did each round improve, and when do we stop?"
Putting that in `payload_json` would make it unqueryable — the exact mistake above,
repeated.

### Design choices worth naming

- **Every FK is `SET NULL`, never `CASCADE`** (CLAUDE.md #15). Deleting a discovery run
  must not delete the record that research happened because of it.
- **`reason` is NOT NULL.** A decision nobody can audit is not a decision.
- **`cost_usd_total` is nullable with no default** (CLAUDE.md #6). Production reports
  `estimated_cost_usd` as NULL because no price book is configured; `NOT NULL DEFAULT 0`
  would turn "we do not know" into "it was free", and the budget predicate would then
  treat unlimited unpriced work as affordable.
- **`EXHAUSTED` ≠ `ABANDONED` ≠ `COMPLETED`.** "We stopped learning" and "we stopped
  spending" need different follow-ups; a reader who cannot tell them apart retries the
  wrong one.
- **The decision vocabulary is the council's existing `internal_action` set**, asserted
  equal to `_ACTION_TO_FIELD` by test. A parallel vocabulary would need a mapping layer,
  and mapping layers between two spellings of one concept are where meaning goes missing.

### `ux_research_decisions_one_open` is the point

"One open decision per company" is a **database** constraint, not a convention. A
read-then-write check in the controller loses under concurrency, and two councils
reviewing the same company concurrently is exactly the case that produces duplicate *paid*
research. Precedent: `ix_research_document_versions_one_current` (migration 022).

The partial predicate is **generated from `OPEN_STATUSES`** in both the model and the
migration, so the index cannot drift from the state machine the code uses.

## 3. Evidence

### 3.1 Migration gate — real PostgreSQL 16.15

Scratch Homebrew server, full chain from empty:

```
upgrade   → … → 039 → 040   (head)
downgrade → 039             research_decisions present in information_schema: 0
upgrade   → 040             research_decisions present in information_schema: 1
```

The index as PostgreSQL actually built it:

```sql
CREATE UNIQUE INDEX ux_research_decisions_one_open
  ON public.research_decisions USING btree (company_id)
  WHERE ((status)::text = ANY ((ARRAY['research_required'::character varying,
         'queued'::character varying, 'running'::character varying,
         'evidence_updated'::character varying, 'reanalysis'::character varying])::text[]));
```

### 3.2 The constraint proved by a rejected insert

| # | Action | Result |
|---|---|---|
| 1 | first open decision (`research_required`) | `INSERT 0 1` |
| 2 | second open decision, **a different open status** (`queued`) | **`ERROR: duplicate key value violates unique constraint "ux_research_decisions_one_open"`** |
| 3 | a terminal decision (`exhausted`) for the same company | `INSERT 0 1` — history is not contention |
| 4 | close the open one, then open a new one | `INSERT 0 1` — a finished escalation does not lock a company out |
| 5 | `DELETE FROM companies` | decisions **survive** with `company_id` NULL (3 rows, 0 non-null) |

Step 2 uses a *different* open status on purpose: it proves the predicate covers the whole
open set rather than one value.

### 3.3 Tests — 18, and the anti-drift one bites

`apps/api/tests/test_v3_17_1_research_decisions.py`. The design forbids the test that let
this gap survive — *"a test that asserts the decision JSON has a key"* — so nothing here
asserts a field exists. Coverage: state-machine coherence (open ∩ terminal = ∅, union =
all), FK ondelete, NOT NULL `reason`, nullable cost, vocabulary equality with the council's
own, and four real-PostgreSQL constraint tests.

Mutation check: hardcoding the migration predicate instead of deriving it from
`OPEN_STATUSES` — the exact drift the index must not suffer — fails
`test_the_migration_builds_the_predicate_from_the_constant` and nothing else.

**One honest caveat about the local PostgreSQL run.** The venv here is Python 3.14, where
SQLAlchemy's `psycopg` version probe raises `TypeError`, so the local scratch run used
`asyncpg` instead of CI's `psycopg`. Under `asyncpg`, five pre-existing tests in
`test_v3_pipeline_postgres_integrity.py` and `test_mrna_producer_postgres_acceptance.py`
fail on a `research_tasks → research_runs` foreign key. **They are not caused by this
slice:** the same five fail on a clean database migrated to **039**, with migration 040
never applied. They pass in CI under `psycopg`. CI is authoritative for the PostgreSQL
path.

## 4. What this slice does NOT do

No controller, no predicates, no enqueue, no API, no UI, no flag read. Nothing writes a
`research_decisions` row. That is V3.17.2 (pure predicates) and V3.17.3 (wiring), and
V3.17.3 carries a real activation decision — `V3_DURABLE_JOBS_ENABLED` — that is not
this slice's to take.
