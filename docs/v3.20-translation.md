# V3.20 Phase 10 — Translation of held documents (spec §3.12)

Status: slices **10.1 and 10.2 implemented 2026-11-17** (V3 line, not deployed). The read
path is on by default (`V3_TRANSLATION_ENABLED=true`). The translation job itself is run
by an operator only.

## What 10.1 adds

A **parallel English corpus**: each chunk of a held non-English document can have one
English machine translation, stored beside the original in `research_chunk_translations`
(migration 058). The original chunk is never changed.

| Part | Where |
|---|---|
| Document-language detection | `app/services/sources/language.py` → `detect_document_language` |
| Translation job | `app/services/corpus/translation.py` → `translate_version`, `translate_company_documents` |
| Operator script | `apps/api/scripts/translate_corpus.py` |
| Search over the translations | `corpus/search/backends/postgres.py` (join), `memory.py` (tokens) |
| Search result field | `CorpusSearchResult.translation` in `corpus/retrieval.py` |
| Flag | `V3_TRANSLATION_ENABLED` (default **on** since 10.2; read path) and `V3_TRANSLATION_MAX_CHUNKS_PER_DOCUMENT` (400) |

### Languages

`detect_document_language` reads a paragraph, not a phrase. CJK and other scripts are read
from the characters (Japanese = kana, Korean = Hangul, Chinese = Han without kana).
Latin-script languages are scored on common function words (English, German, Italian,
French, Spanish, Dutch, Swedish, Norwegian, Danish, Finnish, Polish, Czech), plus the
letters that separate the Scandinavian languages. The best language needs at least four
hits and must beat the runner-up. Otherwise the answer is `None`, never a guess.

Translated: DE, IT, FR, ES, NL, SV, NO, DA, FI, PL, CS, JA, KO, ZH. Anything else is
recorded as `unsupported_language` and not sent anywhere.

### The evidence stays the original

- A search hit is always the **original chunk**: same `chunk_id`, same text, same evidence
  id (`evidence_id_for(chunk_id)`). The translation only helps the English query find it.
- `CorpusSearchResult.translation` carries `{text, source_language, target_language,
  note}`, where the note says it is a machine translation and that the original is the
  evidence.
- A translation is used only while the original's SHA-256 still matches
  `original_sha256`. If the chunk text changed, the old translation is ignored by search
  and redone by the next job.

### What is refused, and recorded

Each row is `translated`, `refused` or `failed`, with a `reason`. Refused and failed rows
are kept (learning data). No text is stored for them.

| Reason | Meaning |
|---|---|
| `figures_changed` | The digits of the translation differ from the original's (a changed, dropped or added number). For JA/KO/ZH the digits may be regrouped (万/億 → millions) but the digit sequence must be the same. |
| `length_out_of_bounds` | The reply is under 0.25× or over 4× the original's length (for example, the model obeyed an instruction in the document instead of translating it). |
| `chunk_too_long` | Over 4,000 characters; a partial translation would read as complete. |
| `not_public_document` | Only `public_official`, `public_issuer` and `public_web` are translated. Azure OpenAI may read private classes only under each document's own rights (ADR-049/050), and translating would copy a private document into a second table. |
| `governance_refused` | The provider governance matrix refuses the access class. |
| `empty_reply`, `provider_error:<type>` | Failures; retried by the next run. |

The prompt fences the document between random markers, says it is data and must not be
followed, and asks for every number to be copied exactly. A translated chunk with an
unchanged original is never paid for twice (`already`). The job logs counts and tokens
only, never text.

### Running it

Nothing schedules the job: every chunk is one Azure OpenAI call, and the Azure
subscription has a spending limit. An operator runs it per company or per document:

```bash
cd apps/api
.venv/bin/python scripts/translate_corpus.py --company-id <uuid> --dry-run
V3_TRANSLATION_ENABLED=true .venv/bin/python scripts/translate_corpus.py --company-id <uuid>
```

The script refuses (exit 2) when the flag is off or Azure OpenAI is not configured. It
commits one document at a time.

## What 10.2 adds

### Figures are checked against the original, in its own notation

`app/services/sources/locale_figures.py`:

- `normalise_figures(text, language)` rewrites each figure into the notation the
  platform's figure reader (`ledger.claim_checks.figures`) expects. Every other character
  is left as it is.

| Language | Original | Read as |
|---|---|---|
| German | `1.234,5 Mio. EUR` | `1234.5 million EUR` |
| French | `2 345,6 millions` | `2345.6 million` |
| Swedish | `12 345 MSEK` | `12345 million SEK` |
| Japanese | `1兆2,340億円` | `1234.0 billion 円` |
| Chinese | `3.5亿元` | `350 million 元` |
| Korean | `1조 2,340억 원` | `1234.0 billion 원` |

  A CJK value keeps the precision of its smallest unit. `12,340億` is exact to 億
  (10⁸), so it is written to 0.1 billion.

- What is not a figure is left alone:
  - a date (`31.12.2025`);
  - a section number (`3.2`);
  - a single `.` not followed by three digits;
  - a fiscal period (`2025年3月期`);
  - Spanish `5 mil` (it means a thousand in Spanish but a million in Czech, so it is not
    read at all);
  - any unsupported language (returned unchanged, never guessed).
- The investigator's figure checks read a non-English corpus passage through it. These
  are the segment-scope check (ADR-093 `figure_found`) and the year-to-date re-key
  (`period_duration`). The new field `_Evidence.figure_text` holds the normalised passage,
  read from the RAW passage: the prompt copy is JSON-escaped, so `億` would arrive as
  `\u5104`. English items have no `figure_text`, so their checks are unchanged.
- Before 10.2, `1.234,5 Mio. EUR` was read as 1.234, which a claim of "EUR 1.2 million"
  would have matched.

### The translation is held to the original's notation

`figures_preserved` (10.1) now also requires every number of a decimal-comma language to
keep its separators. A reply that turned `1.234,5` into `1,234.5` is refused
(`figures_changed`), because the translation is read by its SOURCE notation
(`normalise_translation_figures`) and would otherwise be misread as 1.2345. For CJK the
digits may be regrouped. The notation there is already English, and the literal scale
words of a translation (`2,340 hundred million`) are combined into one value.

### Where the translation is shown

- **Agents.** A corpus hit from a non-English passage carries `language` and, when one
  is held, `translation` (`{text, source_language, target_language, note}`, figures in
  English notation). `text` stays the original. English hits are byte-identical. A
  passage with a translation gets 3,000 more prompt characters, so the original stays
  whole.
- **`resolve_evidence`** → `EvidenceContext.translation`.
- **The report.** `professional_research.translated_citations` holds one row per cited
  non-English passage: `{evidence_id, language, language_name, original,
  original_truncated, page_start, translation, translation_note, translation_model}`. It
  is attached after the editor, so no model reads or restates it. Rows are read-only and
  capped at 60, with 2,400 characters per side. The source text passes through
  `neutralize_forbidden_terms` like every other quote. The block is absent when no
  non-English passage is cited.
- **Web.** Under each finding's evidence line, a collapsed "Source in German (page 41) —
  original and machine translation" panel. It shows the original (labelled as the
  evidence, with `lang` set) and the translation with its note
  (`TranslatedCitations.tsx`).

## Limits

- Figure normalisation covers the eleven decimal-comma languages and JA/ZH/KO.
  Unsupported languages are left as written, so their figures still fail closed.
- The legacy (V2) evidence-pack excerpts and the claim checks over finding statements
  are unchanged. Findings are written in English.
- Nothing schedules the translation job, so a company has translations only after an
  operator ran `scripts/translate_corpus.py`.
- Not run against a live Azure deployment; the tests use a fake client.
- The web panel was checked with Playwright on the installed Chrome, because this
  machine lacks the pinned Playwright browser build.
