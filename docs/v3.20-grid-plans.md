## 7.1 Store + ENTSO-E TYNDP ingest (migration 057)

**Tables.**
- `grid_plan_ingests` — one row per ingest attempt: source, edition, file SHA-256, counts, status
  (`running` / `complete` / `failed`) and the failure reason. A failed ingest is kept.
- `grid_capex_plans` — one row per project or investment. Each row holds:
  - promoters (raw text + split names);
  - plan name and edition;
  - region (for ENTSO-E, from the portfolio's "Borders" sheet);
  - category;
  - technology tags and the highest stated voltage;
  - capex amount + currency, or neither (a CHECK enforces this);
  - capacity;
  - commissioning text + year;
  - status text + `status_class`;
  - source URL, title, retrieval time, use constraint and attribution.

  Unique on (source, edition, record kind, external id).

**Parser** (`services/grid_plans/entsoe_tyndp.py`).
- Layout pinned on the real file. It reads the sheets "Transmission Projects", "Transmission
  Investments" and "Storage Projects" (plus the optional "Borders" sheet), and looks columns up by
  header name.
- A missing sheet or column fails closed (`LayoutError`). The ingest is then recorded as `failed`
  and no plan row is written.
- An investment inherits its project's promoters and region.
- Projects listed as non-submitted or non-compliant are not ingested.

**Vocabulary** (`services/grid_plans/base.py`).
- Technology tags are deterministic keyword matches on name, category and description: `hvdc`,
  `overhead_line`, `cable`, `substation`, `transformer`, `reactive_compensation`, `offshore`,
  `interconnector`, `converter_station`, `storage`, `pumped_hydro`.
- `status_class` ∈ under_consideration / planned / permitting / committed / under_construction /
  commissioned / withdrawn / other.
- The commissioning year is the first four-digit year stated.
- Promoters are split on `,` `;` "and" `&`, keeping a legal form with its name ("Iberdrola, S.A.").

**Ingest** (`services/grid_plans/store.py`, `scripts/ingest_grid_plans.py`).
- It is an operator job; nothing schedules it.
- It reads either `--file PATH` (nothing downloaded) or `--download` (the pinned URL, no redirects,
  research User-Agent).
- A source whose flag is off is refused before anything is parsed or stored.
- Re-ingesting an edition updates its rows in place. A new edition (`--edition`, default: the date
  in the file name) adds rows beside the old ones.

**Real file (2026-11-16).** 633 records: 268 projects (199 transmission + 69 storage) and 365
investments.
- Status classes: 248 under consideration, 161 planned, 135 permitting, 71 under construction,
  18 commissioned.
- 342 records have a stated voltage; 1 has no commissioning year.
- **0 with capex**: the portfolio states none. Capex comes with the CBA results in the final
  TYNDP 2026.

Checked on PostgreSQL 16:
- migration 057 upgrade;
- the capex-pair CHECK rejects an amount without a currency;
- downgrade;
- re-upgrade;
- the script refuses while the flag is off;
- 633 rows written, and a second run of the same edition updates them in place.

**Not in 7.1.** Matching promoters to entities, and the report read. Both are in 7.3 (below).

## 7.2 AEMO + Berkeley Lab Queued Up ingest

**AEMO** (`services/grid_plans/aemo_tai.py`).
- The layout is pinned on the August 2026 workbook. It reads the sheet "Transmission augmentations"
  and looks columns up by name.
- Each row is one project. Its proponents are the TNSPs (Transgrid, Powerlink, EnergyCo, VicGrid,
  TasNetworks, ElectraNet, …).
- Status mapping: Committed → `committed`; Anticipated / Actionable → `planned`; Future →
  `under_consideration`.
- In-service cells come as a date serial (shown as an ISO date), "Oct-26", or
  "Stage 1: Aug-29 / Stage 2: Nov-30". The year is the first one stated, and the full text is kept.
- "Increased network capacity" is kept as text.
- AEMO gives no project id, so the key is region + project name.
- **No capex** is stated.
- Real file: 27 projects (6 committed, 20 planned, 1 under consideration), all with a year.
- The aemo.com.au pages sit behind a bot challenge. A server `--download` may be refused; the
  operator then passes the file with `--file`. The challenge is never circumvented.

**Queued Up** (`services/grid_plans/lbl_queued_up.py`).
- The layout is pinned on the 2026 edition. It reads the sheet "03. Complete Queue Data" and looks
  up the codebook's field names.
- Only **active** requests are counted. They are aggregated into one `queue_summary` row per
  region × transmission provider × utility; names are normalised, so "AMEREN MISSOURI" and
  "Ameren Missouri" are one provider.
- Each row carries:
  - the request count;
  - active MW (the stated `mw_1..mw_3`; storage LBL imputes for hybrids is NOT added);
  - MW with an executed interconnection agreement;
  - MW by resource type (top 5);
  - the span of proposed online years (the median is the year).
- The promoters are the utility and the transmission provider.
- This is a demand signal for the provider's network, **not capex**.
- Real file: 8,513 active requests → 207 provider rows, 1,865 GW. LBL's headline of about
  2,060 GW includes its imputed hybrid storage.
- Largest rows: ERCOT (1,796 requests, 408 GW), BPA (289, 130 GW), SCE (146, 69 GW).
- Run: 28 s and about 0.8 GB peak RSS for the 33 MB sheet.

Checked on PostgreSQL 16 with the real files:
- AEMO: 27 rows.
- Queued Up: 207 rows. A second run updated the same 207 rows in place.

The first Queued Up run hit the unique key: case variants of one utility gave two groups with
the same key. The parser now groups on the normalised key. The store also suffixes a repeated key
within one file instead of failing the ingest.

## 7.3 Demand-side triangulation in the report

`services/grid_plans/triangulation.py` (pure) and `v3_pipeline._demand_plans` produce a
`demand_triangulation` block in the **business model** section. It sits beside the
relationship block and is shown in the web report as "Do the customers' grid plans back the
demand?".

**When it appears.** Only for a company classified into the electricity stack, and only while
`V3_DEMAND_TRIANGULATION_ENABLED` is on (the default). It makes no external call: it reads the
newest held edition of each **enabled** grid-plan source. ENTSO-E is therefore read only when
its private-use flag is on. The block lists the editions it read in `sources_read`.

**The question per named customer** (from `business_model.relationships.customers`): does
that customer publish **active** projects in the subject's technology?

| Status | Meaning |
|---|---|
| `corroborated` | It promotes at least one relevant project that is planned, in permitting, committed or under construction, and not due before this year. A transmission provider with active interconnection requests (a Queued Up `queue_summary` row) also counts. |
| `not_corroborated` | It appears in a held plan, but nothing there is both relevant and active. |
| `not_in_held_plans` | No held plan names it. **This is not evidence against the claim.** The customer may not own a grid, or its plan may not be held. |

**Overall state:**
- `no_customer_named`, with the reason: nothing is disclosed, or the relationship graph is off;
- `corroborated` if any customer is;
- `not_corroborated` if a customer was found in the plans but none is corroborated;
- `no_grid_customer_matched` otherwise.

**Relevance.** A layer maps to the plan technology tags its products go into:
- transmission → HVDC, cable, overhead line, transformer, substation, converter station,
  interconnector;
- storage → storage and pumped hydro;
- utilities → any project;
- generation → queued generation types;
- the other layers as in `LAYER_TECH`.

An active interconnection queue counts for every layer, because new connections need network
equipment.

**Name matching.** Names are normalised before they are compared:
- accents are removed, as is text in brackets;
- dots are dropped, so "S.A.U." becomes "sau";
- legal forms are removed: Inc, Ltd, plc, AG, SA, SAU, SL, SpA, NV, GmbH, Pty, Holdings,
  Group, …

Two names then match in one of two ways:
- through a versioned alias table (`ALIAS_VERSION` 2026-11-17.1): "American Electric Power" ↔
  "AEP", "Pacific Gas and Electric" ↔ "PG&E", RTE, REN, REE, National Grid, APG, IPTO, BPA,
  ERCOT, Duke, Transgrid, SP Transmission, SSEN Transmission, and TenneT ("TenneT TSO GmbH" ↔
  "TenneT DE" / "TenneT-NL" / "TenneT Germany");
- by **prefix**: the shorter name is the start of the longer one, at least 5 characters, ending
  on a word boundary. "Transgrid" matches "Transgrid NSW", and "RWE Renewables UK" matches
  "RWE Renewables UK Humber Wind". A one-word key may do this only when the name **is** one
  word. A word left over after removing the legal form is not enough. A fragment in the
  middle of a name never matches.

The prefix rule replaced whole-token containment on 2026-11-17, after an end-to-end run on
the four real files found two false matches:
- "Southern Company" lost "Company", and "southern" then matched inside the SSEN alias
  "Scottish and Southern Electricity Networks";
- "NV Energy" lost "NV", and "energy" then matched inside "Duke Energy Carolinas".

The same run found two misses. TenneT was missed because filings use the legal entity and
the plans use the brand, which the alias now covers. Energinet was missed because the
ENTSO-E promoter "Statnett together with Energinet" was not split; "together with" is now a
separator.

**What it does not check.** None of the held plans states capex. The block therefore checks
that the customer's projects **exist and are active**, not the **size** of a backlog claim, and
`capex_note` says so. The subject's own backlog, order-book and visibility findings are
referred to by finding **label** (`subject_claim_labels`), because a finding is stated once.

**Per customer** the block carries:
- the number of plan records and of relevant active records;
- the matched promoter names;
- up to 5 projects, each with source, edition, status, commissioning text, tags, capacity and
  attribution.

The block is computed after the editor, like the other computed blocks, and passes through the
report safety scan.

Tests: `tests/test_v3_20_7_3_demand_triangulation.py`. They cover:
- the states and statuses;
- alias and token matching, including that a fragment does not match;
- relevance by layer;
- the commissioning-year cut-off;
- reading only the enabled sources' newest edition;
- pipeline gating;
- the report gate;
- the keys the web reader uses.
