## 1. Why this phase exists

A manual run of the query **"small cap growing european luxury companies"** returned LVMH,
Hermès, Richemont, Kering, Pandora, Swatch, Moncler and Burberry. The Council described them
as *"small-cap European luxury companies"* even though it also called them *"large well-known
luxury firms"*. **The user's words had become company facts.**

The run exposed six things wrong with how companies enter the research engine:

1. `small-cap` was parsed and then nothing enforced it.
2. `growing` was never defined or checked.
3. Pre-V3.18 reports were handed to the Council as "current research".
4. Council prose could state a requested attribute as a verified one.
5. The universe can only contain companies hard-coded in `THEME_COMPANY_REGISTRY`.
6. Peers can only be companies the platform already holds, for the same reason.

V3.18 made deep research professional. V3.19 fixes how companies reach it.

## 2. Forensics — what is true today (`CURRENT`)

All file references are relative to `apps/api/app/`.

### 2.1 The Discovery path

```text
POST /market-discovery/thesis-runs
  → market_thesis_parser.parse_thesis        (keyword tables; no LLM, no network)
  → market_universe_builder.build_universe   (THEME_COMPANY_REGISTRY only — 8 European luxury names)
  → DiscoveryRun(status=pending)             (BackgroundTasks, not the durable worker)
  → process_run: per ticker extract_signal   (runs run_company_analysis, the V1 workflow)
      → score_signal → _build_candidate      (candidate_score: momentum weight 0.30)
  → POST /runs/{id}/council-review           (8-agent run-level council)
  → POST /candidates/{id}/run-analysis       (V2 + V3.18 deep research)
```

| Fact | Where |

| "growth" in a thesis is only a **catalyst-intent phrase** (+4 points) | `market_thesis_parser.py:433`, `discovery_thesis_scoring.py:148` |
| `market_cap_mln` for a non-US listing is **always None** (shares come only from SEC DEI) | `market_metrics_enrichment.py:180-197` |

### 2.2 Freshness

`current_research_resolver.resolve_current_research_report` returns the newest report that has
`final_report_version` and a parseable `report_content` block. It checks no engine version
and no age. A 2026-08 V2 Pandora report and a V3.18 professional report are
indistinguishable to it, and both reach the Council as `research_signals`.

A V3.18 report is identifiable: `source_summary_json["v3_research"]["professional_research"]`
is present (written by `pipeline/v3_pipeline.py:_professional_report`, `REPORT_VERSION = 1`).

### 2.3 Identity

The V3 entity master exists (`legal_entities`, `securities`, `security_listings`,
`entity_identifiers` with LEI/ISIN checksums), but **no production code path calls it except
`resolve`**. Listing verification today:

- **GLEIF** — works by LEI or exact legal name. It has no ticker index.
- **SEC** — US venues only.
- **EODHD search** — only with a key.
- **OpenFIGI** — no client.

`ensure_company` creates a `companies` row from `(ticker, exchange, name)` with no
verification at all. `exchange_registry.py` knows ~45 venues with MIC and currency.

### 2.4 The external research provider

`DeepSeekResearchProvider.investigate` (`integrations/deepseek/providers.py:1009`) runs a
retrieval-backed search on `/responses` and returns **`ResearchLead` claims, never evidence**.
`verify_lead` (`providers/leads.py:1274`) re-fetches the claimed URL through the platform's
own guarded fetcher. The lead's own host becomes the allowlist, with HTTPS only, public IP
only, no off-host redirect and a byte cap. It then checks that the claimed figure sits next
to the claim's words on the fetched page.

**This is the lead → verification machinery V3.19 reuses for companies.**

### 2.5 Metric semantics (the Kering regression)

**The defect is live in the current code**, not only in historical data:

- `sources/primary_fact_parser.py:497`: `net (?:financial )?debt` has no exclusion guard, so
  *"cost of net debt of €122m"* captures €122m as `net_debt`.
- `sources/extracted_fact_validator.py:173`: the table-row matcher is unanchored, so a row
  labelled *"Cost of net debt"* maps to `net_debt`, and so does *"Net debt/EBITDA"*.

No test covers either case.

### 2.6 Critical minerals

No official critical-minerals list exists in the code or on any branch. The
`critical_materials` thesis dimension asks *"whether its products are on official
critical-mineral lists"* and cannot be answered — the V3.18 `KNOWN LIMITATION 1`.

### 2.7 Multilingual

Language detection (fr/de/it/da) and a translation foundation exist; translation is off. The
fact parsers are English-only. The discovery-screening questions in this phase are answered
by the retrieval provider, which reads any language; the platform's own verification of a
figure is language-neutral, because it matches numbers and metric words the provider quotes
from the page.

## 3. Goals and non-goals

**Goals:**

- Turn a natural-language thesis into a **Discovery Intent**: structured, taxonomy-validated,
  with hard/soft semantics, shown to the user.
- **Discover companies the platform does not know**, from external sources, bounded.
- **Verify identity and listing** before anything enters the universe.
- **Verify constraints with evidence**: size from a fetched market cap plus official FX,
  growth from business evidence, region from the listing and domicile, theme from what the
  company does.
- **Decide eligibility deterministically.** The Council prioritises eligible candidates and
  may never redefine eligibility.
- Give every report a **freshness class**. Legacy research is history, never current evidence.
- **Keep requested and verified attributes apart** everywhere prose is written.
- **Discover peers** through the same verified path.
- An **official critical-minerals source**.
- Fix **`cost_of_net_debt ≠ net_debt`**.

**Non-goals:**

- An unbounded market scan.
- A new paid provider.
- Real-time prices.
- Any valuation or recommendation.
- Replacing V3.18 deep research.
- Durable-job migration of discovery runs (see §11).

---

## 4. The core invariant

> **A user's words are a filter hypothesis. They become a company attribute only after
> verification.**

Every constraint result carries:

- `requested`: what the user asked
- `status`: `pass` | `fail` | `unknown` | `not_requested`
- `value` and `basis`: what was observed
- `source`: URL, tier and as-of date

`status = pass` exists only when `value` and `source` exist. The Council, the report and the
UI speak about a candidate's size or growth **only** through these results.

## 5. Target architecture (`V3.19 TARGET`)

```text
thesis text (+ optional selectors)
  │
  ▼  discovery/intent.py ─────────────── DiscoveryIntent (hard/soft constraints, closed vocab)
  │
  ├─► universe sources, each producing LEADS, never candidates
  │     • curated registry            (existing, T3)
  │     • platform company registry   (companies already held, matching the intent)
  │     • external discovery          (discovery/leads.py → research provider, bounded)
  │
  ▼  discovery/identity.py ───────────── listing verification + dedup → VerifiedIssuer | RejectedLead
  │
  ▼  discovery/screening.py ──────────── one bounded screening investigation per issuer
  │        claims → verify_lead (platform fetch) → verified facts
  │
  ▼  discovery/constraints.py ────────── size (fx.py) · growth · region · theme · listing
  │        → ConstraintResult[] → Eligibility
  │
  ▼  excluded (persisted, shown) | returned (≤ max_candidates) → existing extract_signal/scoring
  │
  ▼  discovery/freshness.py ──────────── research freshness per candidate
  │
  ▼  Discovery Council (requested vs verified contract + leakage guard)
  │
  ▼  run-analysis → V3.18 professional research (thesis carry-forward reads VERIFIED size)
```

New package: `app/services/discovery/`. The orchestrator stays in
`market_discovery_service.py`, which gains one branch for intent-driven runs.

### 5.1 Discovery Intent (`discovery/intent.py`)

`DiscoveryIntent` is a frozen dataclass. `schema = "discovery_intent/1"`. Fields:

| Field | Type | Vocabulary |
|---|---|---|
| `themes` | list[str] | parser `_THEME_TABLE` keys + new `critical_materials`, `semiconductor_supply_chain` |
| `sectors`, `industries` | list[str] | `sector_taxonomy` canonical values |
| `regions`, `countries` | list[str] | `discovery_filters` canonical values (+ `Oceania`) |
| `exchanges` | list[str] | `exchange_registry` codes |
| `materials` | list[str] | `macro/commodities` slugs (gallium, germanium, antimony, tungsten, rare_earths, lithium …) |
| `end_markets` | list[str] | V3.18 `THESIS_DIMENSIONS` keys (semiconductors, ai_data_centres, electric_vehicles …) |
| `catalysts` | list[str] | closed set: permitting, government_funding, offtake, production, contracts, orders, regulatory_approval |
| `horizon_years` | (min, max) \| None | parsed from "2–5 years", "over 3 years" |
| `size` | `Constraint` \| None | micro_cap, small_cap, mid_cap, large_cap, mega_cap |
| `growth` | `Constraint` \| None | `growing`, `high_growth` |
| `profitability` | `Constraint` \| None | `profitable` |
| `listing` | `Constraint` | always hard: must be a verified listed security |
| `exclusions` | list[str] | words after an exclusion connective |
| `unmatched_terms` | list[str] | shown to the user, never silently dropped |

A `Constraint` holds:

- `key`, `requested` (the bucket or label)
- `hardness`: `hard` | `soft`
- `hardness_basis`: the rule that decided it, e.g. `"default: bare size term"` or
  `"'prefer' marks soft"`
- `verification_required = True`

**Hardness rules** are deterministic and ordered. The first rule that matches wins.

1. `only` / `strictly` / `must` / `exclusively` within 3 words before the term → **hard**.
2. `prefer` / `preferably` / `ideally` / `ideal` / `if possible` / `bonus` / `nice to have`
   within 4 words before, or the clause starts with one → **soft**.
3. Comparatives such as `smaller` or `larger` → **soft**, mapped to adjacent buckets:
   `smaller` = micro+small+mid, `larger` = large+mega.
4. A bare term (`small cap companies`, `growing companies`) → **hard**. The user named it
   as a property of what they want. The UI shows this default and the basis.

Region, sector, theme and material are **hard** when named. Catalysts and horizon are always
**soft**: they rank, they never exclude.

**Planner.** The intent is built **deterministically**. There is no LLM in V3.19.1. The
closed vocabularies above are the whole output space, so no model text can become a filter.
Terms the tables do not cover are returned in `unmatched_terms` and shown ("not understood:
…"). An LLM planner behind the same schema validator is deferred until live queries show
unmatched terms that matter.

**Size taxonomy.** One table, moved from `director/thesis.py` into `discovery/constraints.py`
and imported back by `thesis.py` so there is one source. Bounds are in USD at the as-of FX
rate:

| Bucket | Range |
|---|---|
| micro | < 300m |
| small | 300m – 2bn |
| mid | 2bn – 10bn |
| large | 10bn – 200bn |
| mega | ≥ 200bn |

`large_cap` keeps its V3.18 meaning (≥ 10bn) when requested, so mega counts as large.

### 5.2 External company discovery (`discovery/leads.py`)

`plan_lead_queries(intent) -> list[LeadQuery]` produces at most
`V3_DISCOVERY_MAX_LEAD_QUERIES` queries (default 4). Each one is a bounded question built
from the intent's closed vocabulary only: region × (theme | material | industry), plus size
words when requested. **The user's raw text is never sent** (same rule as V3.18 thesis
questions: what a user typed is theirs).

Each query runs one `investigate()` call with a **company-lead system prompt**. It asks for
JSON `{"companies":[{legal_name, ticker, exchange, country, listing_source_url,
evidence_url, why}]}`, prefers exchange and issuer pages, and forbids inventing tickers.
Output is parsed into `CompanyLead` records:

- `name`, `ticker`, `exchange` (normalised through `exchange_registry`), `country`
- `source_urls`, `why`
- `discovery_query`, `provider`, `task_id`

**A lead is never a candidate.**

Hard bounds:

| Setting | Default | Hard cap |
|---|---|---|
| `V3_DISCOVERY_MAX_LEAD_QUERIES` | 4 | 8 |
| `V3_DISCOVERY_MAX_RAW_LEADS` | 60 | 100 |

The provider is the existing `research_provider_for(cfg)`. With no provider the run records
`external_discovery: unavailable (no provider)` and continues on the other sources.

### 5.3 Identity & listing verification (`discovery/identity.py`)

A lead becomes a `VerifiedIssuer` only when **all** of these hold:

1. **Venue known.** `exchange` normalises to an `exchange_registry` entry (so MIC and listing
   currency are known). An unknown venue → `rejected: unknown_venue`.
2. **Listing evidence.** A page **fetched by the platform** (`safe_fetch_document`, the
   lead's own host as the allowlist, all fetcher guards applied) names the company **and**
   the ticker (or a checksum-valid ISIN), and its publisher tier is one of:
   - **exchange**: a closed list of exchange-operator hosts, e.g. `euronext.com`,
     `six-group.com`, `londonstockexchange.com`, `borsaitaliana.it`,
     `nasdaqomxnordic.com`, `asx.com.au`, `tmx.com`, `nasdaq.com`, `nyse.com`,
     `boerse-frankfurt.de`, `deutsche-boerse.com`
   - **regulator**: `publisher_tiers` T1/T2, e.g. `sec.gov`, `sedarplus.ca`
   - **issuer**: the page's registrable domain matches the company name (a normalised
     name token of ≥ 4 characters equals the domain label; lookalikes are refused by
     construction because the check is equality on the label)

   A search snippet, an aggregator page or model text **never** verifies a listing (§28 of the
   brief). Aggregator hosts may *discover*; they are recorded as `discovered_via` only.
3. **Name consistency.** The fetched page's name matches the lead's name after legal-suffix
   normalisation (`SA`, `S.p.A.`, `AG`, `plc`, `A/S`, `Ltd`, `Inc`, `Corp`, `N.V.`, `SE`),
   by token-set equality on the distinctive tokens.

Deduplication comes first and costs nothing:

- `(ticker, exchange)` against `companies`.
- The normalised name against held companies.
- Within the run, by `(ticker, venue)` and then by normalised name.

A lead matching a **held** company inherits its identity (`identity_source: platform_registry`).
It is not re-verified, because the curated registry and held companies are T3 reference data
already on record. A matched lead is still screened.

GLEIF is consulted **only** to enrich (LEI, jurisdiction) on an exact single match. It never
verifies a listing, because it has no ticker index. It is optional and never blocks.

Output per lead:

- `identity_status`: `verified` | `platform_registry` | `rejected`
- `rejection_reason`: `unknown_venue` | `no_listing_evidence` | `name_mismatch` |
  `fetch_failed` | `duplicate_of:<key>`
- `listing_source`: url, tier, fetched_at, content_hash

**Lifecycle.** A lead is stored on the run. A verified issuer is stored on the run. A
**returned** candidate goes through `ensure_company` (a `companies` row, `status="new"`),
because deep research needs a company. **Excluded or rejected leads never create a
`companies` row.** That is the staged lifecycle `lead → verified security → discovery
candidate → company`.

### 5.4 Lightweight screening (`discovery/screening.py`)

Each verified issuer gets **one** `investigate()` call, at most `V3_DISCOVERY_MAX_SCREENED`
(default 16, hard cap 25), run with bounded concurrency (`V3_DISCOVERY_SCREENING_CONCURRENCY`,
default 4). The call asks only for what eligibility needs, each item as a claim with a source
URL:

1. `market_capitalisation` (value, currency, date), or `shares_outstanding` + `share_price`
2. `revenue_latest` and `revenue_prior` (period labels, currency), and/or
   `revenue_growth_reported_pct` / `revenue_growth_organic_pct` (period), and for a
   pre-revenue developer `production_growth` / `capacity_growth`
3. `business_description`: products, materials, brands, projects (one sentence each, sourced)
4. `headquarters_country`
5. at most two recent catalysts (dated, sourced), and financial distress signals if any

Every claim then goes through **`verify_lead`**:

- Figures are verified next to their words on bytes the platform fetched.
- Text claims (business description, material exposure) are verified by `locate_passage`.

**Only verified claims count.** Unverified ones are kept and labelled `unverified_claim`, so
the user can see what was alleged and not established.

`V3_DISCOVERY_MAX_VERIFICATIONS_PER_ISSUER` (default 5) bounds fetches.

A company the platform already holds with a **fresh** V3 report (§5.7) uses that report's
facts first (revenue by period) and only screens what is missing.

### 5.5 Constraint verification (`discovery/constraints.py`, `discovery/fx.py`)

**FX (`fx.py`).** FRED H.10 daily noon buying rates, the Federal Reserve's official series,
fetched as CSV through the existing `safe_fetch_document` + `fred_url` path (T2, free, no key).

| Currency | FRED series | Direction |
|---|---|---|
| EUR | `DEXUSEU` | USD per EUR |
| GBP | `DEXUSUK` | USD per GBP |
| CHF | `DEXSZUS` | CHF per USD |
| DKK | `DEXDNUS` | DKK per USD |
| SEK | `DEXSDUS` | SEK per USD |
| NOK | `DEXNOUS` | NOK per USD |
| AUD | `DEXUSAL` | USD per AUD |
| CAD | `DEXCAUS` | CAD per USD |
| JPY | `DEXJPUS` | JPY per USD |
| HKD | `DEXHKUS` | HKD per USD |
| CNY | `DEXCHUS` | CNY per USD |

`GBX` = GBP / 100. The latest observation on or before the market-cap date is used, never
one after it. The rate, its date, the series and the URL are recorded. An unmapped currency
gives `size: unknown (no official FX series for <cur>)`, never a guess. Rates are cached per
process per day.

**Size.** `status`:

- `pass`: the USD value is in a requested bucket
- `fail`: outside every requested bucket
- `unknown`: no verified market cap

Supporting fields:

- `borderline: true` when within ±15% of a band edge (shown, not decisive).
- `value`: native amount + currency + USD amount + bucket.
- `source`: URL, tier, as-of.

The market-cap as-of is the date stated on the page, or else the fetch date, labelled which.

**Growth.** `growing` is defined as **business growth over the latest reported comparable
period**. The preferred measures, in order:

1. organic / like-for-like / constant-currency revenue growth
2. reported revenue growth, or two verified revenue figures for consecutive periods
3. for a company whose playbook is `mining` or `biotech` and which has no revenue:
   production or capacity growth

**Price momentum is not an input.** `constraints.py` has no parameter that could receive it.

Status values:

- `established`: the measure is > 0
- `declining`: < 0
- `mixed`: organic and reported disagree in sign, or the two latest periods disagree
- `not_established`: nothing verified

When `growth` is **hard**:

- `established` → pass
- `declining` → fail
- `mixed` / `not_established` → unknown

`high_growth` requires ≥ 15%.

**Region.** `pass` when the listing venue's region (from `exchange_registry`) **or** the
verified HQ country is in the requested regions or countries. `fail` when both are known and
neither matches.

**Theme / material / industry.** `pass` when a **verified** business-description claim, or
held-company classification, names the theme's or material's vocabulary affirmatively. This
reuses V3.18.14 `names_dimension` negation handling, generalised to any vocabulary.

- `direct` exposure: the company produces or sells it.
- `indirect` exposure: the company supplies inputs to it or buys from it.

Anything short of that is `unknown`; a denial is `fail`.

**Critical materials.** A material on the **official list** (§5.9) is marked
`officially_designated: true, list: USGS 2022`. The company's own "critical input" language
never sets it.

### 5.6 Eligibility

`decide_eligibility(results) -> Eligibility`:

| Condition | Eligibility |
|---|---|
| identity not verified | `excluded` (reason `identity_unverified`) |
| any **hard** constraint `fail` | `excluded` (reasons listed) |
| all hard constraints `pass`, no soft `fail` | `eligible` |
| all hard constraints `pass`, some soft `fail` | `included_with_mismatch` |
| some hard constraint `unknown`, none `fail` | `eligible_unverified` |

Ranking among returned candidates is ordered as follows:

1. eligibility: eligible > included_with_mismatch > eligible_unverified
2. number of verified hard passes
3. soft passes (catalysts, horizon, theme directness)
4. thesis relevance

Nothing else ranks. `max_candidates` (default 10) caps the returned set. **The quota is never
filled with excluded candidates.** Returning 3 is correct when 3 qualify.

Excluded candidates and rejected leads are **persisted** on the run (rule 8: rejected
companies are learning data) and shown in a collapsed "Excluded" list with reasons.

### 5.7 Research freshness (`discovery/freshness.py`)

`classify_report(report, now, cfg) -> ResearchFreshness`:

| Class | Rule |
|---|---|
| `legacy` | no `source_summary_json.v3_research.professional_research` block (V1/V2 report, or V3 before V3.18) |
| `v3_current` | professional block present **and** `researched_at` ≥ now − `V3_RESEARCH_FRESH_DAYS` (default 120) **and** no newer annual period is known for the company than the report's `evidence_as_of` period |
| `v3_stale` | professional block present, but older than the window or superseded by a newer annual period |

The record carries:

- `research_engine_version`: stamped `"v3.19"` on new V3 reports, inferred `"v3.18"` for an
  existing professional block, and `"legacy"` otherwise
- `research_depth`: `professional` | `standard` | `screening`
- `researched_at`, `evidence_as_of`, `report_id`, `age_days`

**Reuse contract:**

- **Only `v3_current` research may be given to the Council as current evidence.**
- `v3_stale` is given as *dated context*, with its age and a `stale` label.
- `legacy` is **never** given as evidence. The Council sees `historical_research_exists: true`
  with its date, so it can say a history exists without reading it as current.
- The UI shows the class on every candidate and report link.

Legacy reports are **not mutated**.

### 5.8 Discovery Council contract

The evidence pack gains:

- **Run level:** `requested_constraints`, a list of `{key, requested, hardness}` labelled
  `REQUESTED BY THE USER — NOT A PROPERTY OF ANY CANDIDATE`, plus the funnel counts.
- **Per candidate:**
  - `verified_attributes`: size bucket and market cap with its source, growth status and
    basis, region, theme exposure
  - `constraint_results`, `unknown_constraints`, `failed_constraints`
  - `eligibility`, `discovery_provenance`
  - `research_freshness`
  - `research_signals` **only when `v3_current`**

Removed from the pack: `momentum_score` and `momentum_label`. They stay on the candidate row
and in the screening score, but a council asked about business growth must not be handed a
price signal next to it.

The prompt gains a `REQUESTED_VS_VERIFIED` contract. Size, growth, region or theme may be
attributed to a candidate **only** from its `verified_attributes`. The cohort may be
described only by counts of verified attributes ("3 of 8 have verified market caps in the
small-cap band").

**Leakage guard (`discovery/attribute_guard.py`).** This is a deterministic post-check on
every stored council text field. A sentence that attributes a size bucket or growth label to
the candidates it cites, or to the cohort ("all", "these", "the candidates"), is kept only if
**every** candidate it applies to has that attribute verified. Otherwise it is removed and
recorded in `review.attribute_guard.removed[]` together with the reason. The guard also
fires when a candidate note's rationale claims a bucket different from the verified one.
Sentences that mention the attribute as *requested* ("the user asked for …", "requested")
are kept.

**Eligibility is not negotiable.** Excluded candidates are not in the pack's candidate list.
A council `internal_action` of `research_next` on an `eligible_unverified` candidate is kept
but labelled with the unverified constraints.

### 5.9 Official critical-minerals source (`sources/critical_minerals.py`)

`CRITICAL_MINERALS_USGS_2022` is a code-defined dataset holding the 50 minerals of the 2022
List of Critical Minerals (U.S. Geological Survey, 87 FR 10381, 2022-02-24). It is stored
with:

- `source_url`, `publisher = "U.S. Geological Survey"`, `tier = T2_regulator_or_gov`
- `published = 2022-02-24`, `version = "2022"`, `retrieved_at`

Pattern: `verified_issuer_sources` (code-defined, provenance-carrying, reviewed in PR).

A `verify_against_source()` acceptance helper fetches the official document and confirms each
name appears. It is run in acceptance, not per request. If a newer official list is
confirmed during acceptance, it is added as a new version beside the old one, never in
place of it.

Consumers:

1. Discovery theme `critical_materials`, via `material ∈ list`.
2. The V3.18 thesis dimension `critical_materials`. The subject profile's commodities are
   intersected with the list, producing a deterministic finding with the list as its cited
   source.

### 5.10 Dynamic peers (`agent_tools/peers.py`)

When `V3_DYNAMIC_PEER_DISCOVERY_ENABLED` is on, `get_peer_set` adds up to 4 **externally
discovered** peers:

1. One lead query from the subject profile: canonical industry, commodities and products,
   region optional.
2. Each lead goes through `discovery/identity.py` (same verification, same bounds).
3. Each verified peer is recorded with `basis` (which dimensions matched: industry, material,
   value-chain position, geography) and `source_tier` of its listing evidence.

Unverified leads are never peers. `get_peer_financials` still compares only what the platform
can read under its own period rules, so non-SEC peers are listed as
`financials_not_comparable_here`, not compared on guesses.

### 5.11 Metric semantics (Kering)

This is a general fix, with no issuer-specific code.

In both label matchers, `net_debt` is preceded by an exclusion guard. The rejected prefixes
are `cost of`, `cost of the`, `interest on`, `finance costs? on`, `income on`, `change in`,
`movement in`. The rejected suffixes are `/ EBITDA`, `to EBITDA`, `ratio` and `x`.

`cost_of_net_debt` becomes a recognised label that maps to **nothing** in the balance-sheet
fields, so the row is consumed rather than falling through to `net_debt`.

The same guard applies to `net_cash` and `cash`, e.g. "interest on cash" and "cash flow". Where
a pattern already excludes a case, the existing exclusion is kept.

Mutation tests: removing the guard must fail `cost of net debt €122m ≠ net_debt 122`.

### 5.12 UI

`/research/discover`:

- **Understood panel.** The intent as chips: Region, Industry/Theme, Materials, Size
  (`Small-cap — hard filter`, with its basis), Growth (`Growing — verified from business
  growth, not share price`), Catalysts/Horizon (soft), plus "Not understood: …". Also shows
  "Open company discovery: on/off".
- **Funnel line.** `N raw leads → N verified public issuers → N met hard constraints → N
  returned`.
- **Candidate card.**
  - Why it matched (provenance: source, query).
  - Verified constraints (value + source + as-of).
  - Unknowns and mismatches.
  - A research freshness badge: `Current V3 research (12 days)`, `Stale (143 days)` or
    `Legacy report — historical only`.
- **Collapsed "Excluded (N)".** Name + the failing constraint with its value.
- **Scores.** "Research priority" is removed from the card. The Council's placement
  (research next / monitor / insufficient data / not now) is the priority shown. The
  deterministic score is renamed **Screening score** and appears only in the comparison
  table with its tooltip. This removes the "Council: highest priority / priority 0.0"
  contradiction.

## 8. Cost

The worst case per dynamic run, at defaults:

- 4 lead calls + 16 screening calls = **20 provider calls**
- ≤ 30 listing fetches + ≤ 80 claim fetches (platform-side, no vendor cost)
- ≤ 11 FRED fetches

At the V3.17.9 measured ~$0.003–0.01 per DeepSeek search call, that is **≈ $0.06–0.20 per
run**, recorded on one consumption row. Unknown cost stays unknown (`derive_cost` → None when
any unit is unpriced).

The deep dives are unchanged: V3.18 runs only when a user launches one.

## 9. Failure behaviour

| Situation | Outcome |
|---|---|
| Provider unavailable | external source skipped, stated on the run; curated + held sources still run |
| Lead with no verifiable listing | `rejected: no_listing_evidence`, persisted |
| Market cap not verifiable | size `unknown` |
| FX series missing or unreachable | size `unknown`, reason recorded |
| Growth not verifiable | `not_established` |
| Screening call failed or truncated | every constraint it would have answered is `unknown`; the candidate stays `eligible_unverified` at best |
| Zero eligible candidates | run `completed_with_warnings`, "no company met the hard constraints", excluded list shown; **never** backfilled |

## 10. Test strategy

- **Unit:** intent hardness rules; size buckets and FX direction for all 11 series and GBX;
  growth classification; region, theme and negation; eligibility table; freshness classes;
  leakage guard; the metric guard.
- **Integration (SQLite + real PostgreSQL via `V3_TEST_POSTGRES_URL`):** an end-to-end
  dynamic run with a fake provider and a fake fetcher, covering leads → rejected + verified →
  screened → excluded / eligible → candidates → council pack.
- **Producer → consumer:** the key sets of `thesis_match_json["v319"]` are pinned against the
  web types (see `reference_v3_payload_was_never_read_by_web`).
- **Mutation tests.** Each of the following reintroductions must make a test fail:

| Mutation | Test that fails |
|---|---|
| size verification bypassed (size → pass on request) | `test_size_hallucination_*` |
| requested attributes copied into candidate facts | `test_query_attribute_leakage_*` |
| momentum substituted as growth | `test_growth_is_not_momentum` |
| legacy report treated as current | `test_legacy_report_is_not_current` |
| a lead entering the universe unverified | `test_unverified_lead_never_candidate` |
| an unverified peer accepted | `test_unverified_peer_rejected` |
| `cost_of_net_debt` → `net_debt` | `test_cost_of_net_debt_is_not_net_debt` |

- **Web:** a Playwright spec for the intent panel, funnel, card constraint rows, freshness
  badge and excluded list against the mock backend.

## 11. Known design limits (declared up front)

- Discovery runs stay on FastAPI `BackgroundTasks`, as today. A container recycle mid-run
  leaves a run `running` until the existing 30-minute stale restart. Moving discovery onto
  the durable worker (a second job kind) is `DEFERRED`.
- The market cap is whatever a fetched page states, on the date it states. It is not an
  exchange feed, so its tier is recorded and a borderline value is flagged.
- The critical-minerals dataset is a code-reviewed copy of an official list, re-verified
  against the source in acceptance, not live-fetched per request.
