**Branch** `feature/v3-web-observability` · **Base** `main` @ `5826f61` (V3 dark)
**Status** implementation complete; activation pending deployment

## The gap this closes

V3 was merged to `main` and deployed dark on 2026-09-08. Every V3 flag defaults off, so
nothing ran. The question this slice had to answer first was what would happen if the
pipeline flag were simply switched on.

**The answer was: nothing visible.** Not "a partial view", not "a rough view" — nothing.

`attach_to_report` (`v3_pipeline.py:482`) writes the entire V3 result to
`reports.source_summary_json["v3_research"]`. The frontend reads `source_summary_json`
in exactly two places — `page.tsx:131` and `reportView.ts:795,863` — and both read one
key, `llm_council`. Nothing has ever read `v3_research`.

So with `V3_PIPELINE_ENABLED=true`, an authenticated user opening a report would have
seen a page byte-identical to one where V3 never ran, while the platform spent real
money on model calls and web searches to produce a payload nobody could reach.

## What was built

### 1. The telemetry the payload was missing (backend)

Before building a view, the thing being viewed had to be worth showing. Three
measurements were absent, and they were the expensive ones:

| Absent | Why it mattered |
|---|---|
| `documents_fetched` was the literal `0`, hardcoded at `v3_pipeline.py:455` | `ToolSession` had been writing real counts to `research_tool_calls.consumption_json` all along |
| Web searches and URL fetches were not reported at all | The most expensive units a run consumes were missing from its own record |
| The research provider's tokens never reached `model_by_vendor` | It is not a routing slot. A measured search spent **27,136 input tokens** and was recorded as costing nothing |

Also absent, and mattering more than the cost: **the external path's provenance**. Leads
were persisted to `research_leads` and never summarised into the payload, so a reader
could not tell a claim InvestingBuddy verified from one a vendor merely asserted.

Added to `v3_pipeline.py`:

* `external_research` on `V3ResearchOutcome` and in `to_dict()`;
* `_rows_for_this_run()` — correlates by `company_id` + `created_at >= run.started_at`.
  **This is an approximation, and it is documented as one**: neither `research_tool_calls`
  nor `research_leads` carries a `research_runs` id, so two runs for the same company
  overlapping in time would blend. Adding the FK is a migration this slice did not take.
* `_tool_call_consumption()` — sums `consumption_json` across the run's tool-call rows;
* `_external_research()` — `leads_discovered`, `leads_by_status`,
  `leads_rejected_by_reason`, `sources_retrieved_by_investingbuddy`, `evidence_promoted`,
  and a bounded `leads[]` array, each row carrying `evidence_id` and the explicit
  `is_canonical_evidence`;
* `_consumption(..., tool_units)` — the hardcoded zero replaced by real counts, plus the
  provider's own token spend under `provider_*` keys.

### 2. The V3 Research panel (web)

`src/components/research/v3Research.ts` — a tolerant parser. It returns `null` for every
report with no V3 payload, which is **the property the whole addition rests on**: an old
report renders exactly as it did. A *failed* run is deliberately not null — hiding it
would leave the reader believing the research simply had nothing to add.

`src/components/research/report/V3ResearchPanel.tsx` — one clearly labelled section on
the existing `/research/reports/[id]` page. No new page, no redesign. It shows the run,
why it degraded, findings with their evidence ids, gaps, external research, the red
team's challenges, the Chair's verdict, the delta and a collapsed consumption block.

Two rules the panel enforces in code, not in prose:

* **A lead is not a source.** `is_canonical_evidence` is read from the backend, never
  inferred from a lead's `status` — a future path could mark a lead verified without
  minting evidence. A rejected lead is *shown*, labelled "Provider claim only" with its
  rejection reason, because rejections are the honest denominator of the survival rate.
  It renders no evidence id, because it has none.
* **Unpriced is never free.** A null `estimated_cost_usd` renders as the stored
  explanation, never as `$0.00`.

### 3. Coverage

* `apps/api/tests/test_v3_report_observability.py` — 11 tests over the new telemetry,

* `apps/web/tests/e2e/v3-research-visibility.spec.ts` — 13 tests: 7 over the parser

## What the configuration actually does

`scripts/v3-production-config-derivation.py` derives the effect of a configuration
through the real code paths — it does not read flag names and assume. It prints no
credential: credentials are reduced to a present/absent bit before anything renders, and
`--check-secret-safety` asserts that rather than trusting it.

Measured, with production's Azure OpenAI present and `.env` excluded:

| Scenario | External tools | Research provider | Investigator routes to |
|---|---|---|---|
| `current` (production today) | none | None | azure_openai |
| `pipeline-only` | none | None | azure_openai |
| **`credentialed-not-consented`** | **none** | **None** | **azure_openai** |
| `proposed` | `search_web`, `fetch_public_source` | `DeepSeekResearchProvider` | deepseek |
| `consented-no-credential` | registered | None | azure_openai |

**The two-key rule holds.** `credentialed-not-consented` is identical to `pipeline-only`
in every derived field. A DeepSeek key in the environment changes nothing without the
flags — which is the specific failure this campaign already made once, when a key in
`.env` silently re-routed the Investigator off Azure OpenAI.

**One looseness, recorded and not fixed.** In `consented-no-credential` the flag is on
with no key: the tools still register, so the Director can plan a question needing one,
and the refusal happens at invocation rather than at plan time.
`register_external_tools`'s docstring claims the plan-time behaviour; `external_tools_enabled`
reads only the flag, so it does not get it. The consequence is bounded and honest — the
tool returns `{"available": false, "reason": "No external research provider is configured
and enabled. This is a statement about this platform's configuration, not about the
web."}` — so it is a wasted tool call, not a crash and not a false finding. It cannot
occur in the proposed configuration, where both are present. Left alone deliberately:
this slice was scoped to observability, not to tightening unrelated seams.

## Durable jobs: not required (Section E, decided from code)

`V3_DURABLE_JOBS_ENABLED` stays **false**.

Traced rather than assumed. The V3 pipeline runs in `_run_v3_pipeline`
(`company_research_service.py:860`), called from `process_company_research_by_id:775`.
**Both** entry points reach it: the durable path (`company_research_job.py:339`) and the
V2 `BackgroundTasks` path (`company_research_service.py:974`, dispatched at
`company_research.py:181`). So durable jobs are orthogonal to whether V3 runs or attaches
its state.

What the flag would change is recovery: with it off, an App Service recycle loses the
in-flight run, which is the V2 behaviour deployed today. Turning it on would also start a
polling worker inside the API process (`main.py:131`, since `v3_job_worker_in_process`
defaults true) — a second contract changing at the same moment as the research contract.
For a first live run, one variable at a time.

**A real risk to watch, not a blocker**: V3 adds elapsed time to a background run that
already takes 261–451s against a 300s gunicorn worker timeout. This is measured on the
first live run rather than predicted here.

## Artifact store: not required

`V3_ARTIFACT_STORE_BACKEND` stays `"none"` — lineage recorded, no bytes stored.

The external verification path does not use it. `_fetch_public_source` hashes bytes it
fetched in memory through `verify_lead`, and `LeadVerificationOutcome` refuses to
construct a verified status without that hash. Evidence promotion therefore works with no
artifact store at all. The `azure_blob` backend would additionally need a
`Storage Blob Data Contributor` role assignment on the App Service identity, which this
subscription's CLI identity cannot create (Contributor lacks `roleAssignments/write`).

## Security review

Independent review: **PASS, no blocking findings.** Secrets, tokenized URLs, SSRF, auth,
publish routes and data leakage all clean. Two points worth recording:

* **No XSS surface, and specifically no link.** Every untrusted string is a JSX
  expression child, which React escapes; there is no `dangerouslySetInnerHTML` and no
  `href` anywhere in the panel, so a vendor-supplied `javascript:` URL has nothing to
  attach to. `fetched_url` is parsed and deliberately never rendered; only `host` — a
  server-side `urlsplit(...).hostname` — reaches the DOM, as text.
* **Provenance holds end to end.** `promoted_evidence_id` is minted at exactly one site,
  guarded by `status == LEAD_VERIFIED and content_hash`; the backend derives
  `is_canonical_evidence` from that id rather than from `status`; and `LeadRow` renders
  the id only in the true branch.

Three non-blocking findings, all fixed:

1. **`sources_retrieved_by_investingbuddy` over-counted.** It also counted rejection
   reasons implying a document had been read. That is true of `value_mismatch` and its
   siblings — which carry the content hash anyway, so the clause bought nothing — but it
   also counted `url_unreachable`, set precisely when the fetch returned nothing usable.
   So the only reason the clause changed was the one where no retrieval happened, and the
   panel reported it as "InvestingBuddy retrieved N sources itself". Now counts the hash
   alone, tested in both directions.
2. The leak-check canary carried an `sk-` prefix; renamed so a naive CI secret scanner
   has no reason to flag a deliberately fake value.
3. #23's list of unguarded surfaces was short by two — gap text and chair open questions.
   Widened, and now enumerated against what the panel renders.
