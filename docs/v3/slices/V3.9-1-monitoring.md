# V3.9 Slice 9.1 — watchlists, change detection and signals

## Objective

The mechanism for "tell me when something relevant changes", **feature-gated with nothing
scheduling it**.

## Why now — and why last

> **Memory before monitoring.** A watchlist alert is only meaningful as "this changed
> relative to what we concluded".

"Pandora filed something" is a feed. "Pandora filed something, and it bears on the
cash-runway question your last analysis left open" is research. The second needs V3.8,
which is why this phase is ninth rather than second.

## Current implementation

None. Nothing watches anything; every run is initiated by hand.

## Proposed changes

Three tables (migration 038) and `app/services/monitoring/detector.py`.

### Nothing schedules it, and that is the deliverable

[OPEN DECISION #15](../OPEN_DECISIONS.md#15-monitoring-cadence) — how often to check — is
**user-owned and unresolved**. So `V3_MONITORING_ENABLED` defaults off, there is no cron,
no worker job and no scheduler, and **two tests enforce it**: nothing outside the package
calls `detect_for_company`, and the detector imports and calls no scheduler. The second is
checked on the **AST**, not on the text — the module's own docstring explains that there is
no cron, and a substring search flagged the explanation.

Guessing a cadence would answer a question asked of somebody else *and* start spending on a
path nobody approved.

### It refuses to be a feed

An issuer with **no prior research produces no signals**: there is nothing for a change to
be relative to. A document retrieved before the last run is not new. The signal that
matters most is a transcript that has appeared since — an event previously recorded
`not_published` whose transcript now exists is a gap the last run could not close and this
one can.

### A signal is an observation, never a conclusion

`summary` says what changed; `relates_to_question_key` says what it bears on. A test
asserts no verdict vocabulary appears in a summary: a signal carrying an interpretation
would be an unreviewed conclusion with an alert's authority, and the platform has a whole
council for reaching conclusions.

### Deduplication is the whole problem

A monitor that re-raises the same signal every run is a monitor everybody turns off.
`signal_key` is derived from **what was observed**, never from when it was noticed — a key
containing a timestamp would make every pass produce new signals — and
`ix_monitoring_signals_open_key` is a **partial** unique index: one *open* signal per key,
with the closed ones kept as history. "We told you in March and again in June" is
answerable; "we told you eleven times in March" is impossible.

There is deliberately **no `dismissed` status**. A signal somebody judged unimportant is
*acknowledged*; one the world overtook is *superseded*. Neither is a deletion.

## Feature flags       `V3_MONITORING_ENABLED` (default off)

## Security considerations

`watchlists.owner` exists from day one, nullable while the platform is single-user, because
retrofitting a tenant boundary onto a store that never had an owner column is a rewrite
(governance §8). A detection pass is bounded at `MAX_SIGNALS_PER_PASS`: a monitor that can
raise a thousand signals in one run is one that will, on the day a reindex touches every
document.

## Unit tests

Scheduling: nothing outside the package calls the detector; the detector imports and calls
no scheduler; the flag off observes nothing **and says so**. Not-a-feed: no prior research
means no signals, with the reason; a pre-run document is not new; a post-run one is; a new
IR event; and a transcript that has since appeared **without** re-raising the event.
Observations: an invented kind refused; the vocabulary closed at six; no verdict vocabulary
in a summary. Deduplication: the key derived from what was observed; a repeated pass
raising nothing twice; the database refusing a second open signal for one key;
acknowledging letting the key be raised again; no `dismissed` status. Watchlists: entries,
the one-issuer-once index, the owner column, and filtering by issuer and kind.

## Integration tests

Migration 038 against **real PostgreSQL 16**: seven statements, including that a second
open signal for one key is unstorable while an acknowledged one lets the key be raised
again, and that deleting the issuer removes its watchlist entry while **leaving the signal
history**.

## Live issuer acceptance

Not performed, and not possible without a cadence decision. Nothing runs a detection pass.

## Acceptance criteria

1. Nothing schedules a detection pass, enforced by two tests, and the flag defaults off.
2. An issuer with no prior research produces no signals, with the reason recorded.
3. One open signal per key, enforced by the database; acknowledging is not deletion.

## Non-goals

- Choosing a cadence. OPEN DECISION #15, user-owned.
- Delivering an alert anywhere — email, webhook, UI. A signal is a row; where it is shown
  is a product decision with its own surface.
- Triggering a research run from a signal. That is the obvious next step and it is a
  behaviour change that spends money on a schedule nobody has approved.
- `research_delta`, `open_gap_closable` and `macro_revision` detectors. The kinds are in
  the vocabulary; two detectors ship, and one source wired correctly beats four
  half-wired ones.

## Rollback

Set `V3_MONITORING_ENABLED=false` (the default). Migration 038 downgrades cleanly —
verified against real PostgreSQL.

## Dependencies

V3.8.1 (memory — the thing a change is relative to), V3.4.8 (IR events and transcript
availability), V3.1.2 (corpus versions).
