# V3.6 Slice 6.1 — the playbook schema and selection

## Objective

> **Industry methodology is versioned configuration, not a prompt.**

A typed, versioned playbook that the Director already knows how to consume, and a selector
that returns every applicable one — or none, with a reason.

## Why now

5.2 shipped the Director against a `PlaybookLike` Protocol and a baseline question set.
The Protocol has no implementation, so every run currently gets the same methodology —
which is the specific failure V3.6 exists to remove: a biotech with no revenue is not
analysable by revenue growth and margins.

## Current implementation

`sector_taxonomy.py` and a deterministic sector classifier exist, and sector affects
*labelling*, not *method*. The eight council roles are fixed, the evidence budgets are
fixed, and the questions are whatever the prompts ask.

## Proposed changes

`schema.py` (the types), `registry.py` (selection), and ADR-054.

### Why typed Python rather than YAML

The architecture sketch is YAML and the substance is identical either way — both are
files, both diff, both version. What typed declarations add is the property that made
`RoleSpec` load-bearing in 5.2: **a playbook naming a tool, role, calculation, evidence
class or completion rule that does not exist cannot be constructed.** With YAML that check
is a validator somebody has to remember to run.

Six refusals, each a playbook that would be quietly broken:

| Refusal | What it would otherwise cause |
|---|---|
| An unknown tool | A question that looks like a research gap forever. |
| A calculation the engine cannot produce | A blocking question nothing can close. |
| An evidence class that is not an access class | A requirement no governance check understands. |
| A **blocking** question naming no tools | Every run of the playbook stops, and the symptom looks like a coverage problem rather than a declaration error. |
| A specialist nobody implements | A run with a silently missing perspective. |
| A completion rule the loop cannot evaluate | Every run exhausts its budget, and the symptom is a budget limit rather than a configuration error. |

The last one is a promise in both directions, and a test enforces it: every member of
`EVALUABLE_COMPLETION_RULES` must appear in the loop's own `_rules_satisfied`.

### The ambiguity that needed resolving — ADR-054

`INDUSTRY_PLAYBOOK_ARCHITECTURE.md` §6 says *"questions union; completion_rules intersect
(the strictest wins)"*. Those two clauses point opposite ways: intersecting the rule
**sets** keeps only what the playbooks share, which makes a conglomerate **easier** to
declare complete than either of its parts — the outcome the sentence's own justification
says to avoid.

Resolved in favour of the intent: **every rule of every applicable playbook must hold.**
What is intersected is the set of *states that count as complete*, and that intersection is
produced by unioning the rules.

### Selection must not guess

A company the platform cannot classify gets **no** playbook and a recorded reason, never
the nearest-looking one. Applying a bank's methodology to an industrial produces a
confident analysis of the wrong things, and the wrongness is invisible because every
question got an answer. The run then uses the Director's baseline — a generic methodology
honestly labelled as one.

Matching is on **any** declared dimension, not all: a company whose sector is known and
whose industry is not should still get its sector's playbook. The failure direction is
applying a methodology too broadly, which produces extra questions.

## New modules

`app/services/playbooks/schema.py`, `app/services/playbooks/registry.py`,

## Existing modules reused

`agent_tools.contracts.TOOL_NAMES`, `calculations.definitions.DEFINITIONS`,
`corpus.policy.ACCESS_CLASSES`, `director.roles.ROLES` — every vocabulary a playbook can
name is one that already exists, which is what makes the refusals possible.

## DB migration        no. A playbook is configuration; the run record already pins its
                      version through `research_runs.playbook_versions_json`.
## Infrastructure      no
## Provider dependency none
## Feature flags       none new

## Security considerations

A playbook is code in this repository, reviewed like code. It cannot introduce a tool, a
role or a completion rule — only *select from* vocabularies that already exist — so a
playbook cannot widen what an agent may do.

## Unit tests

The six constructor refusals; a real calculation accepted; matching on any dimension and
folding case; an unclassifiable company getting nothing **with a reason**; every applicable
playbook returned; **completion rules unioned** so a conglomerate is harder rather than
easier; explicit naming; two methodologies unable to share a version; a new version
replacing the old; the selection recording what a report must state; a playbook satisfying
the Director's Protocol end to end; and that only a playbook can originate a blocking
question.

## Integration tests

None. No schema change and no I/O.

## Live issuer acceptance

Not performed. 6.2 ships the five real playbooks and the differentiation test.

## Acceptance criteria

1. A playbook naming anything that does not exist cannot be constructed.
2. Two applicable playbooks produce the **union** of their questions and the **union** of
   their completion rules, so a conglomerate is harder to complete than either part.
3. An unclassifiable company yields no playbook and a recorded reason.

## Non-goals

- The playbooks themselves. 6.2, deliberately separate: this slice's acceptance is about
  the *schema's refusals*, and shipping content alongside would make a red test ambiguous
  between the two.
- Classifying a company. The existing sector classifier supplies `sector`/`industry`;
  business-model signals are a caller's input.
- Sector-specific data sources (ClinicalTrials.gov, central-bank statistics). Each is a
  connector with its own health check, rate limit and honest gap — and the platform
  already learned the expensive way that four half-wired sources beat none.

## Rollback

Delete the package. Nothing imports it at runtime.
