## Objective

Persist enough parsed structure that a later question about a document is
answered from the corpus rather than by a re-fetch: the full text of every page
the extractor opened, its heading structure, its tables **as grids**, and exact
offsets back to the raw artifact.

## Why now

Slice 1.1 keeps the bytes; slice 1.2 knows what document they are. This is where
the corpus stops being a lineage record and starts being a corpus. Today a
169-page annual report is fetched, ~20 excerpts of ≤1,200 characters survive, and
the document is functionally gone.

## Why the derivation layer exists

A version is a *retrieval* and is immutable. What a parser made of it is not: the
pipeline version is at 15, and versions 9-15 each changed how already-fetched
text is read. Hanging pages off the version would mean improving a parser
silently rewrites the record of what was retrieved, and "what did we believe this
document said, under version 13?" would be unanswerable.

So each parse is its own row, stamped with its pipeline version. Exactly one is
`is_active` — a partial unique index, verified against real PostgreSQL — and the
others are kept. That is `ExtractedFact.is_active`'s supersession philosophy
raised one level, and it makes Slice 1.7's reprocessing non-destructive by
construction rather than by discipline.

## Two design decisions worth stating

**The full text is derived, not stored twice.** A derivation's full text is the
ordered concatenation of its pages joined by `\n`; pages and sections carry
offsets into exactly that. So the document reconstructs byte-for-byte, any span is
locatable, and half a megabyte is not stored twice. The join character is a module
constant because changing it would shift every persisted offset by one per page.

**`partial` is the honest common answer.** The live extraction path reads at most
40 pages plus a targeted 12-page supplemental pass. A 169-page annual report
therefore yields 40 of 169 pages, and `status` says `partial` with both numbers
stored. A corpus that could not distinguish "we never read that page" from "that
page does not say it" would be worse than the excerpt model it replaces.

## The defect the real document found

Sections initially took their scope from `fact_scope.parse_scope` applied to the
raw heading. `parse_scope`'s fail-closed rule — *anything non-empty that is not
Group vocabulary is a named segment* — is correct for a string
`_infer_scope` has already vetted, and wrong for a raw heading.

Running the real Pandora Annual Report 2025 through it produced sections scoped
`segment / "CONTENTS"`, `segment / "BIG"`, `segment / "PICTURE"` — a false segment
attribution on a cover page — and, in the other direction, `segment / "Group
results"`, filing a consolidated section under a segment scope.

The fix routes heading scope through the same `infer_heading_scope`
(`_infer_scope`, now publicly aliased) the extractor already applies before it
puts a scope on a table: a heading that carries no scope vocabulary yields
**no scope at all**, and unknown stays unknown. Re-run on the same document: 0
false segments. Both directions are pinned by test.

This is the pattern the acceptance strategy predicts and the repository's history
keeps confirming — the defect was invisible to fixtures and obvious on one real
document.

## Acceptance criteria

1. **A real annual report ingests to pages and sections, holding far more than
   the excerpt model.** ✅ 40 pages / 108,000 chars / 34 sections from the real
   PNDORA document — 5.6× the text V2 would have kept.
2. **Provenance is exact and reprocessing needs no re-fetch.** ✅ every page
   offset exact; bytes recovered by hash alone; re-parse identical.
3. **A `DocumentTable` survives a borderless five-year summary.** ✅ recorded
   above, on real data, with the column→period map intact.
4. **A partial parse says partial.** ✅ 40 of 169, `status=partial`, both numbers
   stored.
5. **No V2 regression.** ✅ suite 4788 → **4825 passed**, 12 skipped; `ruff`
   clean; `mypy app` 71 (unchanged, same scope). Block capture is off by default
   and the V2 extraction output is asserted byte-identical with it on.

## Non-goals

- Chunking and indexing (Slice 1.5) — a page is not a retrieval unit.
- Search (1.4-1.6).
- Actually re-extracting under a new parser (Slice 1.7). The lifecycle
  *representation* lands here; the driver lands there.
- Raising the 40-page extraction cap. That is a live-path budget decision with a
  worker-timeout invariant attached, and the honest answer is that reprocessing
  runs off the live path from the retained bytes.
- Removing `excerpts_json`. It stays as the compatibility path for documents not
  yet reprocessed.
