# V3.1 Slice 1.7 — Re-extraction and the parser-version lifecycle

**Branch:** `feature/v3-1-7-reprocessing-lifecycle` → `develop/v3`
**Status:** `IMPLEMENTED`, with a **real-document lifecycle run** recorded.
**Migration:** 025 (created; **not applied to any deployed environment**)

## Objective

Close the loop the retained bytes exist for:

```
raw artifact → parser N → parsed representation
             → parser N+1 (or a larger budget)
             → deterministic reprocessing, from the STORED bytes
             → prior derivation retained and auditable
             → new active representation, reindexed
```

## Why now

This is the payoff for Slice 1.1. `CURRENT_EXTRACTION_PIPELINE_VERSION` is at 15,
and versions 9-15 each changed how already-fetched text is read — a two-column
layout fix, a geometric table rebuilder, a gutter-threshold recalibration, a
larger extraction budget. Applying each one meant re-fetching documents from
issuer sites that reorganise, that serve annual reports from a CDN behind
extension-less URLs, and that eventually stop serving the 2019 edition at all.

Slice 1.6 also left a concrete gap: the corpus held pages 1-40 of a 169-page
annual report, so a query for "cash flow from operations" returned the contents
page. Closing that is this slice.

## DB migration

**Yes — 025.** Adds `extraction_profile` to `research_document_derivations` and
widens the unique index to `(version, pipeline_version, extraction_profile)`.

### Why a schema change was needed

The derivation recorded which parser ran, not **how much of the document that
parser was allowed to read** — and on the live path the answer is 40 pages of 169.
Without that column, re-running the same parser under a larger budget would find
the existing derivation on `(version, pipeline_version)` and skip. The document
would stay at a quarter of itself forever, and the argument for retaining raw
bytes would go unrealised.

`extraction_pipeline_version`'s own note says a change to an extraction cap or
budget that lets the extractor reach content it previously never read makes a row
genuinely **incomplete** rather than merely under-interpreted. This column is that
statement made durable per row, instead of requiring a global version bump every
time a budget differs.

**`NOT NULL` is safe here and that is not the general rule.** The additive-only
rule exists so `release/v2-current` runs unchanged against a migrated database.
`research_document_derivations` does not exist in V2 — migration 023 created it,
on this branch, applied nowhere — so no V2 code path can be affected, and the
server default populates any row that could exist.

## The two profiles

| Profile | Caps | Where it runs |
|---|---|---|
| `live` | `primary_document_max_pdf_pages` (40) + a targeted 12-page pass | The request path. Bounded by the deployed gunicorn worker timeout. |
| `deep` | `v3_corpus_reprocess_max_pdf_pages`, `v3_corpus_reprocess_timeout_seconds` | A reprocessing run, from the retained bytes, off the request path. |

`deep` is a **separate setting rather than a raise** of the live one. The live cap
is bounded by the deployed worker timeout, those two drifted apart once and it
cost six live outages; raising it would put every request back under that risk. A
reprocessing run has no request waiting on it and no heartbeat at stake. A test
asserts `deep` raises only those two caps and leaves the byte cap, the
content-type gate and the decompression-bomb guard untouched — none of them
stopped the extractor at page 40, and all of them exist for reasons reprocessing
does not change.

## Four refusals

**Never fetch.** No bytes, no reprocessing — outcome `skipped_no_bytes`. A
maintenance job that reaches the network is one that can be rate-limited, blocked,
or noticed by an issuer.

**Never trust the store.** The re-read bytes are re-hashed against the version's
`content_hash`. A store returning the wrong object would otherwise attach one
document's citations to another's text, silently, and to every fact derived from
it.

**Never destroy a prior derivation.** Its pages, sections, tables and chunks all
stay. Only `is_active` moves. "What did this document say under version 13"
remains answerable — the difference between a corrective and a rewrite.

**Never roll backwards.** Precedence is `(pipeline_version, pages_persisted)`: a
newer parser always wins, and at the same parser more of the document wins. A
failed or empty re-parse never supersedes a derivation with content, so a
regression in a new parser cannot silently empty the corpus.

## The bug the real document found

A deep reprocess of the real 169-page annual report failed with
`UNIQUE constraint failed: research_document_chunks.chunk_id`.

`chunk_identity` keyed on `(version, pipeline_version, kind, ordinal, offsets,
table_location)` — not on the profile. A deep parse **re-reads the same leading
pages**, so its first chunks had the same ordinal and the same offset range as the
live parse's and hashed to the same id: two derivations, one chunk id.

The fix adds `extraction_profile` to the key, which is also the semantically
correct answer — a different profile is a different reading of the document,
exactly as a different pipeline version is. Two tests now pin it: the identities
differ across profiles, and two derivations of one version can both hold chunks
with disjoint id sets.

It took a real document. The unit suite had exercised the deep profile through
`needs_reprocessing` and through a derivation that was persisted but never
chunked, so nothing had ever written two derivations' chunks for one version.

## Security considerations

- Reprocessing makes **no network call** — asserted by
  `test_reprocessing_never_fetches`, and structurally true because the only byte
  source is `load_artifact_bytes`.
- The content-hash check is applied twice (in `load_artifact_bytes` and again in
  `reprocess_version`), because the cost of being wrong is one document's
  citations pointing at another document's text.
- Every outcome is a member of a closed vocabulary, safe to persist and to show an
  operator; a raising parser is an outcome, not a crash.
- **Nothing schedules a reprocess.** Re-extracting a corpus is minutes of CPU per
  document and belongs to whoever decided a parser improved, not to the first
  request after a deploy. A test scans the tree to keep it that way.

## Real-document lifecycle run

`scripts/v3-corpus-acceptance.py --deep-pages 400`, on the same real Pandora
Annual Report 2025 (25.9 MB, 169 pages, fetched through the guarded fetcher):

```
=== 6b. DEEP reprocess from the retained bytes ===
  reprocess    27.8s outcome=reprocessed profile=deep
  pages      40 -> 169 of 169
  chunks     113 -> 602; reindexed 602
  superseded ba17fa09-... (kept, not deleted)
  the citation recorded BEFORE reprocessing still resolves: True
```

And the queries that the 40-page window could not answer:

| Query | Before (live, 40 pages) | After (deep, 169 pages) |
|---|---|---|
| `cash flow from operations` | the contents page | **p. 138, financial statements** |
| `gross margin` | a management-review page | **table `p109:t1`** — `Revenue \| 24,235 \| 8,314 \| 32,549`, `Cost of sales \| -5,368 \| -1,434 \| -6,802` |
| `segment information` | — | **p. 110, "NOTE 2.1 SEGMENT AND REVENUE INFORMATION"** |

Retained text across the three representations of the same document:

| | text kept | chunks | tables | tables with a period map |
|---|---|---|---|---|
| V2 excerpts | 19,232 chars | — | — | — |
| V3 live derivation | 108,000 chars | 113 | 10 | 2 |
| V3 deep derivation | **471,780 chars** | **602** | **177** | **46** |

**24.5× the text the excerpt model kept**, and no re-fetch: every byte came from
the artifact store.

### Two honest findings from the run

**`status` stays `partial` even at 169 of 169 pages.** `extract_pdf` sets
`truncated` when the input exceeds `primary_document_max_download_bytes` (8 MB),
while the fetch layer actually caps at `source_document_extraction_max_bytes`
(35 MB) — so a 25.9 MB document is flagged truncated by a bound that was never
applied to it. That is a **pre-existing V2 inconsistency**, not something this
slice introduced, and the conservative direction is the safe one: the derivation
under-claims completeness while storing `pages_persisted=169, page_count=169` so a
reader can see the truth. Reconciling the two byte caps is a V2-behaviour change
and belongs in its own slice.

**Heading-derived section scope resolves to nothing on this issuer's PDF**, in
both the live and the deep parse (0 of 34, and 0 of 72). Pandora's headings are
"REPORT > PHOENIX", not "Segment information", so the vocabulary correctly finds
no scope signal. Scope filtering for this document therefore rests on table scope
(where it does resolve) and on fact-level scope, not on section scope. That is the
fail-closed behaviour working as designed — before Slice 1.3's fix those same
headings were being labelled *business segments* — but it is worth recording that
section-level scope filtering will be thin for issuers whose PDFs are laid out
this way.

## Acceptance criteria

1. **A parser improvement reprocesses from stored bytes, with no fetch.** ✅
   `test_reprocessing_never_fetches`, and 40 → 169 pages on the real document.
2. **Prior derivations are retained and auditable.** ✅
   `test_a_newer_parser_supersedes_and_the_old_reading_survives` — old pages and
   chunks intact — and the real run's "the citation recorded BEFORE reprocessing
   still resolves: True".
3. **Reprocessing is deterministic.** ✅ `test_reprocessing_is_deterministic`;
   same bytes and profile reproduce identical chunk ids and text.
4. **The corpus cannot roll backwards.** ✅
   `test_a_smaller_reprocess_never_rolls_the_corpus_backwards`,
   `test_an_empty_reparse_never_supersedes_a_derivation_with_content`.
5. **No V2 regression.** ✅ suite 4919 → **4949 passed**, 12 skipped; `ruff`
   clean; `mypy app` 71 (unchanged, same scope). `v3_corpus_reprocess_max_pdf_pages`
   defaults to 0, so no deep profile exists unless configured, and the live caps
   are never mutated.

## Non-goals

- Scheduling. Deliberately absent, and a test keeps it absent.
- Running reprocessing on the durable worker (V3.0's job store would host it, but
  wiring a job type is its own slice).
- Reconciling the two byte caps (see the finding above).
- OCR reprocessing. A scanned document that OCR could now read is a real candidate
  and needs the OCR budget threaded through the profile; out of scope here.

## Rollback

Nothing calls reprocessing, so a revert is inert.
