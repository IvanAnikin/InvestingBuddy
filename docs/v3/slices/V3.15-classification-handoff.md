# V3.15 — The classification handoff

**Status:** implemented, awaiting production acceptance
**Branch:** `feature/v3-classification-sic-handoff`
**Migration:** 039 (additive, four nullable columns on `companies`)
**Baseline:** `0a25162` (main / API / web), Alembic head 038

---

## The defect

Every V3 run of every company used the generic methodology. Not because the platform
could not classify companies — because nothing carried the classification from the layer
that produced it to the layer that needed it.

For Moderna, all four layers were individually correct:

| Layer | What it had | What happened to it |
|---|---|---|
| SEC submissions API | `sic: "2836"`, `sicDescription: "Biological Products, (No Diagnostic Substances)"` | `sic` parsed into a dict key at `sec_edgar_provider.py:79`, read by nothing |
| `enrich_company_profile` | derived sector `Healthcare`, with a provenance tier | written into the report snapshot; `companies.sector` never touched |
| `sector_taxonomy` | knows `Biotechnology → Healthcare` | never asked |
| `biotech` playbook | declares `industries=("Biotechnology", …)` | matched against a NULL column |

`select_playbooks(sector=company.sector, industry=company.industry)` read two columns
that were NULL for 70 of 71 companies and empty for all 71. It returned `[]` every time,
recorded an honest reason, and the run proceeded with the Director's baseline questions.

This is the fourth instance in this campaign of the same shape: **a correct value
produced and then discarded one layer up.**

---

## The fix

### 1. `app/services/classification/sic.py` — the regulator's code, not its prose

SIC codes are enumerated and published; SIC descriptions are prose. Mapping is keyed on
the **code**, with a small number of ranges as backup, because matching descriptions by
keyword is how "Services-Prepackaged Software" becomes a pharmaceutical.

An unmapped code returns `None`. The table covers the codes that reach a playbook plus
their neighbours; everything else is honestly unknown.

Health services (SIC 8000–8099) map to `Health Care Providers`, deliberately **not**
`Biotechnology` — a hospital group is in healthcare and is not a biotech, and blurring
the two would hand a pre-revenue-pipeline methodology to a company with revenue and no
pipeline.

### 2. `app/services/classification/resolver.py` — one canonical answer

`resolve_classification()` is the single place that decides what industry a company is
in. Precedence is by **provenance**, not by order of arrival:

1. SEC SIC code → `T2_regulator_or_gov`
2. a stored value the canonical taxonomy recognises → its own tier (default `T5`)
3. keyword inference from a description → `T6_model_estimate`, labelled

`enrich_company_profile` now delegates to it, so its private keyword table — the
platform's *third* classification vocabulary, emitting labels nothing downstream matched
on — is gone. Nothing is classified twice.

**Raw and canonical are both kept.** `industry_raw` holds the source's own words and
survives being read back on the next run, so `industry = "Biotechnology"` stays checkable
against the regulator rather than taken on faith.

### 3. `app/services/classification/service.py` — one writer, and a supersede rule

`companies.sector` / `.industry` are written here and nowhere else.

A write happens only when the new answer is at least as well-sourced as the stored one.
The failure this prevents: the SEC is briefly unreachable, the run infers an industry
from a description, and a `T6` guess overwrites a `T2` fact — permanently, because
nothing afterwards knows the row used to be better. Unknown never overwrites known.

Both callers use this function, which is what makes it one handoff rather than a second
classification system beside the first:

* `company_analysis` already holds a fetched SEC profile and passes it in — no extra
  request;
* `v3_pipeline` holds none, reads what is stored, and fetches only when the row has never
  been classified. **A repeat run asks the SEC nothing.**

### 4. `AppliesTo.matches` — both sides through the same normaliser

The playbooks were written in GICS names (`Health Care`, `Information Technology`); the
platform's taxonomy is canonical (`Healthcare`, `Technology`). Both sides now go through
`sector_taxonomy`, with a fall back to the folded literal so no declaration that worked
before stops working.

**Normalisation does not widen meaning.** `normalize_industry("Healthcare")` is `None`,
so a company known only to be in healthcare cannot acquire the biotechnology *industry*.
It is pinned by a test.

### 5. `CompanyClassification.matching_sector` — a sector is not always grounds for a methodology

`AppliesTo.matches` already stated the intended rule: the sector fallback is for a company
*"whose sector is known and whose industry is **not**"*. Only the first half was ever
implemented. `matching_sector` supplies both halves, and adds one clause:

* **A known industry a playbook does not declare is evidence the playbook does not
  apply.** Alphabet's industry is software; falling back to its Technology sector would
  hand it fab utilisation and node transitions, and every answer would come back
  unanswerable — reading as a coverage problem rather than as the wrong playbook.
* **An estimate is not grounds for a specialist methodology.** A `T6` sector is still
  reported; it is just not load-bearing.

Measured across the 71 companies: **17 sector-only matches → 1.**

## Dry-run over all 71 companies (read-only, `SELECT` only)

`scripts/v3-classification-dry-run.py`. No backfill exists — classification is lazy, on
each company's next run — so this is the review.

```
classified      : 38/71
gets a playbook : 14/71
stays unknown   : 33/71

by playbook            by provenance tier
  semiconductors    8    T2_regulator_or_gov  26
  biotech           6    T6_model_estimate    11
                         T5_api_aggregator     1
                         unclassified         33
```

**13 of the 14 playbook matches come from a `T2` regulator-sourced industry.** Zero come
from an estimate.

The 33 unclassified are 23 non-US issuers (`resolve_cik` refuses non-US exchanges before
making any request — no guessing) and 10 US filers whose SIC has no canonical industry
(`TSLA` 3711, `ALB` 2821, `BWXT` 3510, `POWL` 3613 …). Unknown remains unknown.

### The one residual, and it is pre-existing

`AAPL` is the only company in the database with a stored sector, and it is literally
`"Information Technology"` — the exact string the `semiconductors` playbook declares. It
matched that playbook on `main` before this change (`_fold` equality) and matches it
after. **This is a playbook-declaration question, not a classification one**, and it is
left for a product decision rather than changed here. See "Open" below.

## Migration 039

Four nullable columns on `companies`: `industry_raw`, `sic_code`, `classification_tier`,
`classification_updated_at`. Additive only — no constraint, no index, no backfill, no
default. Every existing row is untouched and NULL correctly means "not yet classified".

## Web

`V3ResearchPanel` gains a Classification block showing the canonical label, the sector,
and the source's own words beside them (`Biotechnology · Healthcare — source says
"Biological Products, (No Diagnostic Substances)" (SIC 2836)`), plus an explicit warning
when the classification is an estimate. `readV3Research` returns `classification: null`
for every report written before this, so old reports render exactly as they did.

The e2e fixture is regenerated **from the producer** (`scripts/v3-dump-real-payload.py`),
against an *unclassified* company row — which is what every production row actually looks
like.

## Migration 039 on real PostgreSQL 16

`upgrade head` (038 → 039) → `downgrade 038` → `upgrade head`, on a scratch database
(`ib_v3_migcheck_039`, UTF8, created and dropped). The downgrade removed exactly the four
columns and the re-upgrade restored them; all four land nullable with the declared
lengths.

**One real defect was found only here.** The savepoint that protects the classification
write rolls back on failure, and rolling back a savepoint EXPIRES the ORM instances it
touched — so `logger.exception("… %s", company.ticker)` in the failure handler issued a
lazy `SELECT`, synchronously, outside the greenlet the async engine needs. The original
`StringDataRightTruncation` was replaced by a `MissingGreenlet` raised from inside the
handler, in the one path whose whole job is to fail quietly. Fixed by reading the ticker
before the savepoint. SQLite never showed it.

`tests/test_v3_pipeline_postgres_integrity.py::TestClassificationOnRealPostgres` pins
both halves: the write round-trips, and a failed write leaves the transaction usable —
`except Exception` cannot un-abort a PostgreSQL transaction, which is what destroyed a
report earlier in this campaign.

## Signals

Production passes **no** business-model signals — `v3_pipeline` calls `select_playbooks`
with sector and industry only, and nothing sets `pre_revenue`, `pipeline_driven` or the
rest. Two tests document this: one proves every family selects correctly from
classification alone, and one reads the production call site so the claim is checked
against the code rather than restated.

## CIK

`Company.sec_cik` was **not** added. `company_analysis.py:341` and `:1870` pass
`getattr(company, "sec_cik", None)` against a model that has no such attribute, so that
argument has always been `None`; adding a column to make a dead read live would be
inventing a requirement from a typo. CIK is resolved at runtime by
`SecEdgarFundamentalsProvider.resolve_cik`, and the resulting `sic_code` is persisted so
it is resolved once per company rather than once per run.

## Open — for a product decision, not fixed here

1. **`semiconductors` declares `sectors=("Information Technology",)`.** Any company
   classified into technology with no industry matches it. Today that is `AAPL` alone.
   Narrowing the declaration to its industry list would remove the last sector-only
   match.
2. **`biotech` declares `sectors=("Health Care",)`.** A hospital operator would match it
   on the sector arm. No company in the database is affected today.
3. **Duplicate company rows** — `AAPL`/`AAPL.US`, `CFR.SW` on three exchanges,
   `MONC.MI` twice, `PNDORA`/`PNDORA.CO`. Data hygiene, unrelated to this slice.
4. **`_fetch_sec_classification` constructs a new `SecEdgarFundamentalsProvider` per
   call**, so `company_tickers.json` is re-downloaded for each first-time classification.
   Bounded (once per company, ever) but worth a shared instance if classification ever
   runs in bulk.
5. **`company_analysis.py:341` and `:1870` read `company.sec_cik`, which does not
   exist.** Left as-is deliberately (see "CIK" above). Worth deleting in a cleanup pass;
   worth *not* satisfying with a column.
