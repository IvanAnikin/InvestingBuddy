# V3.3 Slice 3.2 — Fact and series tools

**Branch:** `feature/v3-3-2-fact-and-series-tools` · **Merge target:** `develop/v3` only
**Migration:** no · **Infrastructure:** no · **Provider dependency:** none
**Feature flag:** `V3_AGENT_TOOLS_ENABLED` (default **off**, shared with 3.1)

## Objective

`get_financial_facts`, `get_financial_series` and `get_segment_facts` on the machinery
slice 3.1 landed — the first tools that hand an agent **numbers**, which is where
getting the semantics wrong stops being a usability problem and starts being a wrong
figure in a memo.

## Why this slice is entirely about refusals

The machinery is done. `extracted_facts` already exists, already has
`is_active` (017) and already has the typed scope triple (018). So the work is not
querying — it is deciding **what a fact tool is allowed to return**, and every trap is
already documented in this repository's incident history:

- **A number without its period, scope, unit, currency and scale is not citable.**
  All five travel with every fact, from the vocabularies that already own them
  (`ReportingPeriod`, `FactScope`) rather than a second shape invented here.
- **Annual ≠ interim.** A series is the easiest place in the platform to mix them and
  produce something that *looks* continuous. `ReportingPeriod.comparable_with` already
  refuses cross-type comparison; `get_financial_series` therefore **requires** a
  `period_type` argument. There is no default, because a default is what silently
  mixed them before.
- **Group ≠ segment, and unknown ≠ Group.** `scope` is also **required**, with four
  explicit values (`group` / `segment` / `unknown` / `any`). The report layer has a
  legacy convention that treats an absent scope as implicitly Group; a *tool* applying
  that convention would hand an agent a Watchmakers figure labelled Group, which is
  the CFR failure the whole scope triple exists to prevent. So a `group` request
  returns `scope_type = 'group'` rows and nothing else.
- **`is_active` is not optional.** It exists because a superseded derivation was being
  mixed with a current one as evidence. A tool ignoring it resurrects a stale figure.
- **`validation_status` must be `validated`.** `excerpt_only` is retained text, not a
  figure; returning it as a fact is fabrication with a database behind it.
- **A count names its population.** Every result carries a `population` block: the
  filters applied, and what was excluded and why. The rule is not to make numbers
  agree — it is to say which population each number counts
  (`fact_count_scopes.py`).

## Proposed changes

### New module

`app/services/agent_tools/facts.py` — the three tool specs, their argument validators
and a shared `FactView` projection.

### `FactView` — the citable shape

```
label · value_numeric · value_text · unit · currency · scale
period_key · period_type · period_label
scope_type · scope_name · scope_key
document_id · page_number · table_location
confidence · needs_human_review
```

`value_text` is the raw as-found string and travels beside the number, so an agent
citing a figure can quote what the document actually printed rather than this
platform's normalisation of it.

### `get_financial_series` refuses more than it returns

- `period_type` required; rows of any other type are excluded and counted.
- Unknown-period rows are **excluded from a series** — a series is an ordering, and an
  unknown period cannot be ordered — and the count is reported.
- Rows are ordered by `ReportingPeriod.sort_key` *within* the requested type, which is
  the only ordering that module permits.
- Two rows for one period is a **conflict**, not a series point: both are returned
  under `conflicts` and neither is silently dropped. MRNA has 8 genuine numeric
  conflicts, and a guard that suppresses them all is broken, not safe.

### `get_segment_facts` groups by scope, never by name

Grouping is on `scope_key` (the `FactScope` identity), so `"Specialist Watchmakers"`
and `"SPECIALIST WATCHMAKERS"` are one group and the distinct as-printed
`scope_name`s are preserved inside it.

## Unit tests

- Every fact carries all five semantic fields, and `value_text` beside the number.
- `excerpt_only`, `rejected` and `is_active = False` rows are never returned.
- A `group` request does **not** return unknown-scope rows; `unknown` returns only
  those; `any` returns all and labels each.
- The CFR shape: a Watchmakers segment fact never appears in a Group result.
- `get_financial_series` without `period_type` is refused as `invalid_arguments`.
- A series request excludes other period types and unknown periods, and **reports both
  counts**.
- Two facts for one period come back as a conflict, both values present.
- Segment grouping folds casing but keeps the as-printed names.
- Every result's `population` block names its filters.
- All three go through the 3.1 session: undeclared tools are refused, budgets bind,
  and every call is persisted.

## Acceptance criteria

1. **A mixed-period-type series is impossible** — `period_type` is required, other
   types are excluded and counted, and unknown periods never enter an ordering.
2. **A segment figure never comes back from a Group query**, and an unknown-scope fact
   is never labelled Group.
3. **Two facts for one period are a reported conflict**, not a silently chosen value,
   and every result names the population it counted.

## Non-goals

The calculation engine (3.3) — these tools return facts, never derived arithmetic ·
corpus search (3.4) · peer or macro series, which need V3.4's sources · writing or
correcting a fact, which no agent may do.

## What the review pass found

Three, and the first is a genuine correctness bug rather than a hardening gap.

1. **The row limit was applied before the scope filter**, because the filter ran in
   Python after the fetch. A company with 200 Group facts and 5 segment facts, queried
   for segments with `limit=100`, would have returned **zero** segment facts — the limit
   bounded the population *before* the one the caller asked for. The scope and
   `scope_key` predicates now run in SQL, so the limit bounds the requested population.
2. **Making that fix removed the exclusion counts**, since filtered-out rows are simply
   absent from a filtered query — and reporting `0 excluded` would have been a
   fabricated measurement of a population never examined. A separate unlimited census
   query now supplies them, which is the same discipline `consumption` established for
   uninstrumented units.
3. **Conflicting facts were counted as `excluded`.** They are *returned*, under
   `conflicts`, so counting them as absent made `returned + excluded` describe a
   population that never existed — the exact failure `fact_count_scopes` is named
   after. They are now `conflicted`.

A fourth came from a test rather than from reading: the audit row was storing the
**normalised** arguments, so "this agent asked for 10,000 rows" was invisible. It now
stores the arguments **as asked** — which loses nothing, because validation is
deterministic and the applied filters travel in the tool's own `population` block.

`Population` also now reports `filtered_in_query` versus `filtered_after_query`, because
period *cannot* move into SQL: the column holds the document's own label and the key is
derived by `parse_period`, so `"2025"` and `"FY2025"` are one key and two strings. A
period filter therefore runs on an already-truncated set, and the result says so rather
than leaving a reader to discover it.
