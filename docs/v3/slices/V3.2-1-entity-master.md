# V3.2 Slice 2.1 — Entity master

**Branch:** `feature/v3-2-1-entity-master` · **Merge target:** `develop/v3` only
**Migration:** yes (026) · **Infrastructure:** no · **Provider dependency:** none
**Feature flag:** `V3_ENTITY_MASTER_ENABLED` (default **off**)

## Objective

Give the platform durable legal-entity, security and listing identity, with
identifiers that are **validated rather than trusted**, so that "which company is
this?" stops being answered by a `(ticker, exchange)` string pair.

`companies` is not touched by this slice. Nothing on any live path writes an entity
row. What ships is the schema, the identifier semantics and a write/read service —
the pieces every later V3.2 slice needs and none of which can be added safely later.

## Why now

`companies` is keyed `UNIQUE (ticker, exchange)`
(`apps/api/app/models/company.py:46`), and the consequences are not hypothetical —
they are in this repository's own incident history:

- `BA` + LSE resolved to **Boeing's** CIK when the issuer was BAE Systems. `MC` + PA
  returned Moelis for LVMH; `EL` + PA returned Estée Lauder for EssilorLuxottica.
  All three were fixed by *special-casing* (`exchange_registry.sec_eligible` plus an
  empty, provenance-gated `sec_issuer_registry`), not by identity.
- CIK, LEI and ISIN exist today only as fields on **ephemeral dataclasses** —
  `ProfileEnrichment` (`app/integrations/company_profile_enrichment.py:121`) and
  `FreeRealSnapshot` — assembled per run and never persisted. The platform relearns
  an issuer's identity on every run and can never be contradicted by what it learned
  last time.
- Cross-listings and ADRs cannot be linked; a ticker change rewrites history.

V3.1 made this the *binding* constraint rather than a parallel concern. Every corpus
document hangs off `companies.id`. A corpus that cannot say which legal entity a
document belongs to will return one issuer's annual report under another's ticker,
and the period/scope filters that make retrieval safe are worth much less without
entity identity underneath them.

## Current implementation

| Path | What it does today |
|---|---|
| `app/models/company.py:46` | `UNIQUE (ticker, exchange)` — the entire identity model. |
| `app/services/exchange_registry.py:41-67` | `ExchangeInfo` already carries `mic`, country, region, currency, `is_us`, `sec_eligible`. **Reused, not duplicated.** |
| `app/integrations/sec_issuer_registry.py:55` | Deliberately empty, provenance-gated ticker+exchange → CIK table. The workaround this slice makes structural. |
| `app/services/identifier_resolver.py` | Resolves user input to an EODHD symbol, in memory, per call. Ambiguity is surfaced but nothing is persisted. |
| `app/integrations/company_profile_enrichment.py:121-127` | `cik` / `lei` / `isin` as transient strings with a source tier and no validation. |

## Proposed changes

### New tables (migration 026, additive only)

```
legal_entities ──< securities ──< security_listings
      │                 │
      │                 └──< entity_identifiers  (isin, figi)
      ├──< entity_identifiers  (lei, cik, company_register)
      └──< entity_aliases      (former legal name, trade name, …)
```

`entity_relationships`, `reporting_scopes` and `business_segments` are **slice 2.4**.
`companies.legal_entity_id` is **slice 2.2**. Resolution is **slice 2.3**.

### Identity keys, and why each table has one

`legal_entities.entity_key` is UNIQUE and derived from the *strongest identifier
available at creation* — `lei:…`, `cik:…`, `register:DK:…`, or `listing:XCSE:PNDORA`
as the last resort. It is the same device `research_documents.document_key` uses, for
the same reason: a name is not an identity, and the two failure directions are not
symmetric. Splitting produces a duplicate entity, which is visible and repairable.
Merging attributes one issuer's filings to another, which is the most dangerous
failure this platform has. **The fallback key therefore deliberately over-splits.**

Keys are **stable**. A stronger identifier arriving later does not rewrite the key —
promoting or merging an entity is an explicit, evidenced operation and it belongs to
slice 2.3.

### Identifiers are validated, not stored on trust

`app/services/entities/identifiers.py` is pure and has no I/O:

| Scheme | Subject | Validation | Normalisation |
|---|---|---|---|
| `lei` | legal entity | 20 chars, ISO 17442 shape, **ISO 7064 MOD 97-10 checksum** | upper |
| `cik` | legal entity | numeric, 1-10 digits, non-zero | zero-padded to 10 |
| `company_register` | legal entity | shape only; **jurisdiction required** | upper, jurisdiction-scoped |
| `isin` | security | 12 chars, ISO 6166 shape, **Luhn check digit over the letter-expanded body** | upper |
| `figi` | security | structural only — 12 chars, `G` at position 3, consonant/digit body. **The check digit is deliberately NOT validated** (see below). | upper |

A checksum-invalid identifier is **refused**, not stored with a low confidence.
A silently stored bad LEI is how one entity's filings end up attributed to another,
and "we recorded it with confidence 0.3" does not stop the next reader from joining
on it.

CUSIP is **not** a recognised scheme. CUSIP is licensed data from CUSIP Global
Services; storing one is a licensing decision, not a technical one, and ISIN covers
the same need for every issuer in the regression set.

### FIGI, and OPEN DECISION #10

[#10](../OPEN_DECISIONS.md#10-openfigi-usage-and-licensing) — whether OpenFIGI is
used — is **user-owned and open**. This slice therefore makes a FIGI *representable*
and does not make it *obtainable*: the scheme validates structurally, no source
populates it, no OpenFIGI client exists, and
`test_no_openfigi_client_exists_yet` fails if one is added. The check digit is not
validated, and the docstring says so in as many words rather than letting a reader
assume a stored FIGI has been verified — implementing a checksum variant that cannot
be confirmed against a published vector would produce a validator that rejects valid
identifiers, which is worse than no validator.

### Uniqueness is enforced by the database

Two things must be impossible, and neither may depend on a writer remembering:

1. **Two legal entities currently holding the same LEI/CIK/ISIN.**
   `ix_entity_identifiers_current_value` UNIQUE on
   `(scheme, value_normalized, scope_key)` `WHERE effective_to IS NULL`.
   `scope_key` is `'*'` for the globally unique registries and the jurisdiction for
   `company_register`. It is **NOT NULL by construction**, because PostgreSQL treats
   NULLs as distinct in a unique index — a nullable jurisdiction column would have
   silently allowed exactly the collision the index exists to prevent.
2. **Two current listings sharing a venue and a ticker.**
   `ix_security_listings_current_venue_ticker` UNIQUE on `(venue_key, ticker)`
   `WHERE effective_to IS NULL`. `venue_key` is the MIC where one exists and the
   `exchange_registry` code otherwise, again NOT NULL for the same reason.

That second index is what retires the Boeing bug at the schema level: `BA` at `XLON`
and `BA` at `XNYS` are two listings of two securities of two legal entities, and
neither can reach the other's CIK, because a CIK is an identifier **of a legal
entity** and is never derived from a ticker string.

## Feature flags

`V3_ENTITY_MASTER_ENABLED`, default **off**. With it off every write in
`app.services.entities.master` returns `None` without issuing a query — the same
contract `v3_corpus_enabled` has. Deprecation plan: removed once slice 2.2's
backfill is validated and `companies.legal_entity_id` is populated for every row.

## Security considerations

- No network, no vendor SDK, no credential. A test parses every module in the
  package and asserts none of them imports `httpx`, `requests` or an SDK.
- Identifier values are external input and are length-clipped and character-checked
  before they reach a query.
- `entity_aliases` is **not** a resolution mechanism. Name matching is precisely how
  two companies get merged wrongly, so an alias is stored as *evidence* for slice
  2.3 to weigh, and nothing in this slice resolves an entity from a name.
- FKs: `securities` → `legal_entities` and `security_listings` → `securities` are
  `CASCADE` because they are composition (a listing without its security is
  meaningless). `entity_identifiers` and `entity_aliases` are `CASCADE` for the same
  reason. No FK anywhere touches `companies`, so nothing about V2 changes.

## Unit tests

`tests/test_v3_entity_master.py`

- LEI: valid checksums accepted; a single-character mutation rejected; wrong length,
  lower case, and non-alphanumeric rejected. **Test vectors are generated by the
  MOD 97-10 generation rule, not transcribed from memory** — an invented "real"
  LEI is exactly the kind of unverified claim this platform refuses elsewhere.
- ISIN: check digit reproduced for four country prefixes; mutation rejected.
- CIK: normalised to ten digits; `0`, non-numeric and over-long refused.
- Scheme/subject: an ISIN cannot attach to a legal entity, a LEI cannot attach to a
  security; `company_register` without a jurisdiction is refused.
- Vocabulary: an unrecognised security type / listing status / alias type raises.
- Flag off: every writer returns `None` and issues no query.
- No network imports in the package.

## Integration tests

Against real PostgreSQL (the existing async-session fixture):

- Two listings on different venues resolve to **one** `LegalEntity`.
- `BA` at `XLON` and `BA` at `XNYS` coexist as separate entities, and neither
  listing's lookup returns the other's entity.
- The same LEI on a second legal entity raises `IntegrityError`; the same LEI
  re-recorded on the *same* entity is idempotent.
- A ticker change: the old listing gets `effective_to`, the new listing is current,
  and the historical listing still resolves for a date in its window.
- `is_primary` on securities and listings is enforced as at-most-one by partial
  unique index, not by the writer.
- `companies` is unaffected: row count and schema identical before and after.

## Acceptance criteria

1. **Two listings, one entity; two entities, no collision.** A cross-listed security
   resolves to a single `LegalEntity` from either venue, and `BA`@`XLON` /
   `BA`@`XNYS` are two entities that cannot reach each other's identifiers.
2. **An invalid identifier is refused, and a duplicate is refused by the database.**
   A LEI failing MOD 97-10 or an ISIN failing Luhn raises rather than storing; two
   different legal entities cannot both currently hold one LEI.
3. **Nothing about V2 changes.** 026 adds five tables and alters nothing; with
   `V3_ENTITY_MASTER_ENABLED` off no entity code issues a query; `companies` is
   untouched; the full gate suite stays green at its recorded baseline.

## Non-goals

Entity *resolution* from a name or a fuzzy match (2.3) · `companies.legal_entity_id`
and the backfill (2.2) · relationships, reporting scopes and segments (2.4) ·
universe generation (2.5) · any identifier *source* — GLEIF, OpenFIGI, SEC — which
is a fetch path and belongs with the resolution slice · merging two entities, which
must be explicit and evidenced.

## Rollback

`git revert` the merge commit on `develop/v3` and run `026 downgrade`. Because the
migration only adds tables, `release/v2-current` code runs unchanged against a
database with it applied, and a database that has it applied loses nothing when it
is removed.

## What the review pass found

The build pass produced working, green code. An independent review of the diff
found four defects in it, and each one is the kind that a test suite written by
the same reasoning would not have caught:

1. **The listing currency was the venue's reporting currency, not the quote unit.**
   `ExchangeInfo.currency` for LSE is `GBP`; LSE main-market equities are *quoted*
   in pence. Defaulting from it would have mislabelled every London price as 100x
   its real pound value — the exact mistake `_PRICE_QUOTE_CURRENCY_OVERRIDES`
   already exists to prevent. Fixed by sourcing from
   `price_quote_currency_for_exchange` and by naming the column `quote_currency`,
   so the next reader cannot assume the other meaning.
2. **`upsert_security` overwrote `security_type` unconditionally.** A caller
   relying on the `ordinary_share` default would silently downgrade an `adr` row,
   and the whole reason the type is named is that per-share arithmetic must refuse
   to run on a depositary receipt without a ratio. Now `None` means "not asserted"
   and an explicit contradiction raises.
3. **`upsert_listing` accepted `delisted` on an open window** — a row that resolves
   as the *current* listing of its ticker while reading as delisted. Now refused,
   pointing at `close_listing`, which requires the date the window closed.
4. **A comment contradicted the code it sat above**, claiming a rename keeps the
   old name when the code adopts the new one. Corrected, and the alias behaviour it
   describes is now pinned by a test.

### The guarantees, exercised with real conflicting INSERTs

Not through the ORM — directly against PostgreSQL, because "the database enforces

| Attempt | Result |
|---|---|
| `BA` on `XLON` **and** `XNYS` | **allowed** — this is the point |
