# V3.5 Slice 5.1 — the Research Ledger

## Objective

Seven tables that replace V2's coordination mechanism with structured state a run can
query, challenge and remember — and one CHECK that makes an unsupported finding
unstorable.

## Why now

Everything else in V3.5 writes to it. The Director produces questions and tasks; the loop
produces findings and gaps; neither has anywhere to put them. And V3.7's Council consumes
it: without the ledger, "Council V2" is the same council with new prompts.

## Current implementation

V2 agents coordinate through a bounded free-text summary of the previous agent
(`council.py:664-704`, `_prior_summaries` / `_compact_agent_line`). That is lossy by
construction and cannot be queried, challenged or remembered. `gaps.py` and
`gap_attribution.py` already produce excellent honest gaps — as **caveats printed in a
report**, not as work items anything consumes.

## Proposed changes

`research_runs` · `research_questions` · `research_tasks` · `research_findings` ·
`research_gaps` · `research_disagreements` · `research_hypotheses`, plus
`app/services/ledger/store.py`.

### The rule the schema enforces

> **A finding without evidence ids or calculation ids is not a finding.**

`ck_research_findings_has_support` refuses the row. There is no "trust me" state, and a
model's confident sentence cannot enter the ledger by any path — including one that
bypasses the service layer.

It reads two **derived integer columns** rather than the JSON arrays beside them, because
a portable CHECK cannot look inside a JSON column and because `record_finding` is the only
writer of both. Drift is made unrepresentable rather than checked for, which is the rule
V3.2 established for exactly this shape of problem.

### Four more sentences the schema refuses to store

| Constraint | The sentence it refuses |
|---|---|
| `ck_research_runs_stopped_names_a_limit` | "This run stopped." Which limit? A run that stopped for an unnamed reason is one nobody can widen a budget for. |
| `ck_research_gaps_closed_names_a_finding` | "That gap is closed." By what? "Closed" with nothing behind it is the gap disappearing rather than being answered. |
| `ck_research_disagreements_resolution_is_explained` | "The sources agree now." How? A resolved conflict with no note is the laundering the Chair rule forbids. |
| `ck_research_disagreements_two_findings` | A finding disagreeing with itself. |

### Two states that exist because collapsing them loses information

- **`ResearchTask.partial`**, which must name what stopped it. A task that ran out of
  budget produced *something*, and reporting it as complete presents a thin answer as a
  finished one.
- **`ResearchGap.accepted`**, distinct from `closed`. The run finished with the gap open
  and said so, which is the honest outcome for a gap no source can close — and
  `closable=False` is what stops the bounded loop spending another round on it.

### The Council's gate

`LedgerSummary.council_may_convene` is False while any blocking question is open or any
gap blocks the Council. The run then reports insufficient evidence instead of analysing
around the hole, which is the whole point of a `blocking` flag existing.

## Existing modules reused

`research_leads` (031) and `calculation_records` (030) are the two id spaces
`evidence_ids` and `calculation_ids` point into. `research_mode.ModeLimits` (4.11) is
where a task's iteration cap and a run's round cap come from — the ledger records them,
it does not invent them.

## Security considerations

- Every text column is length-bounded and clipped, so a runaway model cannot write an
  unbounded row.
- Closed vocabularies throughout: a gap type invented at a call site is one nothing can
  aggregate on, and "which gap class does this platform keep hitting" is a statement about
  the *pipeline* that free text cannot make.
- `CASCADE` from a run to everything in it, deliberately unlike the `SET NULL` used for
  audit rows: a finding belonging to no run is uninterpretable, where a tool-call record
  whose company was deleted is still evidence of what the platform did.

## Unit tests

The support rule from five angles — neither id, one evidence id, a calculation id alone,
blank strings not counting, and the database refusing it independently of the service.
Then: a stopped run naming its limit; a closed gap naming its finding; a resolved
disagreement explaining itself; a finding not disagreeing with itself; a partial task
naming what stopped it; a task with no iteration cap refused; unclosable gaps excluded
from the loop's input; and the Council gate closing on a blocking question and on a
blocking gap.

## Integration tests

Migration 035 against **real PostgreSQL 16**: twelve statements, including that a finding
with no support is unstorable while one with a single calculation id is fine, an
*unresolved* disagreement is storable while an unexplained *resolved* one is not, and
deleting a run takes the whole ledger with it.

## Live issuer acceptance

Not performed. Nothing writes to the ledger yet; 5.2 and 5.3 are its first writers.

## Acceptance criteria

1. A finding with neither an evidence id nor a calculation id cannot be persisted — in
   Python **and** in SQL.
2. A stopped run, a closed gap and a resolved disagreement each name what justifies them,
   enforced by the database.
3. A blocking question or a Council-blocking gap makes `council_may_convene` False.

## Non-goals

- Writing to it. 5.2 (the Director) and 5.3 (the loop) are the first writers.
- Rendering it. The report layer reads the ledger in V3.7.
- Cross-run memory. `ResearchDelta` is V3.8; this slice is one run's state.

## Rollback

Migration 035 downgrades cleanly — verified by dropping and re-adding all seven tables
against real PostgreSQL. Nothing imports the store at runtime.

## Dependencies

V3.3.3 (`calculation_records`), V3.4.4 (`research_leads`), V3.4.11 (`ModeLimits`).
