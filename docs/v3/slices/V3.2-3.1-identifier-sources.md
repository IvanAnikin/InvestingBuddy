# V3.2 Slice 2.3.1 — Identifier sources

**Branch:** `feature/v3-2-3-1-identifier-sources` · **Merge target:** `develop/v3` only
**Migration:** no · **Infrastructure:** no · **Provider dependency:** GLEIF, SEC EDGAR (both free, both already live in V2)
**Feature flag:** `V3_ENTITY_MASTER_ENABLED` (default **off**) · live calls additionally opt-in

## Objective

Wire the two identifier registries the platform already talks to — GLEIF for LEI,
SEC EDGAR for CIK — behind the `IdentifierSource` contract slice 2.3 defined, so a
`listing:`-keyed entity can acquire real identity.

Plus the orchestration: `promote_entity_identity(...)`, which puts every claim
through the 2.3 gate and returns what was recorded and what was refused.

## Why now

2.3 shipped the contract, the gate and a static reference implementation, and
deliberately shipped no live adapter. Without one, every entity stays keyed
`listing:<venue>:<ticker>` forever and the resolver's decisive-evidence path is
unreachable in practice — GLEIF and SEC are the only free sources of the
identifiers that path needs.

## An architecture amendment, and the evidence that forces it

**`IdentifierSource.lookup` now returns `SourceLookupResult`, not
`list[IdentifierClaim]`.** This changes an interface merged one slice ago, so the
reason is recorded rather than assumed.

GLEIF's name search (`filter[entity.legalName]`) is a **partial match**. Searching
"Pandora" returns every LEI record whose legal name contains it. A source that can
only return a list has exactly two options for that outcome, and both are wrong:

- return every candidate as a claim — and `verify_identifier_claim` will accept the
  first one whose LEI is unheld, because the gate can detect a LEI *already held by
  someone else* and cannot detect a LEI that belongs to a company nobody has
  ingested. That is a silent misattribution of an entire filing history.
- return nothing — and the caller cannot tell "no such entity" from "several, and I
  refused to choose", which is the same ambiguous/unresolved collapse slice 2.3
  exists to prevent.

So a lookup returns claims **and** withheld findings with reasons:

```python
@dataclass
class SourceLookupResult:
    source_id: str
    claims: list[IdentifierClaim]
    withheld: list[WithheldFinding]   # reason + detail
    notes: list[str]
```

`WITHHELD_AMBIGUOUS_NAME_MATCH` is the one this slice exists to express. The
blast radius is small — nothing outside `entities` consumed the protocol yet — and
`StaticIdentifierSource` and the 2.3 tests move with it.

## Proposed changes

### `GleifIdentifierSource`

| Input | Behaviour |
|---|---|
| A known LEI | Confirm it against `/lei-records/{lei}`. A 404 is `WITHHELD_NOT_FOUND`, not a claim. Confidence **1.0** — the registry confirmed its own identifier. |
| A legal name, **one** hit whose folded legal name equals the query's | One LEI claim, confidence **0.9**. Not 1.0: an exact string match on a name is still a name. |
| A legal name, one hit that only *contains* the query | **Withheld**, `WITHHELD_PARTIAL_NAME_MATCH`. |
| A legal name, **several** hits | **Withheld**, `WITHHELD_AMBIGUOUS_NAME_MATCH`, listing what it found. |
| A ticker only | **Withheld**, `WITHHELD_NOT_SUPPORTED` — GLEIF is jurisdiction-based and has no ticker index. Guessing a name from a ticker is how `BA` becomes Boeing. |

### `SecIdentifierSource`

Wraps the existing `resolve_cik(ticker, exchange)`, which already refuses a
non-SEC-eligible venue **before any network call** and already prefers a verified
`sec_issuer_registry` mapping. A refusal becomes
`WITHHELD_VENUE_NOT_SEC_ELIGIBLE`.

The 2.3 gate re-checks the venue independently. That duplication is deliberate
defence in depth: the provider checks the venue *it was asked about*, the gate
checks the venues *the entity actually has*, and those are not the same question
for a cross-listed issuer.

### `promote_entity_identity(...)`

Pure orchestration, in `app/services/entities/promotion.py`: takes a sequence of
sources, a query and an entity, and returns a `PromotionReport` with accepted
identifiers, rejected claims **with their reasons**, and everything the sources
withheld. It never merges, never rewrites `entity_key`, and never treats a source
as more trustworthy than a caller.

### Where the adapters live, and why not in `entities/`

`app/integrations/entity_identifier_sources.py`. The 2.1 test that parses every
module in `app/services/entities/` and refuses a network import is not an obstacle
to work around — it is the design. The package holds semantics; `integrations`
holds clients; the protocol crosses the boundary in the safe direction.

### Live calls are opt-in and never in the unit suite

Every adapter takes an **injected provider**, duck-typed, so the unit suite drives
it with a fake that makes no network call — the same shape as the corpus artifact
store's injected client factory. A live contract test is marked `integration` and
gated on `ENABLE_INTEGRATION_TESTS`, following `config.py`'s existing pattern. Both
registries are free and unauthenticated, so there is no spend to approve; there is
still a rate limit to respect, which is why nothing calls them in a loop.

## Unit tests

- Each GLEIF outcome above, from fixture payloads through the **real**
  `_parse_gleif_record`, so the parsing is not re-implemented in a mock.
- A multi-hit name search yields **zero claims** and one withheld finding.
- A ticker-only GLEIF query yields zero claims.
- SEC: a US ticker yields a CIK claim; an LSE ticker is withheld and **no network
  call is attempted** (asserted on the fake).
- `promote_entity_identity` records the accepted claim, keeps the rejected one with
  its reason, and does not rewrite `entity_key`.
- A source that raises is contained: the report records it and the other sources
  still run.
- With the flag off, nothing is recorded and no source is called.
- The "no network import in `app/services/entities/`" test still passes.

## Acceptance criteria

1. **An ambiguous name match produces no claim and a stated reason** — the outcome
   that makes the amendment necessary.
2. **A CIK is never claimed for a non-SEC-eligible venue**, and the provider is not
   even called; the gate refuses it independently as well.
3. **A promoted entity gains an identifier and keeps its `entity_key`**, and the
   report distinguishes accepted, rejected-with-reason and withheld.

## Non-goals

OpenFIGI ([OPEN DECISION #10](../OPEN_DECISIONS.md#10-openfigi-usage-and-licensing),
user-owned) · ISIN sourcing, which needs an issuer document rather than a registry ·
scheduling or batch promotion of the whole universe, which is a job type and belongs
after V3.3 · merging two entities · fuzzy name matching, which this slice explicitly
refuses to add.

## Rollback

`git revert` the merge. No migration.

## What the review pass found

Two, both about a guarantee that was weaker than it looked.

1. **The venue rule was matched on an exception's *name*.**
   `type(exc).__name__ == "SecExchangeNotSupportedError"` reads as robust and fails
   soft: rename the class and the branch stops firing, the next clause catches it as
   a plain `ValueError`, and `venue_not_sec_eligible` silently degrades into
   `not_found` — losing exactly the distinction the Boeing bug taught this platform
   to keep. The adapter now imports and catches the **real class**, which it can do
   because it lives in `integrations` where a client import is fine. The test fake
   raises the real class too, so the adapter's `except` clause is the thing under
   test rather than a string comparison that happens to agree with it.
2. **`promote_entity_identity` ended with an `assert`** claiming to guarantee that
   `entity_key` was not rewritten. `assert` is stripped by `-O`, and the function
   never assigns the field anyway, so it was documentation wearing a guarantee's
   clothes. Removed, with the reasoning kept as a comment and the property pinned by
   a test.

## Verification performed

No migration. No live network call anywhere in the suite — both adapters take their
provider injected and every test drives a fake, so these proofs do not depend on a
registry's uptime.
