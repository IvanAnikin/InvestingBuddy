## Objective

Route `POST /api/v1/company-research/jobs` — the product's front door — through
the durable job contract behind `V3_DURABLE_JOBS_ENABLED`, without a reader
noticing anything except two terminal states that could not exist before.

## Why now

Slices 1, 2 and 2.1 built a job record, a state machine, a store and a worker,
and wired none of them to anything. Until an entry point uses them, `research_jobs`
is a table nobody writes and the six `BackgroundTasks` call sites are still the
only way research runs.

## Design decisions worth stating

### Two records, and the lifecycle always wins

A durable job is a `research_jobs` row. The reader-facing *content* — company,
provider, stages reached, the report, warnings — stays in the `AgentRun`/
`AgentStep` envelope V2 already writes, linked by `research_jobs.agent_run_id`.

The split is not incidental. The job row is contended for by workers and
rewritten on every heartbeat; the envelope is an audit record written once per
stage. Putting lease churn on the audit trail is the wrong shape, and merging
them would mean rewriting every existing reader.

A poll composes one envelope from both, and the **job row wins every lifecycle
field**. That is what makes the two unable to disagree: the envelope is never
asked for the status, so it cannot claim a job is running that the contract has
dead-lettered. `test_the_lifecycle_wins_over_the_content_record` corrupts the
content record on purpose and asserts the reader still sees the truth.

### A transient failure does not stamp the envelope `failed`

On the V2 path every failure writes a terminal `failed` envelope, because
nothing else is going to — the background task is the last thing that knows. On
the durable path the contract owns that decision, and a retry may well be about
to succeed. A `failed` envelope beside a `pending` job row is a job
contradicting its own state, which is the defect class this repository has paid
for repeatedly.

### `interrupted` got more precise, and had to

V2 derived `interrupted` from a lapsed lease alone, because V2 had nothing that
reclaimed — every lapsed job genuinely meant "nobody is coming, act". That is no
longer true. A lapsed lease with attempts remaining now reads as `pending`:
a worker will reclaim it, the reader need do nothing, and — concretely — the UI
treats `interrupted` as terminal, so the old rule would have stopped polling a
job that was about to produce a report. `interrupted` is now reserved for the
case where nothing is coming.

This changed two Slice 1 assertions. They asserted the rule as written before
anything reclaimed; the rule, not the tests, was what the new capability made
incomplete. Both cases are now pinned explicitly.

### The two new statuses reach the frontend rather than being hidden

Folding `dead_letter` and `cancelled` into `failed` was considered and rejected:
a dead-lettered run hit transient errors and may well succeed later, a failed one
hit a permanent error and will not, and that is exactly the distinction that
decides whether re-running is worth the research budget. Hiding them would also
have been *worse* than doing nothing, because the frontend stops polling on
anything outside `{pending, running}` and renders an outcome only for statuses in
its terminal set — an unknown status leaves a finished job showing a spinner that
had already given up.

### The in-process worker is honest about what it does and does not fix

`V3_JOB_WORKER_IN_PROCESS` defaults to `True` because a separate worker App
Service costs money nobody has approved ([OPEN DECISION #2](../OPEN_DECISIONS.md#2-service-bus-worker-topology)).
An in-process worker delivers the property this phase exists for — the job row
survives a recycle and the next process reclaims it automatically — but it does
**not** move CPU-heavy extraction out of the API process. Setting the flag to
`false` and running `python -m app.services.jobs.worker` elsewhere does, with no
code change. That is stated in the setting's own comment rather than left for a
reader to discover.

## Feature flags

`v3_durable_jobs_enabled` (default `False`) now gates a real code path for the
first time. `v3_job_worker_in_process` (default `True`) and
`v3_job_poll_interval_seconds` are only consulted when it is on.

**Deprecation plan:** `v3_durable_jobs_enabled` is removed once the durable path
has been live-verified on the real-issuer set and the `BackgroundTasks` call site
is deleted. It exists to make a migration safe, not to be permanent.

## Security considerations

- **`payload_json` carries job inputs and no credentials.**
  `test_the_payload_never_carries_a_credential` pins the exact key set, so a
  future field cannot be added to it without a reviewer seeing this test change.
- **`lease_owner` never reaches a reader.** Asserted over the composed envelope
  and over HTTP.
- **An error a reader sees is an exception TYPE or a sanitized code.** Never a
  message, never a trace, on either path.
- **No new endpoint, no auth change.** The three routes are the same three
  routes; `APP_ENV=staging` remains load-bearing and untouched.
- **The safety contract is unchanged on the new terminal states.** A
  dead-lettered job still returns `human_review_required: true` and the internal
  disclaimer — asserted, because a new status is exactly where a safety field
  gets forgotten.

## Unit and integration tests

`tests/test_v3_company_research_durable.py` — **47 tests** against a real
file-backed SQLite database (not `:memory:`: the durable path is genuinely
concurrent — a heartbeat writes while the handler's session writes — and
`StaticPool` shares one connection across sessions, which is a harness artifact
that manifests as "no such table" when the pool reopens an empty in-memory
database). Groups: the flag off · submission · execution · the reader-facing
envelope · event-loop isolation · the in-process worker lifecycle · the polling
contract over HTTP.

The HTTP group deliberately restates the assertions
`test_v2_async_company_research.py` makes, with the flag on. If any of them
differ, the wiring changed something a reader can see.

## Non-goals

- The other five `BackgroundTasks` call sites (field review, market discovery).
  One entry point at a time; this is the one the product's front door uses.
- Service Bus (Slice 6, blocked on OPEN DECISION #2).
- A cancellation *endpoint*. The store supports `request_cancel` and the worker
  honours it, but exposing it is a UI decision that has not been asked for.
