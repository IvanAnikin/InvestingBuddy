# V3.1 Slice 1.4 — Search backend abstraction

**Branch:** `feature/v3-1-4-search-interface` → `develop/v3`
**Status:** `IMPLEMENTED` — and **stopped at the backend-selection gate**
([OPEN DECISION #1](../OPEN_DECISIONS.md#1-azure-ai-search-vs-postgresql--pgvector)).
**Migration:** none.

## Objective

Define the provider-neutral retrieval contract the research domain will call,
make the domain's retrieval rules executable in it, and ship one complete
reference backend — **without** choosing the production search backend.

## Why now

The corpus has documents, pages, sections and tables. What it does not have is a
way to ask it anything. Everything after this slice — chunking, the retrieval
service, the `search_company_corpus` agent tool in V3.3 — is written against this
interface, so it has to exist before them and it has to be right.

## What deliberately does not ship

**The production search backend.** The register in the implementation plan
originally paired this slice with "a PostgreSQL lexical implementation". That was
not done, and the reason is worth stating plainly rather than leaving as an
omission:

OPEN DECISION #1 is *Azure AI Search vs PostgreSQL + `pgvector`*, it is **user-owned
on cost**, and both options cover the lexical layer as well as the semantic one.
Writing a `tsvector` backend would be choosing (b) in everything but name — it is
the same datastore, the same operational model and the same "one less service"
argument that the decision turns on. Answering it here would be answering a
question that was asked of somebody else.

The interface is what makes the deferral cheap. Whichever way #1 goes, it costs
one adapter and no domain change, and this slice is the thing that guarantees
that.

**What the in-memory backend does and does not prove.** It proves the contract is
sufficient: index, filter, lexical, semantic, hybrid, stable ids, deletion by
version, governance. It does **not** prove anything about retrieval quality or
scale — a corpus of thousands of annual reports is not served from a Python dict,
and claiming otherwise would be exactly the "it works locally" the repository has
already been burned by.

## The two rules the interface makes executable

**Vector-only retrieval is forbidden.** `SearchMode.SEMANTIC` exists so a backend
can declare it and a hybrid search can use it internally; a *caller* may request
only `LEXICAL` or `HYBRID`, and asking for `SEMANTIC` raises
`VectorOnlyRetrievalError` with the reason named. "Revenue grew strongly" is
semantically close to every revenue sentence in every period and segment of every
issuer; a hit that cannot be pinned to *Group, FY2025* is a plausible-looking
scope error rather than evidence.

**No accidental cross-entity search.** A query either names the companies it may
return or sets `allow_cross_entity=True`. Deliberate cross-entity search is a real
research question; the accidental version returns another company's numbers under
this company's heading.

## Three smaller decisions, and why

**Filters are applied inside the search, never after it.** A retrieval that takes
the top 10 semantic matches and then drops the wrong-period ones has returned the
top 10 matches from the wrong periods — the right ten were never retrieved. So
every filter key is denormalized onto the chunk, and `CorpusFilters.matches` lives
in the shared types rather than in each adapter, so a new filter cannot be
implemented in one backend and forgotten in another.

**Fusion is ours, not the vendor's.** Combining a lexical ranking with a semantic
one is a research decision — in finance the exact match on a metric name, ticker,
fiscal label or drug identifier usually deserves to win — and if the fusion
belonged to the vendor, changing vendors would change the answers and every
cross-vendor benchmark would compare two systems rather than two backends.
Reciprocal rank fusion is used rather than score mixing because a BM25 score and a
cosine similarity are not on the same scale, are not on the same scale as their
own next release, and are not comparable across backends; only the *order* each
leg produced is meaningful to both.

**A hybrid query with no embedding degrades to lexical.** A worse answer, never a
wrong one, and the result says which it is by leaving `semantic_score` as `None`.

## Security considerations

- `indexable_only` defaults to `True`, so a chunk whose governance policy forbids
  indexing is never returned. It may still be stored and cited.
- `access_classes` is a first-class filter, so a private-content boundary is a
  query constraint rather than a presentation-layer choice — which is what
  §8 of the governance document requires for multi-tenancy readiness.
- No backend query syntax is exposed. A caller supplies typed filters and text;
  there is nowhere to inject a raw query expression, which matters once an agent
  is the caller (V3.3).

## Unit tests

`tests/test_v3_corpus_search_interface.py` — **37 tests**, no database, no
network, against the real in-memory backend rather than a mock.

Covers: semantic-only refused with the reason named · only LEXICAL/HYBRID
requestable · unscoped query refused · empty query · `top_k` bounds · the backend
enforcing the same rules · period / scope / document-type / date-range /
source-tier / access-class filters each constraining · **Group + FY2025 together**
· interim not returned for an annual query · one company's query never returning
another's text · filters before top-k · a non-indexable chunk never indexed or
returned · exact metric name found · identifiers surviving tokenisation
(`FY2025`, `PNDORA`, `mRNA-1273`) · a padded page not beating a precise sentence ·
empty result · determinism · hybrid degrading to lexical · the semantic leg
surfacing what lexical misses · **the semantic leg still filtered** · fusion using
rank not scores · agreement between legs counting · lexical outweighing semantic ·
cosine degrading rather than raising · reindexing a stable id replacing not
duplicating · deletion by version · protocol conformance · capability declaration
· **no corpus module imports a search SDK** · **the backends directory contains
only `memory`**.

That last one is the gate made executable: if somebody adds an adapter, the test
fails and the decision has to be taken deliberately.

## Acceptance criteria

1. **A caller cannot obtain vector-only retrieval.** ✅
   `test_semantic_only_retrieval_is_refused`, plus the same refusal enforced at
   the backend.
2. **Period and scope filters actually constrain results.** ✅
   `test_group_and_fy2025_together_are_expressible` narrows five chunks to one;
   `test_the_semantic_leg_is_still_filtered` shows a semantically perfect
   wrong-period match excluded.
3. **The domain depends on no vendor SDK, and no production backend was
   chosen.** ✅ `test_no_corpus_module_imports_a_search_sdk` and
   `test_the_production_backend_decision_is_not_taken_here`.
4. **No V2 regression.** ✅ suite 4825 → **4862 passed**, 12 skipped; `ruff`
   clean; `mypy app` 71 (unchanged, same scope). Nothing outside
   `app/services/corpus/search/` changed.

## Non-goals

- Embeddings and an embedding provider. `CorpusChunk.embedding` is the slot; who
  fills it is a provider decision in V3.4.
- Chunking (Slice 1.5) and the retrieval service (Slice 1.6).
