# V3.0 Slice 2.1 — Bound the reclaim attempts (corrective)

**Branch:** `feature/v3-0-2-1-bound-reclaim-attempts` → `develop/v3`
**Status:** `IMPLEMENTED`
**Migration:** none

## Objective

Stop a job whose worker keeps being killed from being reclaimed forever, and
give it the `dead_letter` end the contract already promised it.

## The defect

Slice 1 increments `attempt` on every claim, including a reclaim, and its
docstring states the reason plainly:

> Not counting it would let a job that reliably kills its worker be retried
> forever, which is the exact shape of an outage that keeps restarting itself.

The counter was added. **The bound on it was not.** `is_claimable` never
consulted `attempt`, and `fail()` — the only writer of `dead_letter` — is called
by a worker that *caught* an error. A worker that is `SIGKILL`ed catches
nothing, so:

```
claim → attempt=1 → worker killed
reclaim → attempt=2 → worker killed
reclaim → attempt=3 → worker killed
reclaim → attempt=4 → ...      # unbounded, dead_letter never reached
```

Verified against the merged contract before the fix: `is_claimable` returned
`True` at `attempt=3, max_attempts=3`, and successive `claim()` calls returned
`attempt=4`, `5`, … .

This was invisible while nothing executed. Slice 3 routes real company research
through this path, and a real research run is exactly the workload that kills a
worker — a large PDF against ~1.75 GB on B1 is the documented failure mode, and
six live `WORKER TIMEOUT` → `SIGKILL` events in ten days are what the whole
phase exists to survive. Fixing it before the wiring, rather than after, is why
this is its own slice.

## Changes

**`app/services/jobs/job_contract.py`**

- `attempts_exhausted(job)` — the same bound `fail()` already uses, named once.
- `is_abandoned(job, now)` — running, lease lapsed, no attempts left. The case
  nothing else can see, because nobody was alive to report it.
- `is_claimable` — the reclaim branch now also requires attempts to remain.
  Applied **only** to the reclaim branch: a `pending` job with spent attempts
  cannot arise from this contract (`fail` dead-letters instead of scheduling
  one), so refusing it would block a deliberate operator reset rather than a bug.
- `abandon(job, now)` — dead-letters with a reason that names the actual cause.
  Deliberately worded differently from `fail`'s "exhausted N attempts; last
  error: …", which on this path would read "last error: unknown" — a missing
  detail rather than the diagnosis. Here the absence of any reported error *is*
  the diagnosis.

**`app/services/jobs/job_store.py`**

- `claim_next` retires an abandoned candidate mid-scan and continues to the next
  one. On the claim path rather than in a reaper because there is no reaper
  process to run, and the only moment anyone looks at a lapsed lease is when a
  worker is looking for work. The write is CAS-guarded on `attempt`, so two
  scanning workers cannot both retire it and a job reclaimed between the read
  and the write is left alone.

## DB migration

**No.** `dead_letter_reason` and `attempt` are already 019 columns.

## Feature flags

None. This is a correction to code no entry point reaches yet.

## Security considerations

None new. The dead-letter reason is generated text naming a count, never
provider output, and no new data is read, written or logged.

## Tests

- `tests/test_v3_durable_job_contract.py` — `TestAbandonment`, **8 new** pure
  tests: a lapsed lease with attempts left is still reclaimable; with none left
  it is not; `claim` refuses it; abandonment needs all three conditions
  (running + lapsed + exhausted); the reason names the cause; `abandon` refuses
  a job that is not abandoned; a `pending` job with spent attempts stays
  claimable; and the bound is the same one `fail` uses.
- `tests/test_v3_worker_executor.py` — `TestAbandonedJobRetirement`, **6 new**
  tests against a real database: a repeatedly-killed job is dead-lettered rather
  than reclaimed; attempts never climb past the bound; retiring one job does not
  stop the scan finding another; a job with attempts left is still reclaimed
  (the bound must not break the recovery it sits inside); only one of six
  concurrent workers retires it; and the loop reports no work rather than
  spinning on it.

## Acceptance criteria

1. **A job whose worker is killed `max_attempts` times reaches `dead_letter`
   with a reason.** ✅ `test_a_repeatedly_killed_job_is_dead_lettered_not_reclaimed`.
2. **`attempt` can never exceed `max_attempts`.** ✅
   `test_attempts_never_climb_past_the_bound` (five further claim attempts, still 2).
3. **Recovery still works.** ✅ `test_a_job_with_attempts_left_is_still_reclaimed`
   — a bound that stopped legitimate reclaim would be a worse bug than the one
   it fixes.
4. **No V2 regression.** ✅ suite 4488 → 4502 (+14, none lost); `ruff` clean;
   `mypy app` 71 errors, unchanged.
