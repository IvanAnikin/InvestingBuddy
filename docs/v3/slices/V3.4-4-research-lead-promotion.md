# V3.4 Slice 4.4 — ResearchLead persistence and the verification gate

## Objective

Give a provider's claim somewhere durable to live, and build the gate that turns it into
canonical evidence or **rejects it with a reason that is kept**.

Slice 4.1 defined `ResearchLead` as an in-memory dataclass with a closed rejection
vocabulary. Nothing persisted it and nothing verified it, so the promotion path
`lead → source candidate → InvestingBuddy fetch → canonical source → evidence → fact`
existed as a docstring. This slice makes the first three arrows executable and recorded.

## Why now

4.3 shipped adapters that produce leads. A lead a run cannot persist is a lead the next
run cannot learn from, and `verification_survival_rate` per provider — the metric 4.5's
benchmark is built on — is uncomputable without stored rejections.

- `app/services/providers/governance.py` — `permits_document` / `assert_no_credentials`.

## Proposed changes

A `research_leads` table, a persistence layer, and `verify_lead` — a deterministic gate
that fetches the cited source **through InvestingBuddy's own fetcher** and decides.

### The one rule this slice must not break

> **A verification that re-reads the provider's snippet has verified nothing.**

So the verifier never reads `SourceCandidate.snippet` or any provider-supplied text. It
reads only bytes the platform fetched itself, and it records the `content_hash` of those
bytes on the row. A test asserts the failing direction: a lead whose *snippet* contains
the claim and whose *fetched document* does not is **rejected**, not verified.

## Security considerations

- The cited URL is attacker-influenced. It goes through `safe_fetch_document`, which is
  HTTPS-only, applies the host guard, the redirect guard, the byte cap and DNS pinning.
- Fetched text is **data**. Nothing in the gate interprets it as instructions; the only
  operations performed on it are normalisation and substring/numeric comparison.
- `verify_lead` refuses a URL the run's governance does not permit as
  `source_not_permitted` — before fetching, not after.
- The stored `claim_text` and `rejection_detail` are length-clipped so a pathological
  provider payload cannot become an unbounded row.

## Unit tests

The eight rejection reasons, each exercised. The `unverifiable` case (no URL) kept
distinct from `rejected`. Snippet-not-source. Numeric normalisation
(`1,234.5` vs `1234.5`, scale words, currency symbols) and its refusals. Period and scope
comparison delegating to the existing modules. Duplicate and superseded. Clipping.
Vocabulary drift guards.

## Integration tests

Real PostgreSQL: the CHECK constraints, the retention of a rejected lead after the
company it referenced is deleted, and `verification_survival_rate` computed by a real
aggregate query rather than in Python.

## Live issuer acceptance

Not performed — V3 is not deployed. The fetch path is exercised against an injected
fetcher in tests; the injected seam is the same function signature the live path uses.

## Acceptance criteria

1. A provider claim with no resolvable source is persisted and stays a lead: status
   `unverifiable`, distinct from `rejected`, with no rejection reason.
2. A rejected lead keeps its reason, and the reason is from the closed vocabulary — a
   reason outside it cannot be stored (database CHECK, not only Python).
3. A lead is promoted only against bytes InvestingBuddy fetched itself: the row carries
   the `content_hash` of those bytes, and a lead whose snippet contains the claim but
   whose fetched document does not is rejected.

## Non-goals

- Building the evidence fragment or the canonical fact from a verified lead. Promotion
  records *that* the claim survived and against which bytes; turning it into an
  `ExtractedFact` needs the ledger (V3.5) to say which run asked for it.
- Any model-assisted verification. Deterministic or refused.
- Fetching anything not cited by a lead.

## Rollback

Drop the table (031 downgrade). Nothing else reads it.
