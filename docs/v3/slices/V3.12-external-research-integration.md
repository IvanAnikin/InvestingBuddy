# V3.12 — External Research Integration, and the last unstaffed role

## What this closes

The V3.11 release candidate shipped with one honest caveat, in §11.6:

> The `ResearchLead` → Evidence promotion path has never run with a real external
> provider. **Zero lead rows across every real run.**

V3.11.1.2 proved DeepSeek can retrieve. It did not connect the retrieval to anything:
`investigate()` still ran on `/chat/completions` with no tools, and the two external tool
names — `search_web`, `fetch_public_source` — had sat in the closed vocabulary since V3.3
with `builtin.py` recording that they *"wait for the provider runtime"*.

This slice is that wait ending. **It adds no architecture.** The vocabulary, the
governance check, the role policy, the tool session, the verification gate and the
promotion rule all already existed; what was missing was two handlers and the wiring
between them.

## The chain, and where each link lives

```
Research Director            plans `recent_external_developments` when the tools exist
  → external_research_analyst   the one role that reaches outside the platform
  → Investigator                chains the two tools deterministically
  → search_web                  DeepSeek /responses, real retrieval → CLAIMS, no ids
  → ResearchLead                a claim with a URL. Not evidence.
  → fetch_public_source         InvestingBuddy's OWN guarded fetch
  → verify_lead                 the existing gate, unchanged
  → ev:x:…                      minted ONLY on `verified`, from OUR content hash
  → Research Ledger             a finding citing that id
  → playbook → Council          consumed downstream
```

The load-bearing asymmetry is which function may mint an id. `search_web` returns claims
and **no `evidence_id`, `fact_id`, `calculation_id` or `id`** — the four keys the
Investigator reads as citations — so a model physically cannot cite a search result. Only
`fetch_public_source` mints, and only for `LEAD_VERIFIED`, a status
`LeadVerificationOutcome` refuses to construct without a content hash. **"Verified"
cannot exist without bytes InvestingBuddy fetched.**

## Live acceptance — MRNA, real provider, real fetches

**Sixteen runs of `scripts/v3-external-acceptance.py --sqlite --live`, in two phases.**

| Phase | Runs | Promoted evidence |
|---|---|---|
| Before the prompt said *"cite the document, not a listing"* | 10 | 5 |
| After it — the code that ships | **6** | **5** |

An earlier draft of this document reported "five of six" from the first runs only, and
that figure did not survive more runs. **Every non-promotion is the platform correctly
refusing what it could not verify**, and the reasons are all about *which URL the
provider chose* — none about the wiring:

| Failure mode | Runs | What happened |
|---|---|---|
| `value_mismatch` | 2 | It cited an **EDGAR index page** — a list of a filing's documents, containing no figures — so the number legitimately was not there |
| `url_unreachable` | 2 | It cited `investors.modernatx.com`, which returns 403 to our fetcher |
| `claim_not_in_source` | 1 | The cited page did not support the claim |
| `pending` (undecided) | 1 | Documents retrieved and **no text could be extracted**; recorded as undecided, not as a refutation |

The two index-page failures were a defect in the *instruction*, not the provider: the
prompt asked for a primary source without saying that a listing is not a document. The
last three runs on the shipped code cite SEC exhibits directly and promote in all three.

**The operational fact to carry forward: promotion is provider-dependent.** Whether a run
promotes anything depends on whether the provider cites a page our own fetcher can
retrieve *and* read *and* find the figure in. The system behaves correctly in both
outcomes — but a caller must not read "no external evidence" as "nothing to find".

A representative promoted finding:

   a 66% decline year over year from $2,811 million in Q4 2023."
  evidence_ids  ev:x:b2eae498c715bb04c20cbeeb, ev:x:d1f77c2693eb6d906fb84169

**The operational fact to carry forward: promotion is provider-dependent, at roughly a
coin-flip per run on this issuer.** Whether a run promotes anything depends on whether
the provider happens to cite a page our own fetcher can retrieve *and* read *and* find

read "no external evidence" as "nothing to find".

## Negative acceptance — live, against a real document

All eight cases run against the **same real SEC exhibit** the positive path verified, so
each rejection is the gate refusing a claim about a page we really did fetch — not a
fetch failure standing in for a verification failure.

| Case | Outcome |
|---|---|
| control: the true claim | **verified** → `ev:x:16cbe91134b75f2c54051ccc` |
| value fabricated | rejected · `value_mismatch` |
| claim text absent from the document | rejected · `claim_not_in_source` |
| period conflicts with the document | rejected · `period_mismatch` |
| provider mutated the URL | rejected · `url_unreachable` |
| provider fabricated a plausible URL | rejected · `url_unreachable` |
| internal host (SSRF) | rejected · `source_not_permitted` |
| non-https scheme | rejected · `source_not_permitted` |

**Evidence minted: 1 of 8.**

### Two gate defects this found, both pre-existing

Neither was reachable from a fixture. Both needed a real document with hundreds of
numbers and several periods in it, which is the argument for the live negative acceptance
existing at all.

**A fabricated value verified.** A claim of `8675` matched the exhibit's `8650` under the
0.5% relative tolerance. The document holds **393 numbers**, so "within half a percent of
some number in the document" is a condition almost any invented figure satisfies.
`value_supported` now also requires the figure to round to the claim *at the precision
the claim states* — `8675` claims unit precision and `8650` is not that number — while
`145` still matches a document's `144.7`. It is an intersection with the old rule, so it
can only reject what that rule accepted, never promote something it refused.

**A conflicting period verified.** `verify_lead` compares a claimed period only against
one the platform independently determined, and a raw public fetch supplied none — so the
comparison was **skipped, not failed**, and a claim naming `2019-Q1` passed against a 2026
exhibit. `periods_in()` now reads the periods a document states about itself, as the
symmetric partner of `numbers_in()`. An empty set means *unchecked*, never "no periods".

## Four wiring defects the live pipeline found

Each one made the path silently do nothing, and each was invisible to unit tests:

| Defect | Symptom |
|---|---|
| `implemented_tools()` read the **process-global** settings | A run's own `cfg` could not decide its own tool surface, so the external tools never registered however the pipeline was configured |
| The pipeline built its registry without `cfg` | Same, one layer down — the registry the Investigator actually uses |
| `policy_for(role_id, tools=…)` dropped the role's `source_classes` | The first external call was refused `access_class_not_permitted`: `search_web` reads `public_web`, the role declares it, the policy was built with an empty set. **The governance check was right; the wiring was not.** |
| The external query never named the issuer | The provider was asked "what has *the issuer* reported?" and answered about nobody, fast |

## A design correction the live run forced

The first draft **dropped** any claim citing a URL absent from the retrieval trace, on the
theory that an unopened page is a recalled one. A live MRNA run disproved it: the provider
found the right SEC exhibit through a **search result** — whose URLs the contract never
exposes to us — cited it correctly, and the guard discarded the only good lead of the run.

`opened_urls` is a subset of what the provider legitimately saw, so absence from it is not
evidence of fabrication. The trace now **annotates and does not gate**:
`leads_citing_unopened_pages` stays as a provider-quality signal, and the real gate stays
where it belongs — InvestingBuddy fetches the URL itself, and a fabricated one fails there
with a reason worth recording.

## One more failure mode, named

A live run made **27 page opens and wrote no answer at all**: searching and answering
share one output budget on `/responses`, reasoning counts against it, and `max_tool_calls`
is accepted and ignored (V3.11.1.2). The result is indistinguishable from "the web holds
nothing" unless it is detected — so it is, as `exhausted_budget_retrieving`, and the
result is `partial` rather than `completed`.

The mitigation is a prompt, because there is no request parameter that bounds retrieval.
`RETRIEVAL_BUDGET_PROMPT` caps searching in words and explains the trade to the model.
Measured effect on the same question: **119k input tokens and no answer → 36k and a
correct one.**

## Cost — a single bounded sample, and unpriced

| Measure | Value |
|---|---|
| Input tokens | 25,453 – 69,949 (median ≈ 27k) |
| Output tokens | 3,589 – 7,513 |
| Cached tokens | 22,656 – 62,848 |
| Provider web searches | 2 – 4 |
| URL fetches (provider + ours) | 6 – 9 |
| Wall clock | 41 – 78 s |
| Verified useful findings | 0 – 3 |
| **Estimated cost** | **UNPRICED** |

`cost_per_verified_useful_finding` is reported as `None`, not as a number.
`v3_price_usd_per_million_*` is unset, and this campaign's rule is that an unknown cost is
never labelled zero — a zero makes an unpriced provider look like the cheapest one.
DeepSeek's published price could not be read programmatically (the pricing page is
JS-rendered), and **inventing the figure to fill the column would be exactly the
fabrication the platform's own rule 6 forbids**. Supplying it is one flag:
`--price-in`/`--price-out` with `--price-source`, and the metric computes.

## Consent, unchanged

| Credential | `V3_DEEPSEEK_SEARCH_ENABLED` | External path |
|---|---|---|
| ✅ | ❌ | **no** — a credential is not consent |
| ❌ | ✅ | **no** — a flag is not a credential |
| ✅ | ✅ | yes |

With the flag off the tools are **not registered at all**, so `implemented_tools()`
excludes them, the external question is never planned, and the role is never seated.
That is the fail-closed direction: a coverage fact visible at plan time rather than a
refusal mid-run.

Behaviour with the flag off is **unchanged**, verified by planning the same subject both
ways with a real credential present — same five questions, same three roles, same
assignments. Not "byte-identical", which an earlier draft of this document claimed: two
changes are unconditional (`policy_for` now receives a role's `source_classes`, and
`register_builtins` receives `cfg`). Both are inert with the flag off — the only other
spec declaring access classes is `search_private_research`, which no role holds — but
inert is a weaker claim than untouched, and the weaker one is what the code supports.

**Flag-ON is also one question and one role, and had to be made so.** The external role
holds `search_company_corpus`, and review found it winning the `_least_loaded` tie on
role id and taking `recent_disclosure` away from `business_analyst` — routing a question
the corpus answers to a paid vendor. A role that reaches outside the platform is now
eligible only for a question that requires an external tool.

## What is still not true

**Scope is unchecked on this path.** `verify_lead` compares a claimed scope only against
one the platform independently determined, and a raw public fetch produces none. A Group
figure claimed as a segment one would not be caught. The consequence is carried rather
than hidden: external evidence travels with `scope_key = None`, so a finding built on it
inherits no scope, and the payload says `scope_checked: false`.

**Period is checked only when the document says so.** `periods_in` reads what a document
states about itself; a document that names no period leaves the claim unchecked, and the
evidence again carries no `period_key`.

**Six runs is not a benchmark.** The 5-of-6 promotion rate is a measurement of this
question, this issuer, this provider, on one afternoon.

## What the independent code review changed

It returned **REQUEST CHANGES** on four blocking findings, and every one was real. Two
were spend or coverage regressions that flag-on introduced, one was a correctness
regression I had added to a gate every provider shares, and one meant the slice's own
sibling harness had never been executed.

**Turning the flag on re-routed an existing question.** The external role also holds
`search_company_corpus`, so it competed for corpus questions and — winning the
`_least_loaded` tie on role id — took `recent_disclosure` away from `business_analyst`,
sending a question the corpus answers to a paid vendor. Measured, both ways, before and
after. A role that reaches outside the platform is now eligible only for a question that
*requires* an external tool, and flag-on adds exactly one question to one new role.

**An untooled carry-forward gap could trigger a paid search.** A prior-gap question
carries empty `required_tools`, so every role can "answer" it; assigned externally, the
Investigator's fallback ran the role's whole tool list and issued a vendor search for a
question nobody asked to be searched — a bill arriving on the *second* run of a company
and on no other. Fixed at the planner and again in `_gather`, which now refuses to reach
outside the platform on a fallback.

**My period check rejected correct claims.** This is the one that mattered most: a real
10-Q says *"three months ended June 30, 2026"*, a phrase that establishes the **year**,
so a claim of `2026-Q2` was compared against `{"2026"}` and refused. Same for split-year
issuers. That is a worse failure than the one the check was added to fix — it rejects
true statements rather than admitting false ones, and it does so silently into
`verification_survival_rate`. `periods_in` now returns `(period_type, key)` pairs and the
gate compares **only within the claim's own granularity**; a partial read returns
`PENDING`, per the module's own rule that *"a system that cannot tell 'we never read that
page' from 'that page does not say it' is worse than one that admits the difference"* —
which my first version violated.

**The sibling acceptance harness could not run.** `v3-issuer-acceptance.py
--external-research` read two columns that do not exist, and its citation check treated
`ev:x:` as a corpus chunk id — so it failed on **exactly the outcome V3.12 exists to
produce**. External ids now resolve against the lead record they were minted from.

The review also caught a **16× performance regression**: `value_supported` re-parsed the
claim inside a loop over up to 200,000 numbers, on the event loop. Hoisted; measured
0.709s → 0.075s. That is the shape of the defect that once had gunicorn killing workers
mid-run.

Six smaller corrections: the minted evidence id is now **persisted** to
`promoted_evidence_id` (the column has existed since migration 031 and nothing wrote it,
so an auditor holding a citation had no route back to the URL or the hash); the period
key stamped on external evidence is **canonical** rather than the provider's wording,
which would otherwise read as a conflict against corpus evidence; a dead constant and a
dead disjunct removed; two docstrings that described a guard I had deliberately removed;
and the chain fixture rewritten to real 10-Q phrasing after the review found it using the
one wording that dodged the period defect.

One finding was **not** fixed, deliberately: a claim written `8,700` is refused against a
document's `8,674.6`, because a trailing zero is ambiguous between two and four
significant figures and reading it permissively re-admits what the precision rule exists
to refuse. The false negative is the safe direction and the provider can cite the exact
figure. It is pinned by a test so nobody "fixes" it later.

## What the security review changed

The scan returned **PASS** with no blocking finding: the SSRF chain holds on
provider-supplied URLs (scheme, IP-literal and internal hosts, DNS resolution, a
connection *pinned* to the validated address, a 4-hop redirect chain re-validated and
re-pinned at each hop, the host allowlist, the content-type allowlist and the byte cap
all still fire), untrusted content is fenced and cannot smuggle a citable id, and the
gating is correct in both directions. Five things were fixed anyway.

**A budget could not bound the two tools that spend.** Both specs declared
`ToolCost()` — all zeros — and `ToolSpend.would_exceed` reads the *declared* cost,
because a budget checked after the call is a report. So `ToolBudget(max_searches=…)` was
inert against the only two tools in the platform that spend money outside it. Nothing
broke today because budgets default to unbounded; it would have failed the day an
operator set one.

**A role's declared budget was enforced by nothing.** `RoleSpec.tool_budget` is keyed by
tool name while `ToolBudget` bounds tool *classes*, so the two shapes never met and the
declaration was persisted to the plan and ignored. The sum now becomes an enforced
`max_calls`. Per-tool caps remain unenforced and that is recorded rather than implied —
an enforced approximate bound is worth more than an exact decorative one.

**A docstring and a payload key described a guard that had been deliberately removed.**
Both still said leads citing unopened pages were *dropped*; they are kept, by ADR-056 §4.
The key is now `leads_citing_unopened_pages_kept`. A key that says "dropped" about kept
leads is exactly the quiet inaccuracy a reader cannot catch.

**`default_registry()` read the process-global settings**, so on a developer machine the
tool surface came from the `.env` — the same "reads the machine" class this campaign has
already paid for twice. It threads `cfg` now.

**A `getattr` named a setting that does not exist**, so an external search's timeout was
always the literal 180 s regardless of configuration.

Two residuals are recorded and not closed: `check_fetch_url` validates scheme, host and
DNS but **not the port**, so a public host on a non-standard port is reachable — bounded
to public IPs, but newly provider-controlled; and the redirect-stays-on-host guarantee
depends on `SOURCE_CONNECTOR_ALLOWLIST_ONLY` remaining `true` (its default). Both belong
to the fetcher, not this slice, and both are now written down.

> **Noted for the user, not fixed here:** V3 has **no deterministic forbidden-language
> backstop.** Nothing under `services/director`, `services/agents` or `services/pipeline`
> imports `safety_terms`, which V2's report generator uses to scan output. Untrusted
> open-web prose now flows into the Investigator's prompt and thence into findings, and
> the only control is a model instruction. Not a regression — V3 is undeployed and not
> product-facing — but **this should be a required gate before V3 output ever reaches a
> reader**, and the external path is what makes it matter.

### What could not be run

**The migration-chain acceptance.** `scripts/v3-issuer-acceptance.py` builds a scratch
PostgreSQL database and migrates it to head; the Docker daemon on this machine is
unresponsive, so the runs above used `--sqlite`, which builds the schema with

script says so in its own output rather than letting a reader assume otherwise. V3.12
adds no migration, so the chain itself is unchanged from V3.11, where it was verified end
to end against real PostgreSQL 16.
