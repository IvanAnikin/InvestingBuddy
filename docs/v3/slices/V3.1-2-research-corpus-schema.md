# V3.1 Slice 1.2 — Corpus document model

**Branch:** `feature/v3-1-2-research-corpus-schema` → `develop/v3`
**Status:** `IMPLEMENTED`
**Migration:** 022 (created; **not applied to any deployed environment**)

## Objective

Separate the *logical* document from one *retrieval* of it, so a restatement
becomes a new version instead of silently overwriting the original — and give the
corpus a durable identity that existing `ExtractedDocument` rows can be attached
to without a bulk migration.

## Why now

Slice 1.1 stores bytes. A content hash identifies bytes and cannot answer "is
this the same document I already have?": a restated annual report, a re-typeset
PDF and the same report served from a different CDN path are three hashes and one
document. Without the distinction, every later slice — full text, chunking,
citation-preserving retrieval — has nothing stable to hang off, because the thing
a citation points at is the document, not the bytes.

## Security considerations

- `canonical_url` is stored through `canonicalize_source_url`, so no `user:pass@`
  userinfo, no credential-bearing query parameter and no fragment is persisted.
- A URL-derived `document_key` is a **hash** of the canonical URL, so a signed
  variant of a URL maps to the same document and no part of the URL — including a
  token — appears in the key. Asserted by test.
- An unrecognised `access_class` normalises to `licensed_private` (deny), never to
  public.
- Company isolation: the document identity is scoped by `company_id`, and the same
  bytes retrieved for two companies produce two documents. Asserted by test.

## The decision this slice is really about

**Never merge on a guess.** Two retrievals are the same document only when the
documents themselves say so: same company, same declared kind, same declared
period. Everything else stays separate. The two failure directions are not
symmetric — splitting produces a duplicate citation, merging attributes one
report's pages to another report's identity — so the fallback is deliberately the
one that over-splits.

That is why the fallback identity is the canonical URL and not, say, a title
similarity match.

### The one place a year is read that `document_period` refuses to read

`document_period` returns `UNKNOWN` for a bare year, on purpose: a bare "2025"
beside a *figure* is exactly the guess that produced the `INTERIM_AS_ANNUAL`
contradiction. Its own docstring notes that "no period stated" is "the common case
for an annual report".

Taken literally, that leaves every annual report with a URL identity — and the
annual report is the single document class where "version, not overwrite" matters
most. So `identity.annual_period_from` reads a year **only** when it sits directly
beside the document's own name for itself: `Annual Report 2025`,
`2025 Universal Registration Document`, `annual-report-2025-26.pdf`. It refuses
when two candidate years disagree, it never fires for an interim document, and it
recognises a split fiscal year (`2025/26`) without mistaking a range (`2025-2026`)
for one.

It is **corpus-only**. It reaches document identity and the corpus period columns;
it never touches `extracted_fact_validator`, `financial_period` or any fact's
period, and `test_the_rule_never_reaches_the_fact_pipeline` asserts that by
scanning the tree. The blast radius of being wrong is a mis-filed document, not a
mis-dated figure. `period_basis` records `annual_title_label`, so the derivation is
always distinguishable in the audit trail from one `document_period` made.

## Migration path from existing `ExtractedDocument` rows

Three properties, matching the migration plan's backfill pattern:

1. **Nothing is migrated en masse.** The V2 writer keeps writing
   `ExtractedDocument` exactly as before; `ingest_extracted_document` records the
   corpus version *beside* it with `extracted_document_id` pointing back. Every
   existing read path is untouched.
2. **The bridge is explicit.** `research_document_versions.extracted_document_id`
   is how a corpus read for a document whose full text is not yet persisted
   (Slice 1.3) falls back to that row's bounded `excerpts_json` rather than
   answering "not available".
3. **The backfill is resumable, idempotent and operator-invoked.**
   `backfill_from_extracted_documents(session, cfg=..., limit=..., company_id=...)`
   selects only rows with no corpus version yet. Running it twice does nothing the
   second time; running it in batches is safe. **Nothing calls it automatically** —
   a backfill that starts itself on the first request after a deploy is how a
   migration becomes an outage — and a test asserts no other module calls it.

A historical row never claims bytes it never had: artifact retention did not exist
when it was written, so `research_artifact_id` stays NULL. Its period is re-derived
from its own title and URL through the same pure rules; when they say nothing, it
stays NULL and the document takes a URL-derived key.

## Non-goals

- Parsed text, pages, sections, tables (Slice 1.3) — a version is a *retrieval*,
  and what a parser made of it is a derivation that depends on which parser ran.
  Putting extracted text on the version would make the "immutable version" claim
  false the first time a parser improved.
- Any search (1.4-1.6).
- `legal_entity_id`. The entity master is V3.2; until then the corpus links to
  `companies` exactly as every other table does, so V3.2's backfill has one place
  to change rather than two.
