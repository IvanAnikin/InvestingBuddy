# V3.0 Slice 4 — Server-side numeric verification

**Branch:** `feature/v3-0-4-server-side-numeric-verification` → `develop/v3`
**Status:** `IMPLEMENTED`
**Migration:** none

## Objective

Make numeric reconciliation canonical on the server and part of the persisted
research record. Keep the browser guard as defence in depth.

## Why now

The check already existed and worked well. It lived entirely in
`apps/web/src/components/research/numericConsistency.ts`, which is the wrong
place for it, and the three consequences are concrete rather than stylistic:

- **The verdict was not in the record.** A report was persisted and an admin
  approved it, and nowhere did the stored research state say which statements
  had been reconciled or which had failed. The decision existed only while a
  browser tab was open.
- **The presentation layer decided what is true.** ADR-037 says the product layer
  *presents* the research state and never reconciles it. A guard that suppresses
  a sentence is reconciling.
- **It could only see what it rendered**, and it kept a hand-maintained copy of
  `fact_scope.GROUP_SCOPE_LABELS` to do it — a duplicate of "what counts as the
  consolidated entity" that a change on either side could silently
  desynchronise, after which a fact persisted as Group would be read as a
  segment and stop adjudicating Group claims. The server engine imports the one
  table.

## Changes

**New:** `app/services/numeric_verification.py` — the canonical engine, and
`tests/test_v3_numeric_verification.py` (38 tests).

**Modified:**

- `app/services/final_report_generator.py` — writes `numeric_verification` into
  report content at assembly, before validation (so the safety gate scans it) and
  before the save (so it is persisted).
- `apps/web/.../numericConsistency.ts` — `readServerVerification` reads the
  persisted verdict; the guard itself is unchanged.
- `apps/web/.../reportSections.ts`, `.../reports/[id]/page.tsx` — the two
  verdicts are **unioned**.

## Design decisions worth stating

### It records; it does not edit

A contradicted statement keeps the text the council wrote. Overwriting it in the
record would mean a withheld statement could never be reviewed afterwards
(CLAUDE.md rule 8), and it would destroy the evidence for deciding whether the
guard was right. The presentation withholds; the record keeps.

It also does not pick a winner. This layer has no basis for preferring the prose
or the fact, and silently choosing one of two conflicting numbers is the exact
failure mode the mechanism exists to prevent.

### The browser guard stays, for two specific reasons

Not as a general principle. **1,057 reports already exist and report content is
persisted**, so none of them will ever carry a server verdict — deleting the
browser guard would silently un-protect the majority of the corpus. And on a new
report the two are a genuine second opinion over the same figures by different
code.

The two are combined as a **union, never an intersection**: a conflict from
either withholds, because the purpose is not to show a contradiction.

### Deliberate parity with the browser guard

Where the engine could have been made smarter it was not. A canonical value of
"32,549 million" and a prose "32,549" are the same number at different scales and
nothing in the sentence says which; the browser guard has always required the
scale word, and this engine matches it. A server that adjudicated more
permissively than the guard beside it would produce two different answers for one
report — which is the disagreement this slice exists to remove.
`test_a_bare_magnitude_without_a_scale_word_is_not_matched` records it as a
decision rather than leaving it to look like an oversight.

### Every exclusion is a scar, and MRNA is the counterweight

The engine's conservatism is not caution in the abstract. Each exclusion has a
named live report behind it — CFR's 32 withheld segment statements, CFR's 9
withheld Group statements from a margin read as an amount, PNDORA's multiple read
as a level, PNDORA's 10 false positives on periods the report does not hold — and
each has a test named after what it cost.

Against that, **MRNA has 8 genuine conflicts**, and a guard that reports zero on
MRNA is broken, not safe. `test_a_report_with_genuine_conflicts_reports_them`
exists so the suite cannot pass on an engine that does nothing.

### The verdict carries an engine version

`NUMERIC_VERIFICATION_VERSION`, for the same reason
`CURRENT_EXTRACTION_PIPELINE_VERSION` exists: a persisted verdict must never be
assumed compatible with current code.

## Test-harness correction included

The V3 job tests ran on in-memory SQLite with `StaticPool`, which shares **one
connection across every session**. The durable path is genuinely concurrent — a
heartbeat writes while the handler's session writes — so the two interleaved on
one transaction, and when the connection was invalidated the pool reopened it,
which for `:memory:` is an empty database ("no such table"). It surfaced as three
intermittent failures.

Fixed properly rather than papered over: a file-backed database with a real pool
(one connection per session, as PostgreSQL gives), WAL journalling so a reader
and a writer coexist, and heartbeat intervals raised from 10ms — which was a
stress test of SQLite's write lock rather than of the worker, and had pushed the
suite from 1:45 to 4:19.

## DB migration

**No.** `numeric_verification` is an additive report-content section. Reports
generated before it simply do not have it, which is the state the frontend
already handles.

## Feature flags

**None.** A report that silently contradicts itself is not a feature to opt into,
and the browser guard already applies this exact logic today — putting the server
copy behind a flag would mean choosing when the record gets to disagree with the
screen.

## Security considerations

- No new endpoint, no auth change, no new data source.
- The record holds statement text that is **already in the report**, plus a
  metric key and a scope key. No provider output, no URL, no credential.
- Written before the safety gate runs, so the notice text and the recorded
  statements are scanned like any other section.

## Acceptance criteria

1. **The verdict is in the persisted record.** ✅ `TestItIsWiredIntoAssembly`
   pins that it is written before validation and before the save.
2. **It catches real contradictions, including a segment figure stated as
   Group.** ✅ `TestItCatchesRealContradictions`, including the MRNA
   counterweight.
3. **It does not suppress correct analysis.** ✅
   `TestItDoesNotSuppressCorrectAnalysis` — one test per live regression.
4. **The prose is never edited and the frontend still protects old reports.** ✅
   `test_it_never_edits_the_prose`; the browser guard is unchanged and unioned.
5. **No V2 regression.** ✅ suite 4570 → 4608 (+38, none lost); `ruff` clean;
   `mypy app` 71, unchanged; web `lint`/`typecheck`/`build` clean.

## Non-goals

- Deleting the browser guard. That is a separate slice, and it cannot happen
  while existing reports are the majority of the corpus.
- Reconciling anything other than council prose against canonical figures.
- Choosing a winner between two conflicting numbers.

## Rollback

`git revert` the merge commit. No migration. Reports already carrying the section
keep it harmlessly — the frontend treats an absent section as "no server verdict"
and a present one as advisory input to a union.

## Dependencies

None.

## Live issuer acceptance

**Not performed** — V3 is not deployed. The engine is a faithful port of logic
already live-validated in the browser on PNDORA, CFR and MRNA, and every one of
those cases is a test here; what is unproven is the *server* engine's behaviour
on a freshly generated live report.
