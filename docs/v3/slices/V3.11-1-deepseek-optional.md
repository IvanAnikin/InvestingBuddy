# V3.11 Slice 11.1 — DeepSeek: `BLOCKED ON CREDENTIAL`, and no longer release-critical

## The credential search

No DeepSeek key is reachable from this environment. Checked, secret-safely — presence and
length only, never a value:

| Location | Result |
|---|---|
| Shell environment (`DEEPSEEK_API_KEY`, `DEEPSEEK_KEY`, `DEEPSEEK_TOKEN`) | absent |
| `.env`, `apps/api/.env`, `~/.zshrc`, `~/.profile` | no DeepSeek entry |
| Azure app settings on `ib-stg-api` | no DeepSeek setting |
| Azure Key Vault (`ib-stg-kv`, `ivan-anikin`) | **cannot read** — the CLI identity is Contributor-only and has no data-plane access |

The vault case is stated precisely: a secret *could* exist there and be unreadable from
here. What can be said is that **no credential is reachable**, and no app setting
references DeepSeek.

Per the brief, the contract was **not fabricated**. The live contract slice stays
`BLOCKED ON CREDENTIAL`.

## The other way to clear the blocker

The acceptance gate allows either:

> *DeepSeek live contract is verified, **OR DeepSeek is removed as a release-critical
> dependency**.*

The second is now true, and it is demonstrated rather than asserted: **three real
playbook-gated Councils convened end to end with no DeepSeek key, no DeepSeek flag and no
DeepSeek call.** Every model slot resolved to Azure OpenAI.

`tests/test_v3_deepseek_not_release_critical.py` — 17 tests — pins it:

- no key and no flag by default;
- **every** model slot resolves to a usable vendor with DeepSeek absent;
- enabling the flag **without** a key does not route work to it — a flag is not a
  credential, and a slot pointed at a provider that cannot answer is a run that stops
  before it starts;
- the pipeline and the three agent adapters **do not import** the DeepSeek module at all,
  so the research path runs in a build where the adapter is absent entirely;
- the routing reports `shares_vendor_with_chair`, because a Red Team run by the Chair's
  own vendor is a weaker check and a reader must be able to see which they got;
- the live contract test remains opt-in and skips without a key.

## What is still NOT claimed

The adapter is **unverified**. Its request shape, search-result structure, citation
fields, usage accounting and error taxonomy remain **documentation-derived**. The opt-in
live contract test — eight questions, bounded, public-data only, secret-safe — has never
run.

DeepSeek is therefore an **optional, unverified enhancement behind a default-off flag**,
not a dependency of the release. When a key appears, one opt-in run reconciles the adapter
against observed behaviour; until then nothing in the product needs it.
