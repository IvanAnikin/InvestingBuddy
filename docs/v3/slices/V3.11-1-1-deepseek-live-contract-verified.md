# V3.11.1.1 — the DeepSeek contract, verified

A key was supplied on 2026-09-06. The opt-in live contract test ran. **7 of its 8 live
questions failed**, which is what it was written to do: the adapter had been built from
documentation and had never met the API.

## The security defect it found first

The first failing test printed the live API key into pytest output:

```
self = HttpDeepSeekTransport(api_key='sk-…', model='deepseek-chat', …)
```

A dataclass's default `repr` prints every field, and this object appears in pytest failure
output, exception chains and any log line that formats it. Fixed at the type
(`field(repr=False)`) rather than at each call site that might format it, and pinned by two
tests that run **always**, with or without a key.

**The key used for this validation must be rotated.** It reached terminal output before the
fix landed.

## The finding that changes the provider strategy

**DeepSeek has no server-side web search.**

* `tools[0].type` accepts **only** `"function"`. Every builtin spelling — `web_search`,
  `web_search_preview`, `search`, `browser`, `retrieval` — returns
  *"unknown variant … expected `function`"*.
* A `function` tool named `web_search` merely makes the model **ask the caller** to run a
  search and hand results back. It retrieves nothing itself.
* Asked directly: *"No, I do not have live web browsing in this API call. My knowledge
  cutoff is June 2024."*

DeepSeek was designated the **primary external research runtime** precisely because it was
believed to offer server-side search returning URLs and citations. That premise was wrong.

### What the adapter does about it

`search()` now **refuses**, permanently and with a clear message, instead of falling back to
a function-tool round trip.

The alternative was to let the model answer from memory and present composed URLs as
retrieval — which would manufacture, at cost, exactly the leads the `ResearchLead`
promotion path exists to reject. Refusing is the honest implementation. The general-web leg
stays with the safe fetcher and bounded issuer traversal, which retrieve documents that
exist.

`DeepSeekSearchProvider` degrades correctly on top of it: **0 candidates, 0
`web_search_calls`** (nothing was spent), and a warning that says what happened and does not
claim anything about what the web contains.

## Two more defects the key exposed

### A credential silently re-routed the research path

With a key in `.env` and **every feature flag still off**, `resolve_routing` moved
**Investigator and follow-up research to DeepSeek**. Every acceptance measurement in this
report — three Councils, the cost figures — was taken on Azure OpenAI. Adding a credential
should not change which vendor does the research.

`v3_deepseek_model_enabled` (default **off**) now gates the model leg, so both directions
hold:

| Key | Flag | Routes to DeepSeek |
|---|---|---|
| ✅ | ❌ | **no** — a credential is not consent |
| ❌ | ✅ | **no** — a flag is not a credential |
| ✅ | ✅ | yes (Investigator + follow-up; Chair and Red Team stay Azure OpenAI) |

### Seven tests were asserting a property of the machine

Five of mine and two older ones read a bare `Settings()`, which loads the developer's
`.env`. They asserted "no key is configured" and passed only because no key existed
anywhere. The moment a real one did, they failed — having given false confidence up to
that point. Every DeepSeek-absence test now constructs its absence **explicitly**, and
default-value tests read `Settings.model_fields[...].default` rather than a constructed
object.

That second form matters for more than isolation: `assert settings.deepseek_api_key == ""`
makes pytest **print the live key into the failure diff**, which is how the key leaked a
second time. An AST-based guard now fails the suite if any DeepSeek test compares against
a key attribute — checked structurally rather than by text search, because a grep matches
its own docstring.

## What is now true

`deepseek-chat` completions work, with real usage accounting and correct error
classification. **The model leg is verified; the search leg is verified not to exist.**

14/14 tests pass against the live API. The test remains opt-in — it needs both
`DEEPSEEK_API_KEY` and `ENABLE_INTEGRATION_TESTS=true` — and never runs in ordinary CI.

## What this does not change

`V3_DEEPSEEK_SEARCH_ENABLED` stays **off**, and DeepSeek remains **not release-critical**.
If anything this strengthens that decision: the capability it was chosen for does not
exist, and the three real playbook-gated Councils that convened without it are the
demonstration that the platform does not need it.

`ResearchLead` → Evidence is **still** unexercised with a real external provider, and now
demonstrably cannot be exercised with this one — DeepSeek produces no retrieved sources to
promote. Closing that gap needs a provider that actually searches, which is a decision, not
a defect. See [OPEN_DECISIONS.md](../OPEN_DECISIONS.md) #20.
