# V3.4 Slice 4.3 — DeepSeek as the primary provider

**Branch:** `feature/v3-4-3-deepseek-providers` · **Merge target:** `develop/v3` only
**Migration:** no · **Infrastructure:** no · **Provider dependency:** DeepSeek (approved, pay-as-you-go)
**Flags:** `V3_PROVIDER_RUNTIME_ENABLED`, `V3_DEEPSEEK_SEARCH_ENABLED` — both default **off**
**Implements:** [ADR-048](../../DECISIONS.md), [ADR-049](../../DECISIONS.md)

## Objective

Three adapters behind the slice-4.1 interfaces, making DeepSeek the primary external
research and model provider:

| Adapter | Role |
|---|---|
| `DeepSeekModelProvider` | Cheap and bulk analyst work, document reasoning, structured extraction |
| `DeepSeekSearchProvider` | Server-side web search — the primary external general-web path, replacing the need for Exa or Perplexity |
| `DeepSeekResearchProvider` | First-pass specialist investigation producing **leads**, never findings |

Plus `UnavailableBrowserProvider`, which is the honest form of "V3 requires no paid
crawling service".

## ⚠ What is verified here and what is not

**DeepSeek's exact server-side web-search wire format is NOT verified against the live
API in this campaign.** It is modelled as a tool declaration on an OpenAI-compatible
chat-completions call — which is the convention the platform already speaks — and the
request/response mapping is confined to `HttpDeepSeekTransport.search` and
`parse_search_payload`.

That is stated plainly rather than glossed, because the platform's rule about unverified
claims applies to its own code as much as to a provider's. The FIGI check digit is
deliberately unvalidated for the same reason: **a wrong parser that looks right is worse
than an honest seam.**

Three consequences, all enforced rather than intended:

1. `V3_DEEPSEEK_SEARCH_ENABLED` defaults **off**, so nothing calls an unverified endpoint
   by accident.
2. The parser **tolerates a shape it does not recognise**, returning `[]` with a warning
   that names the keys it actually saw. An unrecognised payload is "no candidates and a
   note saying why" — a research gap somebody can close — never a guess.
3. The tool name is configuration (`deepseek_search_tool_name`), so confirming the
   contract is a settings change plus at most one method.

Confirming it is a small, bounded task: one `_post` body, one parser, and the opt-in live
contract test. **Everything else in this slice is verified against fixtures and does not
depend on it.**

## What comes back is a claim, and the types make that hard to forget

A search result is a `SourceCandidate` — a URL and a claim that a page exists. A model
assertion is a `ResearchLead` whose every asserted field is named `claimed_*`. Neither is
evidence until InvestingBuddy has fetched the source through its own guarded fetcher and
the claim has survived verification (slice 4.4). **A search snippet is never canonical
evidence**, and every snippet is labelled untrusted.

Three parser decisions are worth naming because each closes a specific way a wrong
citation gets in:

- **Prose instead of a tool call yields no candidates.** Pulling URLs out of a sentence
  is how a hallucinated link becomes a source candidate, so it is reported instead.
- **A candidate with no usable `http(s)` URL is dropped, and the drop is reported.** A
  candidate that cannot be fetched cannot become evidence, so it is not a candidate.
- **A malformed date becomes `None`.** A provider returning `"Q1 2026"` where a date was
  expected has told us it does not know the date; coercing that into a day invents one.

## An uncited claim is kept

It is **unverifiable, not wrong** — and `unverifiable_lead_count` is a quality signal
about the provider that only exists if such leads are retained. The system prompt says so
to the provider directly: *"An uncited claim is acceptable and will be recorded as
unverifiable; a wrong citation is not."* A provider told to always cite something will
cite something.

## Degrading honestly is part of the contract

| Failure | Behaviour |
|---|---|
| Unconfigured | `transport_from_settings` returns `None`, matching `get_llm_client`. An unconfigured provider is a degradation the caller handles, not a crash. |
| Search unavailable | Empty result **with a warning saying it is not a statement about what the web contains**. |
| Investigation unavailable | `failed` with a warning — never a partial answer presented as complete. |
| Truncated investigation | `partial`, and the warning says *its absence of further findings is not a finding*. |
| Unparseable completion | An empty payload, not an exception: one failed agent must not end a council. |
| Unparseable investigation | No leads, plus a warning naming the keys it saw. |

The one place an exception does propagate is a bare model completion: the caller asked for
a specific structured output and there is no partial form of it, so it reaches the
caller's own isolation — which the council already has.

## Acceptance criteria

1. **A claim is a lead and a result is a candidate**, with `claimed_*` naming throughout,
   and an uncited claim is retained and counted.
2. **An unrecognised payload produces no candidates and a warning naming what it saw** —
   never a fabricated candidate, never an exception.
3. **Every failure mode degrades honestly**, and no test touches the network.
