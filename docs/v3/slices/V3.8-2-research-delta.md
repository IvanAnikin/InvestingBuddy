# V3.8 Slice 8.2 — the ResearchDelta

## Objective

Answer the question a returning investor actually has:

> **What changed since the previous analysis, and which prior conclusions should be
> revisited?**

## Why now

8.1 gave the platform a "before". Without a delta a refresh either repeats itself or
silently replaces last quarter's conclusions, and neither tells anybody what moved.

## Current implementation

None. A V2 refresh regenerates a report; nothing compares two runs.

## Proposed changes

`research_deltas` (migration 037) and `app/services/memory/delta.py`.

### The hard part is refusing to report a change that is not one

Computing a difference is easy. Each of the following would make a routine refresh look
like a reversal, and each is refused:

| Not a change | Why |
|---|---|
| A **rephrasing** — same slot, different words, no new evidence | Two runs phrasing one conclusion differently are not a change. |
| A **different period** — FY2026 beside FY2025 | A new period's number is not a revision of the old one's. |
| A **different scope** — a segment figure beside a Group one | The CFR failure mode, as a delta rule. |
| **Silence** — the new run never asked | A run that ran out of budget before reaching a question has not disproved last quarter's answer, and it has not resolved it either. |
| A **gap raised again** | That is persistence, not churn. Counting it as both closed and new would report movement where there is none. |

A finding is invalidated only when the new run has a finding in the **same slot** whose
statement differs *and* which rests on evidence the old one did not have. Deterministic, and
no model is consulted.

### The prior finding is not modified

Invalidation is a property of the **relationship between two runs**, not of the old
finding: it was a correct conclusion from the evidence available then, and rewriting it
would make the earlier run's record a lie in service of the later one's convenience. A test
asserts the old row is untouched.

### `unchanged_core_thesis` is computed, never defaulted

False whenever anything was invalidated, and a database CHECK refuses the contradictory
row. A **first run** is not "unchanged" — it has no thesis to be unchanged from, and
saying nothing changed would be the most misleading possible summary of it.

### The defect a real DELETE found

The first draft carried `ck_research_deltas_names_a_run` — "a delta must reference at least
one run". Both foreign keys are `SET NULL`, so deleting both runs nulls both columns, and
the CHECK **refused that update**: the delta could not be pruned, which is the opposite of
"a delta outlives the runs it compares".

Removed, with the rule moved to `persist_delta` where it belongs — it is about *creation*,
not about the row's whole life. After the runs are pruned the delta still carries its counts
and its lists, which is exactly the durable record the table is for. Verified against real
PostgreSQL: deleting both runs leaves **3 deltas surviving, 0 still linked**.

## Security considerations

Every list is bounded at `MAX_LISTED`: a delta listing nine thousand new evidence ids is a
reindex, not a change report. Counts are columns and detail is JSONB, so "how much changed"
is a query rather than a payload parse — and the counts are derived in one place so they
cannot drift from the lists.

## Unit tests

First run: not "unchanged", persistable, and a delta naming no target run refused. What
counts: new evidence; a rephrasing **not** a change; a different number on new evidence
**is**; a different period and a different scope both different slots; the slot being
question/period/scope rather than text. Silence: a question never asked neither invalidated
nor resolved; a previously-open question now answered resolved. Gaps: a re-raised gap as
persistence, a disappeared one as closed, a genuinely new one reported. Persistence: the
prior finding untouched; an unchanged thesis with invalidations unstorable; counts matching
lists; retrieval by entity; the serialised shape answering the investor's question.

## Integration tests

Migration 037 against **real PostgreSQL 16**: six statements, including that an unchanged
thesis with invalidated findings is unstorable, a second delta between the same two runs is
unstorable, and **the delta outlives the runs it compares**.

## Live issuer acceptance

Not performed. Nothing computes a delta on a live path.

## Acceptance criteria

1. A second run reports what changed, and a rephrasing, a new period, a new scope and
   silence are each **not** reported as changes.
2. A prior conclusion contradicted by new evidence is marked invalidated in the delta, and
   the prior finding row is **not** modified.
3. `unchanged_core_thesis` cannot be true beside an invalidated finding — enforced by the
   database.

## Non-goals

- Feeding the delta to the Council. V3.7's `CouncilInput` has the seam; wiring it is one
  small slice once a council actually runs.
- Comparing *facts* directly. The delta compares findings, which already carry period,
  scope and evidence; a fact-level diff needs the fact ids V3.2/V3.3 assign and is a
  separate concern.
- Deciding what to do about an invalidation. That is the Council's job, and the delta's is
  to make sure it is asked.

## Rollback

Migration 037 downgrades cleanly — verified against real PostgreSQL. Nothing imports the
module at runtime.

## Dependencies

V3.5.1 (the ledger), V3.8.1 (finding the prior run).
