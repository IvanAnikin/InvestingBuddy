# V3.2 Slice 2.2 — Company backfill

**Branch:** `feature/v3-2-2-company-backfill` · **Merge target:** `develop/v3` only
**Migration:** yes (027) · **Infrastructure:** no · **Provider dependency:** none
**Feature flag:** `V3_ENTITY_MASTER_ENABLED` (default **off**, shared with 2.1)

## Objective

Link the two identity models: `companies.legal_entity_id` as a **nullable** FK, and
a resumable, idempotent backfill that gives every existing `companies` row a
`LegalEntity` + `Security` + `SecurityListing` derived from what that row actually
records.

Every existing report, citation and `company_id` reference must keep resolving,
and nothing may start the backfill by itself.

## Why now

Slice 2.1 built the entity master beside `companies` and deliberately pointed no FK
at it, so that the link and the backfill would land together and there would never
be a period in which two tables disagreed about which entity a company is. This is
that slice. Until it lands, the entity master is a schema nothing can reach from
the 1,057 existing reports.

## Proposed changes

### Migration 027

```sql
ALTER TABLE companies ADD COLUMN legal_entity_id UUID NULL;   -- FK, ON DELETE SET NULL
CREATE INDEX ix_companies_legal_entity_id ON companies (legal_entity_id);
```

Additive: one **nullable** column and one index, no constraint tightened, no
existing column touched. `release/v2-current` code runs unchanged against a
database with it applied — SQLAlchemy emits explicit column lists, so a V2 `SELECT`
never sees the column and a V2 `INSERT` leaves it NULL.

`ON DELETE SET NULL`, not `CASCADE`: this direction is **lineage**, not composition.
Deleting a legal entity must not delete the company row that a thousand reports
point at (CLAUDE.md rule 15). It is the opposite choice from the FKs *inside* the
entity master, and deliberately so.

### The backfill

`backfill_entities_from_companies(session, *, cfg, company_id=None, limit=200)`:

- selects only `companies` rows with `legal_entity_id IS NULL`, so it is resumable
  and running it twice does nothing the second time;
- derives `entity_key = listing:<venue_key>:<ticker>` — the weakest key, because a
  `companies` row carries no LEI and no CIK;
- creates the entity, one `ordinary_share` security and one listing, all
  `is_primary`;
- sets `companies.legal_entity_id`;
- **is called by nothing.** A backfill that starts itself on the first request
  after a deploy is how a migration becomes an outage. A test asserts no other
  module calls it.

### What the backfill deliberately does not claim

**`jurisdiction` stays NULL.** `companies.country` is where the platform believes
the company *is*, populated largely from the listing venue — and where a company
trades is not where it is incorporated. Writing it into `jurisdiction` would turn a
listing location into a claim about a legal register. NULL means "not established",
which is exactly true.

**`quote_currency` comes from the venue, not from `companies.currency`.**
`companies.currency` does not distinguish a reporting currency from a price-quote
unit, and LSE quotes in pence. The listing takes
`price_quote_currency_for_exchange`, which knows the difference.

**`entity_status` stays `unknown`.** A `companies` row says nothing about whether
the entity is still registered.

**The security is `ordinary_share`.** A `companies` row does not record that its
ticker is an ADR. Slice 2.3, which can consult a source, may correct it — and
`upsert_security` refuses to overwrite a type that has been asserted, so a later
correction cannot be undone by a re-run of this backfill.

### Two companies that derive the same key

`normalize_exchange` collapses NYSE/NASDAQ/AMEX onto `US`, so two `companies` rows
can derive one `entity_key`. When that happens the backfill **checks the name**:

- names agree → both companies link to the one entity. This is the intended
  de-duplication: two rows for one issuer become one identity.
- names differ → the second row is **left unlinked** and counted as `ambiguous`.
  It is not attributed to the first row's entity, because two different names on
  one venue and ticker is evidence of a real problem, and guessing which is right
  is the silent merge the entity master exists to prevent.

`legal_entity_id` NULL is a safe, representable state: the FK is nullable and the
compatibility adapter falls back to the `companies` row.

### The compatibility adapter

`resolve_entity(session, ticker, exchange, cfg) -> EntityResolution`, carrying the
entity (or `None`), the company row it fell back to (or `None`), and **which of the
two answered**. Callers that must not act on a fallback can tell. Dated for removal
when every `companies` row is linked and slice 2.3's resolver supersedes it.

## Security considerations

No network, no new external input. The backfill reads rows the platform already
holds. Its `limit` is bounded and its default is small, so it cannot be turned into
an unbounded table scan by a caller passing a large number.

## Unit tests

- Every `companies` row gets an entity, a security and a listing.
- Idempotent: a second run links nothing further and creates no duplicate.
- Resumable: a `limit` smaller than the row count leaves the rest unlinked and a
  second call continues.
- `jurisdiction` is NULL, `entity_status` is `unknown`, `quote_currency` comes from
  the venue and **not** from `companies.currency` (LSE → `GBX` even when the
  company row says `GBP`).
- `BA`+LSE and `BA`+NYSE backfill to **two** entities.
- Two rows deriving one key with the **same** name link to one entity; with
  **different** names the second stays unlinked and is counted `ambiguous`.
- With the flag off nothing is written and no query is issued.
- Nothing calls the backfill automatically.
- The adapter returns the entity when one exists and reports `companies_fallback`
  when it does not.

## Integration tests

- A `Report` whose `company_id` points at a backfilled company still loads, and
  `reports.company_id` still resolves — the V2 read path is unaffected.
- 027 applied → `downgrade()` → re-applied against real PostgreSQL 16; the column
  and index appear and disappear; `companies` row count and every other column are
  identical before and after.

## Acceptance criteria

1. **Every `companies` row backfills**, and running the backfill twice changes
   nothing the second time.
2. **An ambiguous derivation is left unlinked**, never attributed to another row's
   entity, and it is counted so an operator can see it.
3. **No V2 regression**: existing reports still render, `companies` is otherwise
   byte-identical, and with the flag off the backfill issues no query.

## Non-goals

Resolution from a name or an external source (2.3) · fetching LEIs or CIKs (2.3) ·
relationships, scopes, segments (2.4) · universe generation (2.5) · removing the
`companies` table or the `(ticker, exchange)` key, which stay until a validated
replacement is live.

## Rollback

`git revert` the merge and run `027 downgrade`, which drops one nullable column and
one index. No data outside the entity master is touched.

## What the review pass found

Two defects, both in the same place: the backfill looked up an existing entity by
the **derived key only**.

1. **It could abort the whole batch.** A `listing:` key is the weakest identity, so
   an entity for the ticker may already exist under a stronger one — `lei:…`
   created by slice 2.3 from a real source. Searching by the derived key would miss
   it, create a *second* entity for the same issuer, then hit `upsert_listing`'s
   refusal to move a live ticker between securities. That `ValueError` would abort
   the pass and leave a stray entity with no listing behind it.
2. **It could re-open a window somebody deliberately closed.** If the entity existed
   but its listing had been delisted, `upsert_listing` would create a fresh open
   listing — a backfill silently contradicting a sourced decision.

Both are fixed by looking for the **open listing first**, then the derived key, and
by linking only (no security, no listing) when an entity is found. A re-run now
touches nothing it did not create.

A third finding was a **flaky test rather than a defect**: two colliding rows with
the same `created_at` tie in the `ORDER BY`, so which one creates the entity falls
to a random UUID. That is acceptable behaviour — the guarantee is not *which* row
wins but that exactly one is linked and the other is never attributed to it — so
the test now says so explicitly instead of leaving a flake for somebody to find.
Caught by running the file eight times, which is the "run changed tests in
isolation" rule doing its job.

## Verification performed

### Migration 027 against real PostgreSQL 16

Upgraded to 026, a `companies` row inserted, then 027 applied. A column-by-column
diff of `companies` before and after shows **exactly one added column**,
`legal_entity_id:uuid:YES` — nullable, nothing else touched — and the pre-existing
row survived with the column NULL.

`SET NULL` proved rather than assumed: `confdeltype = 'n'`, and deleting the linked
`legal_entities` row left the company in place with `legal_entity_id` NULL. That is
the direction that matters — the opposite choice would have let an entity deletion
take a company row a thousand reports point at.

`downgrade` restored `companies` to a column list **identical** to its pre-027
state and the row survived; re-upgrade clean. ORM-versus-DDL drift check across all
six tables: `DRIFT: none`. Scratch database dropped; the local dev database
re-checked and still at **018**, with no `legal_entity_id` column.

### One pre-existing test had to be tightened, not weakened

`test_nothing_calls_the_backfill_automatically` (V3.1) was a substring grep for
`backfill_from_extracted_documents` across `app/`. This slice's backfill **cites it
as the precedent** in its docstring, so the grep fired on prose. The fix is
`tests/helpers/source_scan.py`: the same invariant checked against identifiers in
**executable position** via the AST, which is at least as strict for anything that
can run and silent about documentation. A test that fails when somebody documents
the rule it enforces is a test that gets deleted.
