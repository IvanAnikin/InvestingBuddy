# V3.2 Slice 2.4 — Relationships, reporting scopes and segments

**Branch:** `feature/v3-2-4-entity-relationships` · **Merge target:** `develop/v3` only
**Migration:** yes (028) · **Infrastructure:** no · **Provider dependency:** none
**Feature flag:** `V3_ENTITY_MASTER_ENABLED` (default **off**)

## Objective

Make three things representable that the platform currently cannot express:

1. **How entities relate** — parent/subsidiary, predecessor/successor, so consolidated
   versus subsidiary reporting can be reasoned about at all.
2. **Durable scope identity** — the `Group` / segment vocabulary `fact_scope.py`
   already enforces *in memory*, given a row, so a segment can be followed across
   periods and renamings.
3. **The ADR↔ordinary link, with its ratio** — so per-share arithmetic can refuse to
   run rather than silently applying the wrong denominator.

## Why now

`fact_scope.py` makes scope a typed, decidable value and it lives entirely in
memory: `scope_key` is `'group'` or `'segment:<casefolded name>'`, recomputed from a
string on every read. That was the right size for V2 and it cannot answer the
question the corpus and the calculation engine both need — *is this year's
"Watches" the same series as last year's "Specialist Watchmakers"?* A string key
answers "no" and a renamed segment silently becomes two series.

The regression case in front of this work is CFR, and it is unforgiving: **Specialist
Watchmakers figures must never become Group**, and the €107m figure needed a
font-size PDF heading stack to scope correctly at all.

## Proposed changes

### `entity_relationships` — one canonical direction, never two rows that disagree

`parent_of` and `subsidiary_of` are inverses. Storing both invites two rows that
contradict each other and no rule for which wins, so the vocabulary declares a
**canonical direction** and the writer normalises to it: asserting
`subsidiary_of(A, B)` stores `parent_of(B, A)`. The inverse is a *query*, not a row.

Every relationship is typed, sourced, confidence-scored and effective-dated, and an
`is_current` window is `effective_to IS NULL` exactly as listings and identifiers use
it. A partial unique index makes one live relationship per
`(subject, object, type)`.

Self-relationships are refused: an entity is not its own parent, and a schema that
can hold that can hold a cycle nothing detects.

### `reporting_scopes` — durable identity for a scope, and it over-splits

One row per `(legal_entity_id, scope_key)`, where `scope_key` is **exactly**
`fact_scope.FactScope.scope_key` — the same string, so the two cannot drift. The
scope types are `fact_scope`'s plus `region` and `division`, which the architecture
document names and which a segment table alone cannot express.

**A renamed segment produces a new scope.** `scope_key` is derived from the name, so
"Watches" is not "Specialist Watchmakers" and the series splits — *visibly*, as two
scopes. Linking them is an explicit, sourced assertion via `predecessor_scope_id`,
which may only be set together with a `rename_source`. Split-by-default, link on
evidence: the same asymmetry the entity key uses, for the same reason. Silently
merging two scopes would join one segment's figures onto another's history.

### `business_segments` — the segment as *disclosed*, per period

A `reporting_scope` is the durable identity; a `business_segment` is one period's
disclosure of it, carrying **the name as printed** in that period. Unique on
`(reporting_scope_id, period_key)`.

That separation is what makes a renaming visible rather than lossy: two rows with
different `reported_name` and different `period_key`, and — once a source says so —
one scope lineage behind them.

### `securities.underlying_security_id` + `receipt_ratio`

The ADR↔ordinary link belongs between **instruments**, not entities: a depositary
receipt represents underlying shares at a ratio. Two nullable columns on the table
that already exists, plus `refuse_per_share_without_ratio(...)`, which is the point
of storing the ratio — a depositary receipt whose ratio is unknown must make
per-share arithmetic *refuse*, not guess 1:1.

`receipt_ratio` is `NUMERIC(20, 6)` and must be positive. NULL means "not
established", never 1.

## Security considerations

No network. Additive-only: three new tables and two **nullable** columns, so
`release/v2-current` runs unchanged. `entity_relationships` FKs are `CASCADE`
(composition of the identity graph); the `securities` self-FK is `SET NULL`, because
losing an underlying instrument must not delete the receipt that referenced it.

## Unit tests

- `subsidiary_of(A, B)` and `parent_of(B, A)` produce **one** row, in canonical form.
- A self-relationship and a duplicate live relationship are refused.
- A closed relationship window frees the pair; history still queries.
- `reporting_scopes.scope_key` equals `FactScope.scope_key` for group and segment,
  across casing — a test compares the two implementations directly.
- The CFR shape: a `Specialist Watchmakers` scope and a `Group` scope on one entity
  are distinct rows and neither can be read as the other.
- A renamed segment creates a **second** scope; `predecessor_scope_id` cannot be set
  without a `rename_source`.
- Two periods of one scope are two `business_segments` rows and one series.
- `refuse_per_share_without_ratio` refuses an ADR with no ratio, allows an ordinary
  share, and allows an ADR with one.
- A non-positive ratio is refused by the database.
- Flag off: nothing written, no query.

## Acceptance criteria

1. **A relationship has exactly one canonical row** whichever direction a caller
   asserts, and a self-relationship or duplicate live pair is refused.
2. **Scope identity matches `fact_scope` exactly**, Group and segment scopes on one
   entity are distinct, and a rename produces a second scope that can only be linked
   with a source.
3. **A depositary receipt with no ratio makes per-share arithmetic refuse**, and
   028 is additive-only — verified against real PostgreSQL with `companies` and every
   2.1 table unchanged.

## Non-goals

Populating relationships from a source, which needs a filing-structure parser ·
merging two scopes · the calculation engine that will consume the ratio (V3.3) ·
segment *figures*, which are `extracted_facts` and already exist · universe
generation (2.5).

## Rollback

`git revert` the merge and run `028 downgrade`: three tables dropped, two nullable
columns removed.

## What the review pass found

1. **`receipt_ratio`'s direction was underspecified, and the test contradicted the
   docstring.** A bare "ratio" of 4 could mean four receipts per share or four shares
   per receipt, and a reader who guesses wrong is out by **16x**. The function is now
   `underlying_shares_per_unit`, its contract is stated as an equation —
   `per_unit = per_share * multiplier` — and both directions are pinned by a test so
   the meaning cannot drift back into a comment. An ambiguous ratio is worse than no
   ratio, because no ratio makes the arithmetic refuse.
2. **Two `assert`s were doing type narrowing in production code.** `assert` is
   stripped by `-O`, so they read as guarantees and are not. Replaced with explicit
   raises.

## Verification performed

### Migration 028 against real PostgreSQL 16

Upgraded to 027, then 028. A column-by-column diff shows **exactly two** columns added
to `securities` (`receipt_ratio`, `underlying_security_id`) and **`companies`
identical**. `downgrade` restored `securities` to a column list identical to its
pre-028 state and dropped all three tables; re-upgrade clean. ORM-versus-DDL drift
check across all **nine** entity and company tables, including CHECK constraints:
`DRIFT: none`. Scratch database dropped; dev database re-checked, still at **018**.

### Eleven guarantees exercised with real conflicting statements

Directly against PostgreSQL, not through the ORM:

| Attempt | Result |
|---|---|
| one canonical relationship | allowed |
| a duplicate live `(subject, object, type)` | refused, `ix_entity_relationships_current` |
| a self-relationship | refused, `ck_entity_relationships_no_self_reference` |
| Group **and** a segment scope on one entity | both allowed — the CFR shape |
| the same `scope_key` twice for one entity | refused, `ix_reporting_scopes_entity_key` |
| a predecessor with **no** `rename_source` | refused, `ck_reporting_scopes_rename_needs_a_source` |
| a predecessor **with** a source | allowed |
| two periods of one scope / the same period twice | allowed / refused |
| `receipt_ratio = 0` | refused, `ck_securities_receipt_ratio_positive` |
| a positive ratio | allowed |
| deleting the **underlying** security | the receipt survives, `underlying_security_id` NULL |
