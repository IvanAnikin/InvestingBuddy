# V3.3 Slice 3.3 — Calculation engine

**Branch:** `feature/v3-3-3-calculation-engine` · **Merge target:** `develop/v3` only
**Migration:** yes (030) · **Infrastructure:** no · **Provider dependency:** none
**Feature flag:** `V3_AGENT_TOOLS_ENABLED` (default **off**, shared with 3.1)

## Objective

Deterministic arithmetic in deterministic code, with a refusal for every way two valid
numbers can fail to belong in one expression — and a persisted record of both the
results and the refusals.

## Why the engine is mostly refusals

Computing is one line per metric. Every arithmetic defect this platform has had was a
float that was *valid* — a real number, correctly parsed — combined with another valid
float that measured something else: a segment figure over a Group figure, an interim
number against an annual one, a figure in thousands divided by a figure in millions.

So the unit of computation is a `Quantity` carrying its period, scope, unit, currency
and scale, and combining two of them asks a question that can be answered **no**. The
acceptance strategy states the demonstration in exactly those terms: *a calculation
with incompatible periods or scopes is refused, not computed.*

## The six checks, in the order they matter

1. **Every input present.** A metric computed from a subset of its inputs is a
   different metric.
2. **Period.** `ReportingPeriod.comparable_with` is *called*, not re-implemented — it
   already refuses cross-type comparison and refuses an unknown period against
   anything, including another unknown.
3. **Scope.** Same scope key, and an unknown scope is refused, because **unknown is not
   Group**. The report layer's implicit convention is right for a rendered report and
   would produce a Group margin out of a figure nobody attributed.
4. **Currency.** Refused on a mismatch, never converted: an FX rate this platform did
   not source is an invented number (CLAUDE.md rule 6).
5. **Scale.** One known and one unknown is the pair with no safe reading. An undetected
   1000× does not look broken — it looks like a plausible percentage, which is worse.
6. **Domain.** A zero denominator and a non-positive growth base are refused rather
   than clamped, because a clamped input produces a number that looks like an answer.

Only after all six does anything multiply.

## The one cross-scope definition, declared

`segment_revenue_mix` requires a **segment** numerator and a **Group** denominator.
Declaring the exception per definition is what lets every other definition refuse a
scope mismatch outright instead of having a general "sometimes scopes may differ"
escape — and a test asserts it is the only one. Its result is stamped with the
**segment** scope, because the answer is a property of the segment.

## Ten definitions, each versioned

`gross_margin` · `operating_margin` · `net_margin` · `net_debt` ·
`net_debt_to_ebitda` · `fcf_conversion` · `capex_intensity` · `return_on_equity` ·
`revenue_cagr` · `segment_revenue_mix`.

`net_debt_to_ebitda` takes net debt as an **input** rather than recomputing it, so a run
that already refused `net_debt` cannot silently produce a leverage ratio. Each
definition carries a `version`: a silently redefined metric makes every historical value
a different metric wearing the same name, which is why
`CURRENT_EXTRACTION_PIPELINE_VERSION` exists and the same reason applies here.

## The tool binds; the engine refuses

`get_calculated_metrics` chooses which fact fills which role — which is where a wrong
answer comes from — and **never picks between two candidates**. Two active validated
facts with differing values for one role is the conflict `get_financial_series` already
reports, refused here for the same reason: the platform does not choose between two
figures it cannot reconcile. Two facts with the *same* value are agreement, not a
contradiction, and are allowed.

`scope` is required and **`any` is not available**: arithmetic over a mixture of scopes
is precisely what the engine exists to refuse.

## What the review pass and the tests found

1. **Identical known scales were being converted to base units.** Two figures both in
   millions came back as `-4100000000` where the documents said `-4100` — the same
   number in a form no reader recognises, with the shared scale thrown away for
   nothing. Conversion now happens only when the scales *differ*, and a money result
   carries the inputs' shared scale. A `NULL` result scale now means **base units**,
   which the column comment distinguishes from a fact's `NULL` scale meaning "the
   document never said".
2. **Two `mypy` errors** the gate caught, both real: an inferred `str` where
   `str | None` was assigned, and an index on an `Optional`.

## Acceptance criteria

1. **A calculation with incompatible periods or scopes is refused, not computed** — an
   unknown period, a period mismatch, a cross-type CAGR, an unknown scope and a scope
   mismatch each produce a refusal with a distinct reason and **no value**.
2. **A refused row cannot carry a value**, enforced by the database.
3. **Every attempt is persisted** with its definition version, formula, inputs by role
   and input fact ids, so a result is reproducible and a wrong input is attributable.

## Non-goals

Sector KPIs, which belong with the playbooks that will require them (V3.6) · dilution
and incremental margin, which need share counts and two periods of two metrics · peer
comparison (V3.4 sources) · any FX conversion · a model computing anything.
