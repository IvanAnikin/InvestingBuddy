# V3.11.1.2 — DeepSeek's web search exists; it was on the other endpoint

## What this corrects

V3.11.1.1 concluded, from a live probe, that **DeepSeek has no server-side web search**.
It changed `search()` to refuse permanently, recorded that the premise for choosing
DeepSeek as the primary external research runtime had been wrong, and opened
[OPEN DECISION #20](../OPEN_DECISIONS.md) on whether to buy a provider that does search.

That conclusion was wrong, and the way it was wrong is worth more than the fix:

> **The probe only ever asked `POST /chat/completions`.**

DeepSeek serves two OpenAI-compatible APIs. The builtin web-search tool lives on
`POST /responses`. Measured live on 2026-09-07 with the same key that produced the
original finding, the capability ADR-048 selected DeepSeek for is real: it issues queries,
opens pages, reads them, and reports the URLs it opened.

**An absence measured on one endpoint is not an absence.** That is now pinned by two live
tests rather than by a sentence — test 5 keeps the true part of the old measurement
(`/chat/completions` really has no builtin tools) and test 7 records what the other
endpoint does.

## The contract, as measured

Eight live runs on `deepseek-v4-flash`, public data only, key never printed.

| # | Question | Measured answer |
|---|---|---|
| 1 | Does `POST /responses` exist? | **Yes**, 200 |
| 2 | Is `tools: [{"type":"web_search"}]` accepted? | **Yes** — echoed back as `{"type":"web_search","search_context_size":null,"user_location":null}` |

| 7 | Are the URLs real? | Yes — e.g. Pandora FY2025 revenue confirmed against `pandoragroup.com/news/27811` |

### Three of those changed the design

**A 200 is not a capability.** `/responses` is *permissive* where `/chat/completions` is
strict: it accepts an unknown tool type, an unknown `include`, an unknown field inside a
known tool, and silently drops each one. So the adapter proves execution from the `tools`
echo **and** the presence of `web_search_call` items. Without that, "the tool never ran"
reads as "the web has nothing" — and only one of those is a claim about the world.

**There are no structured citations, so the retrieval trace is the provenance.** A
candidate is a page the provider *opened*; a URL that appears only in the answer's prose
is counted as `cited_but_never_opened` and never promoted. That count is a fabrication
signal this platform did not previously have — and it matters here specifically, because
this model's own knowledge cutoff is June 2024, so a cited page it never visited may be
recalled rather than found.

**The vendor's safety controls do not work, so ours are authoritative.** `max_tool_calls`
and `filters.allowed_domains` are both accepted and ignored. A bound that is not enforced
is worse than no bound, because it gets trusted. InvestingBuddy now owns the domain
restriction, the candidate ceiling, de-duplication, URL canonicalisation and the SSRF host
pre-filter, and the telemetry says so in as many words:
`domain_filter_enforced_by: investingbuddy_client_side`.

The same standard applies to the bound this slice *does* set. `max_output_tokens` caps
what the model **writes**; every page it opens comes back as **input** tokens, which no
request parameter bounds — which is why an observed request sat at ~41k tokens behind a
4,000-token output ceiling. The real ceiling on one call is the timeout, and the ceiling
on a run belongs to `ResearchBudget`, above this layer. Saying "the two bounds the API
honours" without that distinction would have been the same overclaim in our own voice.

### A second key leak, found by this slice's own test run

The rewritten live test failed once on an assertion about `Settings().deepseek_model` — an
innocent field — and pytest rendered the **whole `Settings` object** into the failure
diff, API key included.

V3.11.1.1's AST guard could not have caught this: it forbids comparing a *key attribute*,
and this compared a model name. No rule about how to write assertions covers every object
that might carry a credential into a formatter, so the guarantee moved to the type, exactly
as it did for the transport in V3.11.1.1:

```python
deepseek_api_key: str = Field(default="", repr=False)
```

Applied first to the five `*_api_key` fields — and review caught that as **not enough**:
`database_url` (which carries the DB password in every deployed environment) and
`staging_basic_auth` (literally `user:pass`, and load-bearing for API access control)
were still printed by any `repr(Settings())`, while the structural guard matched only on
a name suffix and therefore passed anyway.

The predicate is now a named list, `CREDENTIAL_SETTING_FIELDS`, with two tests: one that
every listed field is non-printing, and one that the list has not drifted from the
settings in either direction. The behavioural test was also rewritten — its first version
asserted `planted not in repr(...)`, and pytest's assertion rewriting would have printed
that whole rendered `Settings` on failure, which is the leak it exists to prevent.

> ⚠️ **The validation key must still be rotated.** V3.11.1.1 already required this; this
> slice is a second reason, not a replacement one.

## What did not change

* **A candidate is still not evidence.** It is a URL InvestingBuddy has not fetched.
  Promotion runs through the platform's own guarded fetcher and the verification gate,
  untouched by this slice.
* **The `ResearchLead` path is now *staffable*, and is still not staffed.** An earlier
  draft of this document claimed the gap was closed. It is not:
  `DeepSeekResearchProvider.investigate()` still runs on `/chat/completions` with no
  retrieval, and the search leg emits `SourceCandidate`s — a URL and no claim — which
  `verify_lead()` cannot consume. What changed is that the reason V3.11.1.1 gave for the
  role being permanently unstaffable is gone. Wiring the search tool into the
  investigation is a separate slice.
* **Both flags stay off — and the search flag now actually gates.** Review found that
  `V3_DEEPSEEK_SEARCH_ENABLED` had **no consumer in application code**: the hard refusal
  this slice removed was the real brake, so making search work had quietly removed it.
  `DeepSeekSearchProvider.search()` now returns the honest-degradation response without
  touching the transport unless the flag is on. A verified capability is not a decision to
  spend on it, exactly as a credential is not consent. With the flags off, behaviour is
  bit-for-bit what it was.
* **DeepSeek is still not release-critical.** The three real playbook-gated Councils
  convened without it and still do.

## What the independent review changed

The first draft passed every gate and was still wrong in four ways worth recording,
because three of them are the *same failure mode this slice is about* — a claim that
outran its evidence.

| Found | Why it mattered |
|---|---|
| **`V3_DEEPSEEK_SEARCH_ENABLED` had no consumer in application code.** | The removed refusal *was* the gate. Making search work silently removed the brake while three documents said the flag held it. Now enforced in `DeepSeekSearchProvider.search()`, which never touches the transport with the flag off. |
| **"Every credential field is now `Field(repr=False)`" was false.** | Matching on the `*_api_key` suffix missed `database_url` (the DB password) and `staging_basic_auth` (`user:pass`) — and the structural test was scoped to the same suffix, so it passed anyway. A named `CREDENTIAL_SETTING_FIELDS` list now drives both, with a drift test. |
| **The action dispatch was a deny-list of one.** | Only `search` was special-cased, so *every* other action carrying a URL was promoted as a page the provider opened. The day `include: [...sources]` starts working, that would have promoted never-visited search results as retrieved — precisely this slice's thesis, inverted. Now an allow-list of the two measured retrieval actions. |
| **OPEN DECISION #22 was struck through on a producer that does not exist.** | See "What did not change" — the role became *staffable*, not staffed, and the first draft claimed the stronger thing. |

Also corrected: truncation was parsed and then dropped (a search cut off at its ceiling
read as complete); `web_search_calls` counted page-opens as searches; the
cited-vs-opened comparison flagged a trailing slash as fabrication; `domains=[""]`
rejected everything and blamed the domain filter; and `_reduce_responses` — the one
function that touches the real wire body — had no test at all, only the opt-in live one
that never runs in CI. It now has a **golden fixture captured from a real `/responses`
body**, which is the thing this slice criticised its predecessor for lacking.

## What the security review changed

A separate security pass over the same diff cleared the credential mechanism, the SSRF
boundary and the spend gate — and found one HIGH item, in the same category as everything
else this slice is about.

**The test guarding the leak was itself the leak.** `test_a_configured_transport_repr_redacts_it_too`
read the live key into a local and asserted `key not in repr(transport)`. It runs
**always**, not only under the live opt-in. pytest's assertion rewriting renders both
operands plus an "is contained here" expansion, so on the one day that test can fail — the
day `repr=False` regressed — it would have printed the real key **three times**. Verified
empirically with a planted value before fixing.

Worse, this slice's own AST guard was blind to it: it matched an `ast.Attribute` named
`deepseek_api_key` appearing as a compare operand, and binding the value to a local first
turns that into an `ast.Name`. So the guard passed while the path was open. The guard now
follows local bindings **and** is scoped to `assert` statements — which is the precise
rule, because a plain `leaked = key in repr(t)` renders nothing. Both directions are
proven: re-introducing the old line makes the guard fail; removing it makes it pass.

Carried forward from V3.11.1.1 rather than introduced here — and fixed here, because a
slice that claims to close a leak class does not get to leave an instance of it standing.

Four lower-severity items, all hardened:

| Item | Change |
|---|---|
| Prose URLs in the trace are unfiltered, and sat beside filtered lists with no marker | Key renamed to `cited_but_never_opened_unfiltered` and documented as a diagnostic that nothing may fetch |
| `enabled=True` can bypass the search gate by construction | Structural test: no module under `app/` may pass `enabled=` to `DeepSeekSearchProvider` |
| Caller-supplied `domains` interpolated verbatim into model instructions | Validated against a hostname pattern, length-capped, and limited to 20 entries |
| `_clean_domains` stripped a leading dot but not a trailing one | Both stripped, so `"example.com."` matches |

The SSRF boundary was probed independently by both the reviewer and this slice against
userinfo (`https://good.example@evil.com/`), suffix confusion, ports, case, IDN/punycode,
trailing dots, `file:`/`javascript:`, `169.254.169.254`, `[::1]` and `localhost` — all
resist, and the fail-closed cases fail closed. The one documented residual is
pre-existing and unchanged: `is_safe_public_host` is a name-based pre-filter that does not
resolve, so decimal/hex IP literals and `127.0.0.1.nip.io` pass it. The safe fetcher's
`assert_resolved_ip_public` is what closes DNS rebinding, and the parser's comment now says
so rather than claiming to be "the same predicate the safe fetcher uses".
