# V3.4 Slice 4.9 — the production PostgreSQL search backend

## Objective

Give the corpus a search backend that survives a process restart, per
[ADR-047](../../DECISIONS.md): retrieval lives in the database that already holds the
corpus, so entity, period and scope filters apply in the same transaction as the data
they filter.

## Why now

V3.1.4 shipped `SearchBackend`, the rank fusion and a complete in-memory reference
implementation, and **stopped at the backend-selection gate** because the choice was the
user's. The user made it. Everything downstream — the corpus search tool (3.4), the
Director's retrieval (V3.5), the Council's evidence (V3.7) — currently searches a Python
dict that dies with the worker.

## Current implementation

- `app/services/corpus/search/types.py` — `CorpusChunk` / `CorpusFilters` / `CorpusQuery`
  / `CorpusHit` / `SearchBackend`, and the two refusals (`VectorOnlyRetrievalError`,
  `UnscopedRetrievalError`).
- `app/services/corpus/search/fusion.py` — reciprocal rank fusion, backend-neutral.
- `app/services/corpus/search/backends/memory.py` — BM25 + cosine, the reference.
- `app/models/research_chunk.py` — the chunks are already rows, with every filter key
  denormalized onto them.

## Proposed changes

### What ADR-047 asked for, and what is actually installable

The lexical leg needs **no extension**: a GIN index over `to_tsvector('simple', text)`.

`pgvector` is **not available** on the PostgreSQL this project runs — checked, not
assumed: `SELECT count(*) FROM pg_available_extensions WHERE name='vector'` returns `0`
on `postgres:16-alpine`. On Azure it is a server-parameter change to a **deployed**
server, which this campaign must not make. [ADR-053](../../DECISIONS.md) records the
amendment: embeddings are stored portably as JSONB with their model and dimension, the
semantic leg is a bounded rerank rather than a nearest-neighbour search, and it is off.

### De-indexing is an UPDATE

For every other backend "remove this version from the index" is a deletion. Here the
chunk rows *are* the corpus, and deleting them would destroy the spans old citations
resolve against. `delete()` clears `indexed_at`; the span stays citable and stops being
retrievable, which is exactly what reprocessing needs.

## Security considerations

- The `tsquery` is built from the shared tokeniser, whose character class admits only
  `[a-z0-9]` runs with internal `-`/`/`, so it cannot carry a `tsquery` operator. Each
  token is additionally wrapped as a quoted lexeme and the whole string is passed as a
  **bind parameter**. Three independent reasons it cannot be an injection.
- `indexable` is enforced at write time *and* in the query filter. A row that is in the
  index and excluded at read time is one forgotten `WHERE` clause from being returned.
- Cross-entity search still has to be asked for, and semantic-only retrieval is still
  refused. Both rules live in `CorpusQuery.validate`, which this backend calls first.

## Unit tests

Query construction and its injection resistance; the deterministic embedding provider;
the factory including an unknown name; index state, re-indexing, de-indexing and
embedding attribution on sqlite; **filter parity** — every dimension of `_filter_clauses`
evaluated against the same rows as `CorpusFilters.matches`, so a filter cannot be
implemented in one backend and forgotten in the other.

## Integration tests

Against **real PostgreSQL 16**, on a scratch schema created and dropped per run: lexical
ranking, the un-indexed row never returned, the period filter applied inside the search,
a segment chunk excluded from a Group query, hybrid degrading to lexical, the semantic leg
running on deterministic embeddings, an embedding from another model never compared, and
an `EXPLAIN` asserting the GIN index is the one PostgreSQL plans against. Plus: the two
backends return the same top hits for the same query.

## Live issuer acceptance

Not performed — V3 is not deployed. The real-PostgreSQL tests are the strongest available
substitute and they run against the same engine version the deployed database uses.

## Acceptance criteria

1. A lexical query returns the right chunk from real PostgreSQL, ranked, with every
   metadata filter applied **inside** the statement — demonstrated by a chunk that is the
   better textual match being correctly excluded by a period filter.
2. De-indexing a version leaves every span present and citable and returns none of them.
3. The semantic leg is off by default, declares itself non-exhaustive, and never compares
   two models' vectors.

## Non-goals

- A `pgvector` column or an IVFFlat index. Not installable here (ADR-053).
- A production embedding provider. A spend decision on a path nothing yet consumes.
- Routing anything to this backend. `V3_SEARCH_BACKEND` defaults to `memory`; switching a
  running system's retrieval is a behaviour change and gets its own gate.
- Stemming, synonyms, or a second text-search configuration.

## Rollback

Set `V3_SEARCH_BACKEND=memory` (the default). Migration 032 downgrades cleanly — verified
by dropping and re-adding every column and the index against real PostgreSQL.

## Dependencies

V3.1.4 (the interface), V3.1.5 (chunks as rows), ADR-047, ADR-053.
