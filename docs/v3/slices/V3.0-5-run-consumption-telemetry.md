# V3.0 Slice 5 — Run consumption telemetry

**Branch:** `feature/v3-0-5-run-consumption-telemetry` → `develop/v3`
**Status:** `IMPLEMENTED`
**Migration:** **020** (created; **not applied to any deployed environment**)

## Objective

Record what a research run consumes, in vendor-neutral units, with cost derived
rather than stored — and put the budget enforcement point in place without
inventing the numbers that belong to the user.

## Why now

Two questions V3 cannot answer, and both gate real decisions:

- **What does one run consume?** [OPEN DECISION #14](../OPEN_DECISIONS.md#14-research-mode-budgets)
  says the mode budgets should be "derived from measured live runs rather than
  guessing". Nothing measures them. Token counts exist per council attempt
  (`token_pacer.CouncilUsageTracker`) and are logged as events, but they are
  never aggregated to a run and never persisted — so "what did the Pandora run
  cost" can only be answered by grepping logs, and only while the logs are
  retained.
- **Which provider is worth its price?** The provider strategy's central metric
  is `cost_per_verified_finding`. Its numerator has to be recorded per run before
  any of it can be computed.

## Changes

**New:** `app/services/consumption.py` (pure: units, prices, budget — no DB, no

## Design decisions worth stating

### Zero is not the same as "not measured"

This is the one thing that would quietly corrupt every later comparison. Most
units have no producer yet — there is no `SearchProvider`, no browser, no
per-page counter — and a record reporting `web_search_calls: 0` would be
asserting that no searches happened, which is a different claim from "nothing
here counts searches". Every record therefore names the units it actually
instrumented, and `to_dict()` emits `not_instrumented` explicitly rather than
leaving a reader to subtract two lists.

It is the fact-count discipline again: the rule is not to make the numbers agree,
it is to say which population each number counts.

### Units are vendor-neutral; money is derived

Consumption counts things that happen; cost comes from a configurable price book.
A vendor price change is then a config change, and historical runs stay
comparable instead of being denominated in a price that no longer exists.
`estimated_cost_usd` is **NULL when no price book is configured** — "we do not
know what this cost" and "this cost nothing" are different statements and only
one of them is true. An unpriced unit is named in `unpriced_units` rather than
silently contributing zero, because an estimate missing its dominant term is
worse than no estimate.

### Every budget limit is unbounded by default

The numbers are [OPEN DECISION #13](../OPEN_DECISIONS.md#13-model-cost-thresholds)
and [#14](../OPEN_DECISIONS.md#14-research-mode-budgets), **both user-owned**, and
#14 explicitly wants them derived from the measurements this slice produces.
Guessing a ceiling and shipping it as a default would be answering a question
that was asked of somebody else — with the failure mode that an invented ceiling
silently truncates a legitimate research run. The enforcement point exists now so
that setting a number later is configuration, not code.

`ResearchBudget.check` takes what is **about to be spent**, not only what has
been: a run that discovers it is over budget after a $2 Deep Research call has
not been bounded, it has been audited. And `BudgetExceeded` names the limit,
because "budget exhausted" without saying which one is a dead end for whoever has
to tune it.

### A failed run is recorded too

A run that failed after ingesting eleven documents and running six council agents
spent a real budget. Recording only successes would make every average taken from
this table an average of the runs that went well — precisely the number nobody
needs. Every FK is nullable and `SET NULL` for the same reason.

### Recording never fails a run

A research run that completed and then lost its report to a telemetry insert
would be an unusually expensive way to learn nothing. The measurement is the
least valuable thing the run produced.

## DB migration

**Yes — 020, additive only.** One table, nothing existing touched, so
`release/v2-current` runs unchanged against a database with it applied.

**Verified against real PostgreSQL 16 on a SCRATCH database:**
`ib_v3_migcheck_020` created, `alembic upgrade head` (014 → 020), all four FKs
confirmed `confdeltype = n` (SET NULL), three indexes present, `downgrade 019`
(table dropped, head back to `019`), `upgrade head` again, then the scratch
database dropped. **The dev database stayed at 018 throughout and was never
touched.**

## Feature flags

`v3_run_consumption_enabled` (default **False**), paired with 020 — turn it on
only where the migration has been applied. It is the switch that *produces* the
evidence for OPEN DECISION #14; it spends nothing.

Seven budget ceilings and seven prices, all `0` (= unbounded / unpriced).

**Deprecation plan:** the enable flag is removed once the table has carried live
runs and the measurement is unconditional. The budget ceilings are permanent
configuration, not flags.

## Security considerations

- Counts and durations only. No prompts, no completions, no evidence text, no
  URLs, no provider identifiers beyond what the council already logs.
- `consumption_json` is generated from typed fields; nothing from a provider
  response reaches it.
- No new endpoint and no auth change. The table is not exposed by any route.
- A `BudgetExceeded` is classified **permanent** for the worker: retrying spends
  the budget again to reach the same ceiling.

## Live issuer acceptance

**Not performed** — V3 is not deployed and 020 has not been applied anywhere.

unproven is exactly what it exists to produce: real consumption figures for
PNDORA/CFR/MRNA/ASML runs. Recorded as an explicit gap rather than implied.

## Acceptance criteria

1. **A run's consumption is recorded in vendor-neutral units with cost derived.**
   ✅ `TestPersistence::test_a_run_is_recorded`,
   `TestDerivedCost::test_a_price_change_is_a_config_change`.
2. **A zero is never mistaken for a measurement.** ✅
   `test_a_record_names_what_it_did_not_measure`,
   `test_a_council_result_without_consumption_reports_nothing_measured`.
3. **The budget is checked before spending, names its limit, and is unbounded by
   default.** ✅ `TestBudget`.
4. **Migration 020 applies, rolls back and re-applies on real PostgreSQL, with
   SET NULL FKs.** ✅ verified on a scratch database; dev DB stayed at 018.
5. **No V2 regression.** ✅ suite 4608 → 4647 (+39, none lost); `ruff` clean;
   `mypy app` 71, unchanged.

## Non-goals

- Choosing the budget numbers. User-owned.
- Enforcing budgets inside the council's own loop — there is no multi-round loop
  yet; that is V3.5.
- Instrumenting units that have no producer. Naming them unmeasured is the point.

## Rollback

`git revert` the merge commit, then `alembic downgrade 019` if 020 was applied
anywhere. With the flag off nothing writes to the table, so a revert is inert.
