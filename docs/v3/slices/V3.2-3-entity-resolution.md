# V3.2 Slice 2.3 — Entity resolution

**Branch:** `feature/v3-2-3-entity-resolution` · **Merge target:** `develop/v3` only
**Migration:** no · **Infrastructure:** no · **Provider dependency:** none (contract + fake; live adapters are 2.3.1)
**Feature flag:** `V3_ENTITY_MASTER_ENABLED` (default **off**, shared with 2.1/2.2)

## Objective

Answer "which legal entity is this?" with a **state**, not a guess — `resolved`,
`ambiguous`, `conflicting` or `unresolved` — and give an identifier *claim* a
verification gate before it can attach to an entity.

Slices 2.1 and 2.2 built identity and filled it from `companies`. Everything they
produced is keyed `listing:<venue>:<ticker>`, the weakest form. This slice is where
a stronger identifier can arrive, be checked, and either be recorded or be refused
with a reason.

## Why now

The entity master currently answers only exact questions. Every real identity
question is inexact: a name from a document, a ticker from a user, a LEI from a
registry that may disagree with what is already stored. Without a resolver, each
caller invents its own matching rule — which is exactly how `scope` came to have
three incompatible interpretations in three layers before `fact_scope` existed, and
how a ticker string came to be treated as identity in the first place.

## Current implementation

| Path | State |
|---|---|
| `app/services/entities/master.py` | `find_entity_by_identifier`, `resolve_entity_by_listing` — exact lookups that return `None` rather than a state. |
| `app/services/entities/compatibility.py` | `resolve_entity(...)` — exact listing lookup with a `companies` fallback. |
| `app/services/entities/vocabulary.py` | `RESOLUTION_STATES` and `NON_ACTIONABLE_RESOLUTION_STATES` already defined in 2.1, deliberately, so schema and resolver could not drift apart. |
| `app/services/identifier_resolver.py` | V2's EODHD symbol resolver. In memory, per call, nothing persisted, and it resolves a *symbol*, not an entity. Untouched. |
| `app/integrations/providers/gleif_provider.py` | A live GLEIF client with a **pure** `_parse_gleif_record`. Not wired here — see non-goals. |

## Proposed changes

### Evidence has strength, and weak evidence is never sufficient

Candidate generation produces `MatchEvidence(kind, strength, detail)`:

| Kind | Strength | Why |
|---|---|---|
| `identifier` | `decisive` | A LEI, CIK or ISIN is issued to one subject by a registry. |
| `listing` | `strong` | One ticker on one venue is one instrument at a time — the database already guarantees it. |
| `alias` / `name` | `weak` | Two companies may legally share a name. **Never sufficient on its own.** |

### The decision rules

1. No candidate → `unresolved`. Not an error: a company the platform has never seen.
2. One entity, and at least one `decisive` or `strong` evidence → `resolved`.
3. Two or more entities from `decisive`/`strong` evidence → the query's own inputs
   disagree with each other, which is `conflicting` — stronger than ambiguous,
   because something upstream is wrong and a human should see it.
4. Only `weak` evidence → `ambiguous`, **even for a single candidate**. The platform
   cannot distinguish "this is the one" from "a second company of this name exists
   and has not been ingested yet", and a name match is how one issuer's numbers get
   attributed to another.

Only `resolved` is actionable. `NON_ACTIONABLE_RESOLUTION_STATES` from 2.1 is the
check a call site makes, so "never silently merge" is a membership test rather
than a rule to remember.

### An identifier claim is a claim until it is verified

This is the promotion path of
[DATA_AND_EVIDENCE_ARCHITECTURE.md §4.1](../DATA_AND_EVIDENCE_ARCHITECTURE.md#41-the-promotion-path)
applied to identity: a provider's identifier is not evidence, it is an
`IdentifierClaim`, and it must survive a gate.

`verify_identifier_claim(...)` refuses with a **recorded reason**:

| Reason | When |
|---|---|
| `invalid_identifier` | It fails its own checksum or shape. |
| `held_by_another_entity` | The identifier is currently held by a different subject. **Never overwritten** — which of the two is right is an evidence question, not a write order. |
| `venue_not_sec_eligible` | A CIK claimed for a listing on a venue SEC's ticker index does not cover. **This is the Boeing bug expressed as a rule** rather than as a special case. |
| `subject_mismatch` | An ISIN claimed for a legal entity, or a LEI for a security. |
| `no_source` | The claim names no source. |

A rejected claim is **returned with its reason** rather than dropped — the same
"store rejected companies and failed analyses, they are valuable learning data"
rule (CLAUDE.md rule 8) applied to identity, and what makes a source's accuracy
measurable later.

### Promotion never rewrites the key

An entity created as `listing:XCSE:PNDORA` that later acquires a LEI **keeps its
key**. The LEI becomes an `entity_identifiers` row. Rewriting the key would be an
implicit merge of the identity's history and would break every `entity_key` a
caller had recorded. Pinned by a test.

### `IdentifierSource` is a contract with a fake, not a live client

```python
class IdentifierSource(Protocol):
    source_id: str
    schemes: frozenset[str]
    async def lookup(self, query: IdentifierQuery) -> list[IdentifierClaim]: ...
```

`StaticIdentifierSource` is the reference implementation used by every test. **No
live adapter ships in this slice** — GLEIF and SEC are network paths and they get
their own slice (2.3.1), which is where rate limits, failure modes and opt-in test
gating belong. The existing "no network import in this package" test from 2.1
covers the new modules automatically and fails if one appears.

## New modules

| Module | Responsibility |
|---|---|
| `app/services/entities/resolution.py` | `EntityQuery`, `MatchEvidence`, `EntityCandidate`, `ResolutionOutcome`, `resolve(...)`. |
| `app/services/entities/claims.py` | `IdentifierClaim`, `IdentifierSource`, `StaticIdentifierSource`, `verify_identifier_claim(...)`, rejection reasons. |

## Security considerations

No network, no migration, no new external input surface. Every identifier still
goes through `normalize_identifier`, so a claim from any future source is
checksum-checked before it can reach a query. The `venue_not_sec_eligible` rule is
a security control as much as a correctness one: it is what stops a ticker string
becoming another issuer's regulatory identity.

## Unit tests

- The four states, each reached by a distinct, realistic input.
- A single **name-only** match is `ambiguous`, not `resolved`.
- A LEI and a ticker pointing at two entities is `conflicting`, and the outcome
  names both.
- `resolved` requires `decisive` or `strong` evidence; the actionable check is
  membership of `NON_ACTIONABLE_RESOLUTION_STATES`.
- Every rejection reason, including a CIK claimed on LSE.
- A verified claim is recorded, is idempotent, and **does not rewrite `entity_key`**.
- A claim for an identifier held by another entity is refused and the existing row
  is unchanged.
- With the flag off, `resolve` returns `unresolved` and issues no query.

## Acceptance criteria

1. **Two listings resolve to one entity; an ambiguous match raises a state instead
   of merging.** A name-only match never returns `resolved`.
2. **An identifier claim that fails verification is refused with a reason** and the
   entity is unchanged — including a CIK claimed for a non-SEC-eligible venue.
3. **Promotion adds an identifier and never rewrites `entity_key`**, so a caller
   holding the old key still resolves.

## Non-goals

Live GLEIF/SEC/OpenFIGI adapters (2.3.1) · persisting an `entity_ambiguous` gap,
which needs the Research Ledger (V3.5) and is returned rather than stored here ·
merging two existing entities, which needs a provenance-preserving merge record and
is not in V3.2 · fuzzy or phonetic name matching · relationships (2.4) · universe
generation (2.5).

## Rollback

`git revert` the merge. No migration, no schema change, nothing to undo.

## What the review pass found

Five things, and the last one is the most valuable finding in V3.2 so far.

1. **A losing candidate was being dropped.** Strong evidence beating weak evidence
   is correct, but a caller that supplies a ticker *and* a name, and finds the name
   matching a **different** entity, has learned something real — that is the class
   of defect this repository has already seen live, where a report's `legal_name`
   came back as the ticker. `ResolutionOutcome.dissenting_candidates` now carries
   the losers and the reason counts them.
2. **An acceptance did not say what had been checked.** `checksum_verified` being
   false is not a weaker acceptance — it means the scheme *has* no check digits
   (CIK) or that its variant is deliberately not validated (FIGI). The outcome
   detail now states which, so a reader does not have to infer it.
3. **A local import inside a helper** for no reason; moved to the top.
4. **A `mypy` regression** the gate caught — a `set[str | None]` where `set[str]`
   was declared. Fixing it surfaced the fifth finding.
5. **`is_sec_eligible(None)` returns `True` by design, and inheriting that here was
   a fail-open on the most dangerous rule in the module.** That default is correct
   where it lives: V2's legacy ticker-only flow passes no exchange, and treating an
   absent one as ineligible would regress every `AAPL`/`MSFT` lookup to "not
   sourced". But a **listing row** is a different thing — it always has a venue, and
   `exchange_code` NULL means the platform holds a listing whose venue it *cannot
   name*. Inherited unchanged, an unnamed venue would have read as SEC-eligible and
   a derived CIK would have been accepted: the Boeing bug, through the one gate
   built to stop it. `_listing_is_sec_eligible` now decides the empty case
   explicitly, in the safe direction, and says in its docstring why it does not
   simply delegate.

The fifth is the pattern worth carrying forward: **a shared helper's default can be
right at one call site and wrong at another**, and "we reused the existing function"
is not the same as "we applied the existing rule".
