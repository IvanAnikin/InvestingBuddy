## Objective

The broker-agnostic execution loop the durable contract was written for: claim
a job under a lease, heartbeat while it runs, and finish by recording an outcome
the contract chose. PostgreSQL-polling mode only — no queue broker, no second
App Service, no cloud dependency.

## Why now

Slice 1 gave the rules and the table and deliberately wired nothing. Until
something claims and executes, `research_jobs` is a table nobody reads and the
V2 `BackgroundTasks` path is still the only way research runs. This is the slice
that makes durability real; Slice 3 is then pure routing.

## Design decisions worth stating

### Claiming is a compare-and-set, not a row lock

`SELECT ... FOR UPDATE SKIP LOCKED` is the obvious PostgreSQL answer and this
slice does not use it. It does not exist on SQLite — which is what the offline
suite runs on — so the production path would be exercised only by whatever
integration coverage happened to exist. And it makes correctness a property of
transaction isolation rather than of the row, which cannot be asserted in a unit
test.

Instead every claim is `UPDATE ... WHERE id = :id AND status = :seen AND attempt
= :seen_attempt`, with `attempt` acting as the version counter that every claim
increments. Two workers issue the same guarded UPDATE; the database serialises
them; the loser gets `rowcount == 0`. One winner, on any dialect, with no lock
held for the handler's runtime. `test_exactly_one_worker_wins_a_contended_claim`
and `test_an_expired_lease_is_reclaimed_exactly_once` run this concurrently
against a real database.

### Re-runs are a new generation, not a reused key

A bare unique `idempotency_key` would make a job un-re-runnable forever, which is
wrong — "analyse Pandora" is a request a user may legitimately make again. The
caller supplies a *base* and the stored key is `base#N`. `enqueue` joins the
newest generation while it is non-terminal and starts `N+1` once it is terminal.
The unique constraint still does the enforcing, per generation.

One consequence is a deliberate improvement on V2 rather than an accident. V2
allowed a resubmit to start a fresh run once the previous one was judged *stale*,
because nothing was going to recover it. Here a lapsed lease is not stale, it is
reclaimable — so a resubmit **joins** the run that is about to be resumed instead
of paying for a second one.

### A shutdown does not fail a job

`asyncio.CancelledError` / `SystemExit` reaching the handler means the *process*
is going away, not that the *job* failed. The row is left exactly as it is, its
lease lapses, and another worker reclaims it. Writing `failed` there would turn
every deployment into permanent data loss and is precisely the V2 behaviour this
phase exists to remove.

### The heartbeat gives the event-loop invariant teeth

A worker owns its job only while it keeps saying it is alive, so a handler that
occupies the event loop cannot heartbeat, its lease lapses, and the job is taken
from it. That converts "someone blocked the loop" from an invisible latency
problem into a visible ownership loss.
`test_blocking_the_event_loop_stops_the_heartbeat` and
`test_the_same_cpu_work_via_to_thread_keeps_heartbeating` are the two halves of
that, and they sit beside the existing
`tests/test_ingestion_event_loop_not_blocked.py` rather than replacing it.

## Security considerations

- **`payload_json` is never logged.** Job inputs stay in the row; the loop logs
  ids, types, statuses, attempts and durations.
- **A failure records the exception TYPE, never its message.** Provider errors
  have been observed to carry credential material — the reason `RedactingFilter`
  exists at all. `test_a_failure_message_carries_only_the_exception_type` pins it.
- **`lease_owner` never reaches a reader.** It is operational identity (host,
  PID); `contract.describe` omits it and
  `test_the_reader_envelope_never_exposes_the_lease_owner` asserts the hostname
  cannot appear in the envelope.
- **A handler cannot write its own outcome.** `JobContext` carries no session, no
  store and no worker API beyond `checkpoint`; a handler that could complete
  itself could record an outcome that contradicts what happened.
  `test_the_handler_never_receives_a_session_or_the_store` pins the field set.
- **Ownership guards every write.** Heartbeat, complete, fail and cancel all
  require `lease_owner = :owner`, which is what stops a worker whose lease
  lapsed from overwriting the result of the worker that took over.

## Acceptance criteria

1. **A job survives a worker restart.** ✅ `test_a_job_survives_a_worker_restart`
   kills worker A mid-run, reads the job as `interrupted` without mutating it,
   and has worker B reclaim (attempt 2) and complete it.
2. **An expired lease is reclaimed by exactly one worker, and a duplicate submit
   joins rather than duplicating.** ✅ `test_an_expired_lease_is_reclaimed_exactly_once`
   (6 concurrent reclaims, 1 winner), `test_only_one_row_exists_after_a_duplicate_submit`.
3. **Attempts are bounded, dead-letter is reachable with a reason, and
   cancellation is honoured at a task boundary.** ✅
   `test_attempts_are_bounded_and_dead_letter_is_reachable`,
   `test_cancellation_is_honoured_at_a_task_boundary` (step 1 completes, step 2
   never starts).
4. **No V2 regression and no vocabulary drift.** ✅ full suite 4433 → 4488
   (+55, none lost); `interrupted` is never stored
   (`test_interrupted_is_never_stored`).

The new file was run in isolation **and** in the full suite, and the first
version of it failed only in the full suite: two liveness tests asserted a
heartbeat count after a fixed `asyncio.sleep`, which is a wall-clock assertion

instead of for a duration. This is the order-dependent-failure pattern the
acceptance strategy warns about, caught locally this time.
