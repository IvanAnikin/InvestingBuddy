# V3.16.1b — Root-Cause Measurement

Case A was established in production (see
[`v3.16.1a-production-acceptance-report.md`](v3.16.1a-production-acceptance-report.md)):
all eight investigator write-ups stopped on `finish_reason: length`.

The brief permits V3.16.1b to change output-budget and response-shaping behaviour, but
requires that four things be *inspected* first, and forbids blindly multiplying
`max_tokens`. This document is that inspection. Every number below was measured against
the live `deepseek-v4-flash` endpoint using the investigator's real prompt, at the real
`MAX_EVIDENCE_CHARS` cap, at the real `max_tokens=1200`.

---

## 1. The hypothesis I started with, and why it was wrong

**Hypothesis:** `DeepSeekModelProvider.complete()` never passes `json_mode`, so the API
is never sent `response_format: {"type": "json_object"}`. The model therefore emits a
prose preamble, the preamble consumes the 1,200-token ceiling, and the JSON is cut
mid-object.

It was a tidy story and it fit every production counter. It is also **false**, and the
first probe said so:

| Mode | finish | out tokens | first `{` at | parses |
|---|---|---|---|---|
| `json_mode=False` (production today) | `length` | 1200 | **char 0** | no |
| `json_mode=True` | `length` | 1200 | **char 0** | no |

`first '{' at: 0` in both. **There is no prose preamble.** The model begins emitting
JSON immediately and simply has more to say than 1,200 tokens allows. Turning on
`json_mode` alone does not fix the truncation.

Recording this because the brief was right to forbid inference: the hypothesis was
plausible, consistent with the evidence, and wrong. Only measurement separated it from
the truth.

---

## 2. The four required inspections

### 2.1 Did truncation happen before or inside a JSON object?

**Inside, always.** Every failure is a `JSONDecodeError` of the form
`Unterminated string` or `Expecting ',' delimiter`, at a character offset near the end
of the emitted text, with `first '{' at: 0`. The model is cut mid-object, typically
partway through a `gaps[]` entry.

### 2.2 How many tokens were requested and returned?

Requested 1,200. Returned exactly 1,200 on every truncated call. With the ceiling raised
to a deliberately non-binding 4,000, the *unshaped* reply finished naturally at
**1,435 tokens** with `finish_reason: stop` — and produced 4 findings and **5 gaps**.

So production was short by roughly 235 tokens on a typical call. Not a catastrophic
overrun; a ceiling set slightly below what the prompt asks for.

### 2.3 Did evidence serialization inflate the requirement?

**Input: no. Output: yes, indirectly.**

Prompt length averaged 2,839.9 tokens, consistent with an evidence block filled close to
`MAX_EVIDENCE_CHARS = 12_000`. That is large but it was never the constraint — the
failure is on the completion side.

The indirect effect is real: eight evidence items covering one topic invite the model to
write four findings *and* five gaps about them. More evidence means more to say.

### 2.4 Can a smaller structured response solve this more safely than raising tokens?

**Partly — and this is the most important measurement in the slice.**

`investigator.py` already enforces `[:MAX_FINDINGS_PER_QUESTION]` — 4 findings and 4
gaps — *after* parsing. **The prompt never tells the model those caps.** So the model
writes a 5th gap the code was always going to discard unread, and the space that 5th gap
consumes is what pushes the 4 items the code *does* keep past the ceiling. The
overproduction destroys the output, then the code discards the overproduction anyway.

This is the campaign's signature defect wearing a new hat: the consumer's limit is never
communicated to the producer.

Telling the model the truth about those caps, plus per-field character bounds, moves the
distribution a long way:

| Configuration | parsed | median out | max out |
|---|---|---|---|
| Unshaped (production today) | 0/8 in prod | — | 1200 (clipped) |
| Shaped, `json_mode=False` | 3/4 | — | 1200 (clipped) |
| Shaped, `json_mode=True`, 4 findings/3 gaps | 5/5 | ~840 | 901 |
| Shaped, `json_mode=True`, 4 findings/4 gaps | 10/12 | ~860 | 1200 (clipped) |

Shaping cuts the median requirement from ~1,435 to ~860 tokens. **But it does not make
the tail safe.** With the ceiling lifted to a non-binding 2,400, the shaped distribution
across 15 replies was:

```
min 668   median 860   p90 1186   max 1443      (n=15, all finish=stop, 0 malformed)
budget 1200 covers 13/15    budget 1600 covers 15/15
```

and a wider acceptance run later observed a single shaped reply at **1,763 tokens**.

**Conclusion: a smaller structured response is necessary but not sufficient.** The reply
length has a long right tail, so no fixed ceiling can be made safe by sizing alone.
Chasing the tail with a bigger number is precisely the blind multiplication the brief
forbids.

---

## 3. What `json_mode` is actually for

It does not fix truncation (§1). What it fixes is **variance**. Shaped, without it, 1 run
in 4 drifted to the ceiling (`out=[1200, 966, 1133, 1018]`). Shaped, with it, the same
prompt ran `[812, 864]`, `[815, 901, 782]` — tighter and lower. It stabilises length; it
does not bound it.

It is also free of the HTTP 400 risk that made it opt-in: `_json_hinted()` guarantees the
literal the API demands regardless of caller wording.

---

## 4. The selected fix

Four changes, each traceable to a measurement above. None of them weakens the citation
guard, the validator, or playbook blocking semantics.

1. **Tell the model the caps the code already enforces.** Derived from
   `MAX_FINDINGS_PER_QUESTION`, not hardcoded in the prompt string — so the prompt cannot
   drift from the constant later. Plus per-field character bounds and an explicit token
   target. *(§2.4: median 1,435 → ~860.)*
2. **Enable `json_mode` on the investigator's write-up call.** *(§3: removes length
   variance.)*
3. **Raise `max_tokens` 1,200 → 1,800.** Read off the measured distribution in §2.4, not
   multiplied. 1,200 covered 13/15 shaped replies; 1,800 clears the observed max of
   1,443 with margin, and the later 1,763 outlier still fits.
4. **Retry once, tighter, when a reply truncates.** This is the part that makes the tail
   safe. It uses the `truncated` signal V3.16.1a made observable — the instrument becomes
   actionable rather than merely descriptive.

Measured retry shape (at most 2 findings, 2 gaps, 120/100 chars, "fit inside 500 tokens"):

```
cash_runway        4/4    out=[267, 325, 267, 240]
regulatory_posture 4/4    out=[261, 229, 337, 245]
pipeline_state     4/4    out=[252, 242, 333, 265]
                  12/12   median 263   max 337   margin under 1800: 1463
```

A truncated first attempt therefore stops being a total loss and becomes a shorter
complete answer.

### 4.1 Acceptance of the combined configuration

Shaped + `json_mode` + `max_tokens=1800`, across three question types × 5 runs:

```
pipeline_state      5/5   out=[812, 938, 742, 845, 814]
regulatory_posture  5/5   out=[1235, 664, 806, 765, 1261]
cash_runway         5/5   out=[1763, 856, 682, 933, 1092]
                   15/15  median 845   4 findings + 4 gaps on every call
```

### 4.2 The fix costs fewer tokens, not more

Production today burns 1,200 completion tokens per call and returns **zero** findings,
because all 1,200 are thrown away. The shaped configuration uses a median of **845** and
returns four findings. Raising the *ceiling* does not raise spend — completion tokens are
billed on what the model actually writes, and shaping makes it write less.

---

## 5. One thing the probes found that must NOT be "fixed"

In one acceptance run the model cited `ev:c:0000` — an id that was never in the allowed
set. The citation guard is what discards such a finding, and in production it is what
`statements_dropped_uncited` counts.

The guard remains necessary and is not touched by this slice. A model that invents
citation ids under length pressure is an argument for keeping the guard, not for
relaxing it.

---

## 6. Residual risk, stated plainly

The right tail is long and 15–27 samples do not bound it. A reply can still exceed 1,800
tokens. When it does:

- the retry (§4, change 4) converts it into a short complete answer, and
- if the retry also truncates, `responses_truncated` and the per-question gap text record
  it exactly as they did in §3.4 of the acceptance report.

The failure mode after V3.16.1b is therefore *visible and degraded*, never *silent and
total*. That is the whole difference between this slice and the state it replaces.

---

## 7. Three things reading the patch found, that the measurement had not

The four changes in §4 were all necessary and none was sufficient on its own. Reviewing
the implementation against this document surfaced three further defects — two of them
introduced *by* the fix, and one it exposed. Recorded here because a slice whose stated
fix and shipped fix differ is a slice whose documentation has started lying.

### 7.1 The retry blinded the instrument built one slice earlier

`finish_reasons` is the field V3.16.1a's Case A verdict rests on, and nothing else. The
first implementation recorded it **once per question, from the reply that was kept** — so
a run in which all eight first attempts hit the ceiling and all eight retries recovered
would have reported:

```json
{"finish_reasons": {"stop": 8}, "responses_retried_after_truncation": 8}
```

Two fields disagreeing about the same eight calls, with the authoritative one wrong. The
recording moved into `_complete`, so **one model call means one recorded reason**, and the
invariant is now:

```
sum(finish_reasons.values()) == responses_total + responses_retried_after_truncation
```

`responses_truncated` deliberately keeps its V3.16.1a meaning — *the reply the run used*
was cut off — so a recovered retry leaves it at zero and the retry counter is what says
the strain was there.

### 7.2 A flaky retry could erase a correct diagnosis

`_retry_shorter`'s model call sat inside `_write_up`'s exception handler. A timeout on the
*second* attempt therefore replaced "truncated at the output limit" — correct and
actionable — with "the model failed: TimeoutError", for a question whose cause the run had
already identified correctly.

The retry is a **bonus** attempt on an already-diagnosed question, so its failure is now
swallowed and the first reply stands. **A retry must never leave the run worse off than no
retry.**

### 7.3 The transport seam was narrower than its own implementation

`json_mode` was implemented on `HttpDeepSeekTransport.complete` and never declared on the
`DeepSeekTransport` Protocol that `DeepSeekModelProvider` calls through. Forwarding it
produced:

```
providers.py:678: error: Unexpected keyword argument "json_mode" for "complete" of
                  "DeepSeekTransport"  [call-arg]
```

and `FakeDeepSeekTransport` — the only transport the unit suite touches, and which asserts
it satisfies that Protocol — raised `TypeError` on four existing tests. The Protocol and
the fake both now declare it, and the fake records it so a caller's opt-in is assertable
rather than assumed.

This is the same defect class as the slice itself, one layer down: **a capability that
exists, is reachable, and that nothing in the declared contract admits to.** It is why the
acceptance test for the opt-in runs through the shared fake and not a local stub — a stub
would have accepted the keyword and hidden the hole.
