### 2.1 Narrowing by elimination (each step is forced)

1. **`outcome.findings` was empty.** If a draft had reached `record_finding` unsupported,
   the loop would have written the distinctive gap *"stated … with no evidence or
   calculation behind it"* (`loop.py:325-338`). Production shows no such gap. **So the
   ledger was never reached.** The break is upstream of insertion and upstream of
   validation.

2. **Evidence was non-empty.** An empty evidence list produces *"No citable evidence was
   retrieved for X"* (`investigator.py:401`). `pipeline_state` and `regulatory_posture`
   did **not** receive that gap — while `identity`, `cash_runway`, `dilution` and others
   did. So for those two, `_gather` returned citable items and `_write_up` ran.

3. **Therefore `_write_up` returned `([], [], False)`** — no finding, no gap, not answered.

4. **`_write_up` has exactly three ways to return that**, and two are silent:

   | Path | Leaves a trace? |
   |---|---|
   | fabricated citation ids | gap **and** `fabricated_citations_discarded++` → **it is 0, so not this** |
   | period/scope conflict | gap → **absent, so not this** |
   | **payload has no `findings` and no `gaps`** | **nothing** |
   | **every finding cited nothing → `if not real: continue`** (:622) | **nothing** |

**The failure is one of the two silent paths.** Neither is counted, so production telemetry
cannot currently distinguish them. That is the primary finding.

## 3. Root cause: the V3 provider path drops the reason

```python
# investigator.py:687  _complete_json
if hasattr(self.client, "complete_json"):                  # ← V2 LLMClient
    return await self.client.complete_json(...)            #   repairs, then RAISES
response = await self.client.complete(...)                 # ← V3 ModelProvider
payload = getattr(response, "payload", None)
return payload if isinstance(payload, dict) else {}        #   SILENT {}
```

```python
# deepseek/providers.py:673
payload = _json_object(response.text)
return ModelResponse(
    payload=payload if payload is not None else {},        # unparseable → {}
    finish_reason=response.finish_reason,                  # ← recorded here
    truncated=(response.finish_reason or "").lower() in {"length", "max_tokens"},
)                                                          # ← and discarded above
```

**`ModelResponse` carries `truncated` and `finish_reason`. `_complete_json` returns
`payload` alone.** The reason the payload is empty is produced correctly and thrown away
one layer up — the same defect shape as the SEC SIC code, the server numeric verdict, the
classification snapshot and `index_version`. This is the fifth instance.

### 3.1 The asymmetry that decides it

| Client shape | Malformed / truncated reply | Visible? |
|---|---|---|
| **V2 `LLMClient.complete_json`** (`llm/client.py:265`) | "repairing one malformed reply if needed… **Raises LLMJsonError**" → caught at `investigator.py:572` → **`tool_unavailable` gap** | **yes** |
| **V3 `ModelProvider.complete`** (deepseek) | `payload={}`, no repair, no raise, reason discarded | **no** |

**Production routes `investigator → deepseek`** (chair and red_team → azure_openai). So the
one slot that writes findings is the one slot on the silent path. Had the investigator been
on Azure, this would have surfaced as a gap on the first run.

### 3.2 Why truncation is the leading hypothesis

* `LLMInvestigator.max_tokens = 1200` (`investigator.py:372`) and **the pipeline does not
  override it** (`v3_pipeline.py:446` passes `client=`, not `max_tokens=`).
* Measured: **7,285 completion tokens over 7 calls = 1,041 average**, against a 1,200 cap.
  An average that close to the ceiling means several calls almost certainly finished at
  exactly 1,200 — i.e. `finish_reason="length"`.
* A JSON object cut mid-emission is unparseable. `_json_object` (`providers.py:177`) is
  prose-tolerant but not truncation-tolerant: it takes `raw.find("{")` to `raw.rfind("}")`,
  and for a truncated object the last `}` is typically a *nested* one, so the slice is
  invalid JSON → `None` → `payload={}`.
* Prompt size is consistent: 20,010 prompt tokens / 7 = ~2,859 per call, from up to six
  corpus hits under `MAX_EVIDENCE_CHARS = 12_000`.

**This is a hypothesis, not a proof, and it cannot be proven from current telemetry —
because `finish_reason` is exactly the field that is discarded.** Anyone claiming certainty
here would be inventing it. Which is the point: fix observability first.

### 3.3 A contributing factor worth fixing

`_evidence_of` (:218) sets the evidence text to a **JSON dump of the whole hit payload**,
truncated to 1,500 chars:

```python
text = json.dumps({k: v for k, v in item.items() if k not in {"payload","raw"}})[:1500]
```

For a corpus hit that is `evidence_id`, `score`, `lexical_score`, `semantic_score`,
`matched_terms`, `citation_label`, `canonical_url`, `title`, `document_type`,
`source_tier`, `access_class`, `period_key`, `period_type`, `scope_type`, `scope_name`,
`scope_key`, `page_start`, `page_end` **and** the chunk text — with the chunk text last and
therefore first to be cut, and the result often invalid JSON mid-string. The model is asked
to reason over metadata noise and a mangled excerpt, then to restate it within 1,200 output
tokens. Not the root cause; a real amplifier.

## 4. Design

**Principle: make the failure impossible to have silently, before changing what the model
is asked to do.** If we raise `max_tokens` first and findings appear, we will have fixed it
by luck and learned nothing; if they do not, we will still be unable to say why.

### V3.16.1a — Observability (no behaviour change)

1. **Stop discarding the response.** `_complete_json` returns the `ModelResponse`, not just
   `payload`. `_write_up` reads `truncated`, `finish_reason` and response length.
2. **A non-dict / empty payload becomes a GAP**, matching the V2 path's behaviour:
   *"the model returned no parseable JSON for `pipeline_state` (finish_reason=length,
   truncated=true); the evidence exists and was not interpreted."*
3. **Count the silent drop.** New loop counters, surfaced on the run exactly as
   `fabricated_citations_discarded` already is:
   * `statements_dropped_uncited` — a finding that cited nothing (`if not real`)
   * `responses_unparseable`
   * `responses_truncated`
4. **Propagate to the outcome** so `V3ResearchOutcome.degraded` names it. A run that
   produced no findings because every model reply was truncated must say so on the report.

Nothing here changes what is written to the ledger. It changes only what the run can tell
you about itself.

### V3.16.1b — Corrective (after 1a measures the real distribution)

Apply only what the measurement justifies:

* **Budget** — make the investigator's `max_tokens` configurable
  (`V3_INVESTIGATOR_MAX_OUTPUT_TOKENS`, default raised from 1200) and pass it from
  `v3_pipeline`. Justified only if `responses_truncated > 0`.
* **Repair parity** — give the `ModelProvider` branch the same one-shot JSON repair the V2
  client already has, rather than two different contracts for the same failure.
* **Evidence rendering** — send the chunk **text** plus a small labelled header
  (`period`, `scope`, `tier`, `citation_label`), not a truncated JSON dump of the hit.
* **Uncited statements** — decide deliberately: drop-with-a-gap (recommended, symmetric
  with every other rejection path) rather than drop-in-silence.

### Explicitly NOT in scope

* Weakening the citation guard. A finding with no real citation must still never enter the
  ledger — the rule is right; only its silence is wrong.
* Changing `record_finding`'s `UnsupportedFindingError` contract.
* Changing Council blocking semantics.
* Re-prompting or re-trying a truncated reply automatically (that is a cost decision, and
  it belongs with V3.17's budget work).

## 6. Testing

| Kind | Test |
|---|---|
| **Producer** | a provider returning prose / truncated JSON yields `ModelResponse(payload={}, truncated=True, finish_reason="length")` |
| **Producer** | a finding whose `evidence_ids` is `[]` increments `statements_dropped_uncited` |
| **Consumer** | **`_write_up` turns an unparseable payload into a GAP** — the test that would have caught this. Today an empty payload produces nothing, and no test fails. |
| **Consumer** | the run's `degraded` list names truncation when it occurred |
| **End-to-end** | given six real corpus chunks and a *well-formed* model reply citing two of them, a Finding reaches the ledger with inherited period/scope — the path has never been exercised end to end on corpus evidence |
| **Regression** | fabricated ids still produce a gap and still increment the existing counter |
| **Regression** | an unsupported draft still raises `UnsupportedFindingError` |

**Forbidden:** a test asserting `payload == {}`. That asserts the silence rather than the
behaviour, and is the shape of test that let this survive.

## 7. Relationship to V3.17

V3.17's escalation loop reruns research, which runs into this same step. Until 3.16.1a
lands, an escalation round that produces no findings is indistinguishable from one where
the model was simply cut off — so the loop could not tell "no more evidence to find" from
"we never read the reply".

**Recommendation: V3.16.1a before V3.17.1.** It is small, additive, migration-free, and it
makes V3.17's improvement threshold trustworthy.

---

## 8. Honest summary

The investigator retrieves real, citable, T1 filing evidence and produces nothing from it,
and the platform records no reason. The break is between the model returning bytes and the
platform parsing them: `ModelResponse` knows whether the reply was truncated and
unparseable, and `_complete_json` throws that away, returning `{}`. Two silent `continue`
paths in `_write_up` then complete the erasure.

Which of the two silent paths fired **cannot be established from production telemetry**,
because the field that would say is the field being discarded. Token arithmetic (1,041
average against a 1,200 cap) points hard at truncation, and the route being DeepSeek — the
one client shape that does not raise on a malformed reply — explains why it is invisible
rather than a gap.

So V3.16.1a is not a fix. It is the instrument that tells us which fix to make.
