## 4. Root-cause classification

The brief defined five cases and forbade inferring between them from elapsed time,
token count or probability. The classification below rests on one field only:
`finish_reasons`, which the provider itself reported.

| Case | Meaning | Verdict |
|---|---|---|
| **A** | Truncated responses | **THIS ONE** |
| B | Unparseable but not truncated | No — every unparseable reply was also flagged truncated (8 = 8) |
| C | Genuinely empty | No — `responses_empty_payload: 0` |
| D | Valid findings dropped as uncited | No — `statements_dropped_uncited: 0` |
| E | Valid findings that failed downstream | No — `responses_with_findings: 0`, so nothing reached downstream |

**CASE A, measured.** `finish_reasons: {"length": 8}` is the provider stating, for all
eight write-ups, that it stopped because it hit the output limit. `responses_truncated`
and `responses_unparseable` are both exactly 8 and describe the same eight calls: every
reply was cut off, and every reply was cut off *mid-JSON*, so none could be parsed.

The three cases that would have pointed elsewhere are excluded by counters that are
exactly zero, not by argument.

### 4.1 What this rules out

- Not an outage. Nine model calls succeeded and returned billable tokens.
- Not a prompt-safety refusal. No `content_filter` finish reason appeared.
- Not the citation guard. `statements_dropped_uncited: 0` — the guard discarded nothing,
  because nothing ever parsed far enough to reach it.
- Not an evidence famine. Seven `evidence_unavailable` gaps are real and separate, but
  the eight `tool_unavailable` gaps were *manufactured by the truncation itself*.

## 5. DERIVED — stated as inference, and labelled as such

These do not carry the same weight as §3 and are marked accordingly.

1. Average completion length was 1,103.2 tokens against a 1,200 ceiling — consistent
   with replies running into the limit. This **corroborates** Case A; it is not the
   evidence for it. The evidence is `finish_reason`.
2. Average prompt length was 2,839.9 tokens, consistent with an evidence block filled
   close to `MAX_EVIDENCE_CHARS = 12_000`. Input size was never the failure; the
   failure was on output.
3. `stopped_by: max_tasks` with `rounds: 2` suggests the loop kept re-asking questions
   that truncation had guaranteed could never be answered — wasted work downstream of
   the real defect.

## 7. Verdict

**V3.16.1a: ACCEPTED.**

The slice made a silent failure legible, and the first production run it observed
identified the cause unambiguously. The defect it exposed is the campaign's signature
shape once more — *a correct value produced and then discarded one layer up*. Here the
discarded values were `ModelResponse.truncated` and `finish_reason`, and discarding them
cost eight research questions and two blocking answers per run.

This is the sixth confirmed instance in this campaign.

**V3.16.1a does not fix anything, and was not meant to.** The fix is V3.16.1b, which is
constrained by §5 of the brief: *do not blindly multiply `max_tokens`*. The measurement
required before changing a single number is recorded in
[`docs/v3.16.1b-root-cause-measurement.md`](v3.16.1b-root-cause-measurement.md).
